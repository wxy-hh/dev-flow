# Dev Flow 可信交互与语义失效优化

Status: implemented; ready-for-review

## Problem Statement

Dev Flow 在两次真实项目运行中都能按照 Core 派生的路线完成并 finalize，但用户为此承担了不必要且容易误导审计的恢复成本。

用户已经明确回答过的问题，可能因为宿主 hook 与 feature revision 不同步而无法落账，甚至在 feature 的第一个 revision 永久卡住；同一执行批准会在计划重新登记或配置恢复后重复出现；多个文件的归属只能逐一确认，用户明确说“全部纳入”也不能形成一次正式批量决定。hook 中断后，系统不能尽早说明接线已经失效，某些文件又会因为“已经观察过”而不再进入归属对账，最终迫使操作者重建 host event 或直接编辑控制状态。

证据失效同样过于粗糙。`.dev-flow` 未被业务仓忽略时会进入 governed roots 指纹，使 Dev Flow 自己写入状态就足以让 review basis 变化。项目验证命令的 guarantee 缺口直到最终 verification 才暴露；中途补充一个命令又会让完整 Trace、计划审查和执行批准重新基准。已经由审查角色确认修复的 blocking finding，也会因为整个 review batch 的 basis 变化重新成为 blocker，并被错误地引导为“接受风险”。

从用户角度看，这些行为混淆了三件不同的事：真实用户是否回答过、执行内容是否真的改变、某项证据是否只在局部失效。结果是流程虽然严格，却不能做到“严谨且不扰民”，且恢复动作有时会制造与事实相反的审计语义。

## Solution

Dev Flow 将可信交互统一为一个深模块：Core 先登记当前问题，再接受同一宿主随后捕获的一次回答；真实先后顺序由 append-only 事件账本证明，不再用 feature revision 代替用户回合。原生 MCP 表单可在同一次调用内可信落账，文本回答继续要求同宿主、问题之后、唯一且未消费。所有问题类型共享同一呈现、回答、重放保护和恢复合同。

Dev Flow 同时将全局证据失效改为语义切片失效。工作区观察与工作区归属分开；工作流控制目录从业务指纹中永久排除；验证能力在路线锁定前检查；项目配置通过受并发保护的更新入口按变化种类只使相关证据失效。执行批准绑定稳定的执行授权依据，而不是阶段重进、工件文件哈希或 review batch ID。审查 finding 的解决状态绑定对应审查角色的语义依据，无关变化继续复用，相关变化才交回原角色复核。

工作分两批交付。第一批优先消灭死锁、hook 盲区、指纹自污染、归属旁路和配置晚发现；第二批完成执行批准复用与 finding 精细继承。两批都保持 fail-closed、显式用户决定、同宿主证据和一次性消费，不压缩正常路线，也不降低 Core 派生的治理下限。

## User Stories

1. 作为 Dev Flow 用户，我希望一个真实回答只需要说一次，从而不会为了满足系统留证而重复确认同一决定。
2. 作为 Dev Flow 用户，我希望 feature 的第一个归属问题可以正常回答，从而不会在 revision 0 永久卡住。
3. 作为 Dev Flow 用户，我希望系统按问题与回答的真实先后顺序认定回答，从而不受内部状态 revision 是否推进影响。
4. 作为 Dev Flow 用户，我希望原生 MCP 表单中的选择能够当场落账，从而不会在点击选项后还要再发送一条相同文本。
5. 作为文本交互用户，我希望 Dev Flow 在宿主不支持原生表单时提供一致的文本回退，从而仍能完成同一个正式决定。
6. 作为安全敏感用户，我希望旧消息不能被拿来回答后来出现的问题，从而避免历史意图被错误重放。
7. 作为跨宿主用户，我希望 Claude 捕获的回答不能被 Codex 消费，反之亦然，从而保持回答来源可信。
8. 作为安全敏感用户，我希望一条用户事件最多解决一个问题，从而避免一次确认被多个门禁复用。
9. 作为 Dev Flow 用户，我希望路线确认、文件归属、现场取舍、执行批准和风险决定遵循相同规则，从而不必记住每种问题不同的回答方式。
10. 作为 Dev Flow 用户，我希望系统清楚展示当前唯一待回答问题，从而不会误答已过期或并行出现的问题。
11. 作为存在多个未归属文件的用户，我希望先看到完整路径清单，从而理解批量决定会影响哪些文件。
12. 作为存在多个未归属文件的用户，我希望可以正式选择“全部纳入当前任务”，从而用一次回答完成明确的批量归属。
13. 作为存在多个未归属文件的用户，我希望可以正式选择“全部排除并先处理”，从而不必逐个重复同一决定。
14. 作为需要精细控制文件归属的用户，我希望可以选择逐个确认，从而不会被迫批量处理来源不同的改动。
15. 作为 Dev Flow 用户，我希望一个未归属文件即使已经被 checkpoint 观察过也继续待决，从而不会因为观察记录覆盖归属缺口。
16. 作为 Dev Flow 用户，我希望系统自动区分“看见过这个文件”和“知道它属于谁”，从而不需要直接编辑状态修复 ownership。
17. 作为支持宿主的用户，我希望开始任务前就知道 hook 是否正常接线，从而不会运行到一半才发现证据从未被捕获。
18. 作为正在执行任务的用户，我希望 hook 中断时 Dev Flow 在关键推进动作前暂停并解释原因，从而不会继续累积无法证明归属的写入。
19. 作为 Dev Flow 用户，我希望 doctor 区分 hook 未安装、已安装但没有活跃信号、以及恢复后的健康状态，从而能采取正确的恢复动作。
20. 作为从 hook 故障恢复的用户，我希望系统自动重新对账工作区，从而只需回答真正无法判断的归属问题。
21. 作为从 hook 故障恢复的用户，我希望恢复过程不要求伪造 user-prompt 事件，从而保持审计账本真实。
22. 作为从 hook 故障恢复的用户，我希望恢复过程不要求直接修改 state，从而继续遵守 Core 是唯一状态写入者的约束。
23. 作为 governed root 配置为仓库根目录的用户，我希望 `.dev-flow` 永远不进入业务指纹，从而 Dev Flow 自己写状态不会使 review basis 变化。
24. 作为业务仓维护者，我希望正确性不依赖 `.gitignore` 中是否存在 `.dev-flow`，从而不会因遗漏一行配置形成流程死锁。
25. 作为业务仓维护者，我希望 Dev Flow 不自动修改 `.gitignore`，从而插件不会擅自改变业务仓的版本控制策略。
26. 作为计划审查用户，我希望只有业务内容变化才会改变 governed roots fingerprint，从而状态、日志和快照写入不会触发无意义重审。
27. 作为初始化项目的用户，我希望配置至少提供所有路线都需要的 targeted guarantee，从而不会创建一个注定无法完成验证的项目配置。
28. 作为准备锁定路线的用户，我希望系统提前检查该路线需要的全部 verification guarantee，从而缺口在写需求、计划和 Trace 前暴露。
29. 作为配置存在缺口的用户，我希望错误明确列出缺失 guarantee 和恢复动作，从而不用等到最终 verification 才猜测原因。
30. 作为项目维护者，我希望通过受 Core 管理的配置更新入口补充验证命令，从而不用直接修改 project control state。
31. 作为项目维护者，我希望配置更新使用旧配置哈希做并发保护，从而不会覆盖其他会话刚刚完成的配置变化。
32. 作为进行中任务的用户，我希望新增一个未被现有 RU 引用的验证命令只更新验证能力，从而不会推倒需求、计划和审查。
33. 作为进行中任务的用户，我希望扩充命令的 `provides` 只影响 guarantee 覆盖，从而不会把业务执行语义误判为改变。
34. 作为进行中任务的用户，我希望修改或删除一个已被 RU 引用的命令只使对应恢复与验证切片失效，从而其他独立 RU 继续保留证据。
35. 作为安全敏感用户，我希望 governed roots 或 enforcement 的广泛变化要求显式重分类或恢复，从而高影响配置不能伪装成普通验证补充。
36. 作为已经批准执行的用户，我希望相同执行语义在阶段重进后继续保留批准，从而不会因为流程恢复重复询问“确认开始执行”。
37. 作为已经批准执行的用户，我希望 TEST-only、生成投影、无关配置和非执行文档变化不撤销批准，从而批准只绑定真正的授权对象。
38. 作为安全敏感用户，我希望 scope、执行相关分类、TASK/RU、文件范围、恢复语义或阻断风险变化时重新确认执行，从而批准不能覆盖用户从未看过的新影响。
39. 作为 Dev Flow 用户，我希望状态能够解释批准被复用或失效的原因，从而审计者可以理解系统为何没有重问或为何必须重问。
40. 作为计划审查用户，我希望已经修复的 blocking finding 在无关批次变化后保持已解决，从而不会重复处理同一个问题。
41. 作为计划审查用户，我希望相关审查角色的输入变化时由原角色复核旧 finding，从而修复结论不会在真正相关的变化后被盲目沿用。
42. 作为计划审查用户，我希望复核结果可以明确记录“仍已修复”或“重新阻断”，从而 finding 生命周期与当前事实一致。
43. 作为风险决定的用户，我希望系统只对当前审查角色明确判定仍阻断的问题提供风险接受，从而不会把过期的修复结论改写成用户接受风险。
44. 作为专项风险审查用户，我希望 specialty-risk 角色随相关计划与 Trace 语义变化而重新审查，从而角色复用不只依赖风险标签是否存在。
45. 作为审计者，我希望 resolved、needs-revalidation、still-blocking 和 risk-accepted 具有互不混淆的含义，从而审计日志不会说出与真实处理相反的话。
46. 作为现有 Dev Flow 5.0 active feature 的用户，我希望升级后原任务可以继续，从而不必因为新增交互或失效信息而 finalize、abandon 或重开任务。
47. 作为现有 Dev Flow 5.0 active feature 的用户，我希望 Core 自动补齐旧记录缺少的新信息，从而兼容恢复不需要人工编辑状态。
48. 作为 Claude 与 Codex 接力的用户，我希望两个宿主使用相同的交互与失效合同，从而换宿主不会改变当前任务的治理语义。
49. 作为插件维护者，我希望所有交互复杂性集中在一个模块中，从而修复一次即可覆盖所有问题类型和两个宿主。
50. 作为插件维护者，我希望配置差异被分类为明确的影响切片，从而不再通过整份配置哈希触发全局失效。
51. 作为插件维护者，我希望错误返回稳定代码、用户影响和单一恢复动作，从而 Skills 不需要猜测下一步或组织人工旁路。
52. 作为插件维护者，我希望第一批可以独立消灭卡死与状态旁路，从而高优先级可靠性改进不必等待全部语义复用工作完成。
53. 作为插件维护者，我希望第二批建立在第一批统一交互和切片失效基础上，从而批准与 finding 复用不再重复实现证据逻辑。
54. 作为 Dev Flow 用户，我希望本轮优化不删减正常路线的阶段、工件或 Core 派生义务，从而可靠性优化不会暗中降低治理强度。

## Implementation Decisions

- 采用两阶段交付。第一阶段覆盖可信交互顺序、hook 健康、工作区归属、控制目录隔离、验证能力前置检查和配置切片更新；第二阶段覆盖执行授权依据与 review finding 的角色级复用。
- 建立统一的交互模块作为呈现和回答的唯一 seam。其外部接口只表达“以当前依据呈现一个问题”和“以可信来源提交一次回答”；问题类型、选项匹配、原生表单、文本回退、事件消费、跨宿主拒绝和幂等恢复都隐藏在实现内部。
- 所有用户问题写成同一种 interaction 记录。现有 pending decision 形状作为公共读取兼容投影保留，不再作为第二份可独立变化的事实来源。
- 每次问题呈现生成稳定 presentation 标识，并在 Core 事件账本中留下可定位记录。文本回答必须位于该记录之后、来自当前宿主、匹配当前问题且尚未消费；feature revision 只承担状态并发控制，不再承担用户回合排序。
- 原生 MCP elicitation 的 accepted form response 是可信回答来源，可在呈现工具的同一次调用中解决 interaction；decline、cancel、超时或协议失败保持 interaction pending，并统一降级为文本回答。
- 不引入模糊自然语言猜测。普通文本回答继续匹配公开选项或明确批准短语；多文件归属通过正式的“全部纳入、全部排除、逐个确认”选项表达批量意图。
- 宿主适配器额外记录项目级健康信号，使尚未创建 active feature 时也能证明 SessionStart 或 UserPromptSubmit 接线。健康信号只用于诊断与推进前检查，不允许宿主适配器自行改变工作流状态。
- 开始任务、实现 checkpoint、implementation 完成和 finalize 前执行宿主健康与归属检查。健康信号缺失时返回可恢复阻塞；恢复后由 Core 对账，不创建手工事件注入入口。
- 工作区模型分别保存观察进度与归属结论。对账时从 feature 基线到当前工作区重新求出所有仍未归属路径，而不是只看自上次观察后新变化的路径。
- `.git` 与 `.dev-flow` 是业务枚举、指纹、checkpoint、review basis 和 delivery snapshot 的内建排除项，优先级高于 project config 与 Git ignore 结果。
- 项目初始化校验至少一个非 preflight 命令提供 targeted guarantee。路线预览完成、正式锁定前，Core 计算该路线的完整 guarantee 集并验证配置覆盖；缺口不会创建 Trace、review ledger 或路线确认。
- 增加 `dev_flow_update_project` 公共工具，输入完整候选配置和 `expectedConfigSha256`，输出新配置哈希、变化分类、受影响证据以及唯一恢复动作。已存在项目的 `dev_flow_init_project` 只允许幂等重复初始化，配置变化必须走更新工具。
- 配置依据拆为治理范围哈希、验证目录哈希与逐命令哈希。新增未引用命令或扩充 guarantee 只使 verification capability 变化；命令正文、参数、工作目录或删除操作只使引用该命令的 Trace/RU 切片失效；治理范围与 enforcement 变化进入显式重分类或高影响恢复。
- Trace 登记返回执行变化、验证变化或文档变化。变化分类由 Core 持久化的结构化 Trace 关系与命令绑定确定，不由调用者直接声明。
- 执行批准绑定新的执行授权依据：scope、执行相关分类、当前 REQ/AC/TASK/RU 图、文件范围、恢复语义以及当前阻断风险。review batch ID、生成投影、TEST-only 关系、无关配置哈希和阶段位置不属于执行授权依据。
- 批准记录保存执行授权依据哈希。任何工件或配置更新后重新计算：相同则保留 confirmed 记录并写复用原因；不同才撤销批准、重开 approval obligation 并写失效原因。不得因 planning 或 implementation 阶段重进而无条件清空全部 human gates。
- review finding 的 origin 继续不可变；resolved 与 still-blocking 事件额外绑定提交该结果的审查角色语义依据。有效状态以对应角色当前依据计算，不再要求 resolution 的哈希等于整个当前 batch 哈希。
- 新增 needs-revalidation 派生状态。角色依据未变时 resolved 保持终态；依据变化时原角色的新 job 必须收到旧 finding 并提交 resolved 或 still-blocking。只有当前 still-blocking finding 才能进入风险接受。
- specialty-risk 角色的语义依据包括对应风险标签与相关计划/Trace 切片。未知或无法定位的 diff 保持现有保守策略，触发完整角色重审，而不是静默复用。
- 兼容现有 5.0 active state、Trace snapshot 和 review snapshot。新增字段保持可选，读取旧记录时从事件顺序和现有 basis 进行确定性推导；新写入使用新形状。不得要求用户手工迁移或重开任务。
- doctor 增加宿主健康、验证 guarantee 覆盖、未知归属和兼容推导诊断。所有新阻塞错误都提供稳定错误码、用户可见原因、影响以及一个可执行恢复动作。
- 在领域词汇表中记录“可信回答、执行授权依据、证据失效、工作区归属、宿主接线健康”等术语；用 ADR 记录“可信回答按事件顺序绑定”和“治理证据按语义切片失效”两项难以逆转的取舍。

## Testing Decisions

- 最高测试 seam 是公开 MCP 工作流接口。测试在临时 Git 仓中以用户可见工具驱动完整状态变化，并只断言公开状态、错误、审计事件、是否要求用户回答以及最终能否继续路线；不直接测试交互模块内部 helper。
- 第二个必要 seam 是宿主 hook 协议适配，因为 Claude 与 Codex 是两个真实 adapter。通过规范化 hook JSON 输入验证两端记录相同健康信号、用户事件和写入归属，并通过 interop 场景验证一个宿主呈现、另一个宿主继续时的来源限制。
- 纯策略测试只覆盖在公开工作流场景中组合成本过高的变化分类、哈希切片与 finding 状态归约；这些测试断言领域结果，不断言内部调用顺序或私有数据结构。
- 沿用现有动态路线 E2E、host provenance、Git reconciliation、artifact invalidation、verification command cover、review carry-forward 和跨宿主 interop 测试作为 prior art。由统一交互 seam 覆盖的新测试到位后，删除或改写把旧浅模块行为当合同的测试。
- 将两份真实审计记录提炼为回归旅程，而不是依赖手工复现：revision 0 首个 ownership 回答、原生选择后立即落账、六文件批量纳入、hook 中断恢复、`.dev-flow` 指纹自污染、缺 targeted 的配置恢复、三次 execution approval，以及 resolved finding 被误导为风险接受。
- 验证 presentation 与 host prompt 处于同一 feature revision 时仍可按账本顺序解决；presentation 之前的相同文本、另一个宿主的事件、已消费事件和多个候选事件继续失败且不改变状态。
- 验证每种 interaction 都同时覆盖原生 elicitation 与文本 fallback，并产生一致的领域结果、来源记录和下一步。
- 验证多个未知路径的三种批量选项；逐个模式不能遗漏路径，批量模式必须精确绑定当时展示的路径集合，集合变化后旧回答不得继续适用。
- 验证文件在未知归属时被 checkpoint 或 reconcile 观察后仍保持待决；完成归属后重复 reconcile 不再询问。
- 验证 hook 健康、缺失、中断和恢复四种状态；健康检查失败不得推进关键步骤，恢复后的对账不得伪造用户事件或自动接纳未知文件。
- 验证 governed root 为仓库根目录、`.dev-flow` 未写入 `.gitignore` 且包含大量 untracked 状态文件时，业务指纹和 review basis 均保持稳定。
- 验证初始化缺 targeted 失败；不同 XS/S/M/L 与风险组合在路线锁定前准确报告 guarantee 缺口；preflight 命令永远不计 guarantee evidence。
- 验证配置更新 CAS 冲突不覆盖新配置；新增命令、扩充 provides、修改未引用命令、修改已引用命令、删除命令、改变 governed roots 和改变 enforcement 分别产生预期影响切片。
- 验证相同执行授权依据跨计划重新登记、验证配置补充、review batch 重建和阶段重进继续复用批准；scope、TASK/RU、file scope、恢复语义或当前风险变化必须撤销批准。
- 验证 resolved finding 跨无关角色变化保持 resolved；相关角色依据变化进入 needs-revalidation；原角色重新确认后恢复 resolved，判定仍有问题后进入 still-blocking；needs-revalidation 不能直接风险接受。
- 验证 specialty-risk job 在相关计划/Trace 变化时不能仅凭相同风险标签复用，并验证未知 diff 继续保守全量重审。
- 使用真实旧版 5.0 state、interaction、Trace 和 review fixture 验证升级后继续推进；兼容推导必须幂等，重复读取或恢复不能生成不同 basis 或重复问题。
- 每批先运行聚焦测试，再运行 typecheck、全部源码单测、受影响路线和跨宿主测试。源码稳定后再更新受版本控制 bundle，并运行完整发布验证与 bundle 一致性检查。

## Out of Scope

- 不减少或合并正常路线的 requirements、planning、review、approval、implementation、verification 或 finalize 阶段。
- 不删除路线要求的工件、Trace、checkpoint、代码审查或验证义务。
- 不降低 fail-closed、同宿主来源、一次性消费、显式用户决定或 governed write 门禁。
- 不通过模糊语言模型判断把任意自然语言映射为用户选项；批量意图只通过正式选项表达。
- 不支持缺少可信 hook 的第三方 MCP 客户端执行 governed write。
- 不自动修改业务仓 `.gitignore`、stash、reset、清理缓存、提交、推送或发布。
- 不为 Dev Flow 4.x active state 提供迁移器；兼容范围仅为当前 5.0 数据。
- 不在本工作中重新设计路线分类算法、level 下限、风险标签或 review role 集合。
- 不把代码或命令输出交给 Core 做启发式语义判断；变化分类继续依赖明确的结构化合同。
- 不处理仓库中与本 feature 无关的智能体技能迁移、说明文档漂移或其他未提交改动。

## Further Notes

- 最高优先级不是减少正常路线步骤，而是让“相同语义只确认一次、局部变化只重做局部证据、证据缺失时不靠人工旁路恢复”成为可执行合同。
- 第一批完成标准是两份审计记录中的 revision-0、hook 事件重建、state 手改、`.dev-flow` 指纹漂移和 verification guarantee 晚发现均有自动化回归覆盖且不再复现。
- 第二批完成标准是同一 execution approval 不再因无关恢复重复出现，resolved finding 不再因为 batch basis 变化被错误转换为风险接受。
- 当前相关测试全部通过并不代表现有行为正确；部分测试明确固化了完整标签匹配、粗粒度 artifact invalidation 和 batch-wide finding basis。实施时应先用新用户旅程建立期望，再替换这些旧合同。
- 实施必须保留工作区中已有且与本 feature 无关的改动，不得覆盖或顺手整理它们。
