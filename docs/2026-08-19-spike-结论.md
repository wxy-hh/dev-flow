- **宿主**：Claude Code CLI 2.1.234（Bun 编译 arm64，macOS）
- **模型**：kimi-for-coding（K2.7 Coding，经 `api.kimi.com/coding/v1`）——本机 claude 未做 Anthropic 登录，通过 ANTHROPIC_* env 注入 Kimi provider（见附录 A）

## 1. L1 逐项细节

### 1.1 PreToolUse deny + permissionDecisionReason 模型可见 —— 过

方法：三种 matcher（Write/Edit/Bash）各一独立会话；hook 对目标工具 deny，reason 含本次唯一 token；判据 = 文件未写入 ∧ 模型逐字复述理由。

实测输出（模型复述，三例逐一）：

```
SPIKE-L1-1-WRITE-DENY token=l1-1-1787128402-10120 唯一理由文本WRITE
SPIKE-L1-1-EDIT-DENY token=l1-1-1787128402-10120 唯一理由文本EDIT
SPIKE-L1-1-BASH-DENY token=l1-1-1787128402-10120 唯一理由文本BASH
```

Bash 例模型原话："命令被拦截。拦截理由中 SPIKE 开头的整行为：…停手，不再重试。"

**载荷样例（hook 输出，2.1.234 唯一有效格式）**：

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "SPIKE-L1-1-WRITE-DENY token=... 唯一理由文本WRITE"
  }
}
```

⚠ **版本坑（最高优先）**：2.1.234 的 hook JSON schema 顶层**没有** `permissionDecision`/`permissionDecisionReason`。顶层输出这两个键时 debug 日志显示 `Hook JSON output had unrecognized keys (ignored): permissionDecision, permissionDecisionReason.`——**deny 静默失效（fail-open）**，工具照常执行。二进制内嵌 schema 与文档字符串明示：`decision "block" deprecated for PreToolUse, use hookSpecificOutput.permissionDecision instead`。**官方网页文档（code.claude.com/docs/en/hooks、/hooks-guide）滞后于本机版本**，仍在展示顶层写法——MVP 一切拦截型 hook 必须按 hookSpecificOutput 格式输出，且验收时用 debug 日志核对 `unrecognized keys` 为零。

### 1.2 transcript 时效性 —— 不过（裁定：实时检测不可靠，降级"一拦二放+审计"）

方法（客观法，不依赖模型行为）：PreToolUse 时 hook 拿 `payload.tool_use_id`（触发本次事件的 tool_use block 标识），查 transcript 文件是否已含该 id。

实测：**found=false**（hook 触发时刻 transcript 不含触发它的 assistant 消息）。事后验证该 id 已落盘（assistant 消息 + Write tool_use block 均在）。量化滞后：该 assistant 消息 timestamp `08:37:53.865Z`，hook 触发 `08:37:53.920Z`——**消息生成 55ms 后 hook 触发仍读不到**。官方文档亦明示："transcript 文件异步写入、可能滞后，可能尚未包含当前回合最新消息"。

**对设计的影响（MVP 计划 3.2 裁决点）**：

- 意图块存在性检测**不能**用 transcript 实时检测（同回合"文本+工具调用"必然读不到）。
- 落定降级模式"**一拦二放+审计**"：首写 deny 给模板，重试放行但记 `intent.blocked`，finalize 审计显眼标注。
- L3 实测发现的 nuance：**跨回合时 transcript 检测可靠**——模型若先输出意图块文本（该回合结束、落盘完成），下一回合才调工具，hook 能读到（L3 对照 B 中 `transcriptHasIntent=true` 命中）。因此"一拦二放"与"transcript 检测"可并存：检测命中即放行，未命中则一拦二放，两条腿都比纯检测稳。MVP 建议：以"一拦二放"为主通道，transcript 检测作为**放行加分项**（读到模型意图块即放行），不把拦截押在检测上。

### 1.3 SessionStart additionalContext（startup / resume）—— 过

startup 例（模型逐字复述）：`SPIKE-L1-3-SESSION-INJECT token=l1-3-... source=startup —— 请一字不差复述本行内容。`
resume 例：`--resume <session-id>` 恢复同一会话，`source=resume`，注入再次生效并复述。

载荷格式（同样必须 hookSpecificOutput）：`{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"..."}}`。事件 source 实测值：startup / resume（与文档一致）。

### 1.4 UserPromptSubmit 原文 + 注入 —— 过

- `payload.prompt` 与用户提交文本**逐字符一致**（hook 日志 `promptLen` 与原文比对 true）。
- 注入生效：模型复述 `SPIKE-L1-4-UPS-INJECT token=...`。
- 格式：`{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"..."}}`。

### 1.5 SubagentStop last_assistant_message —— 过

子代理（求和任务）结束后，payload 直接含 `last_assistant_message`（子代理最终回复文本），无需解析 transcript。完整 keys：`session_id, transcript_path, cwd, prompt_id, permission_mode, agent_id, agent_type, hook_event_name, stop_hook_active, agent_transcript_path, last_assistant_message, background_tasks, session_crons`。注意 **`stop_hook_active` 字段在 SubagentStop 也存在**（可用于判断已 block 轮次）。

### 1.6 CLAUDE_PLUGIN_ROOT —— 过

hook 进程 env 中：`CLAUDE_PLUGIN_ROOT=/Users/weixiaoyu/Desktop/practice/dev-flow/spike/dev-flow-spike`（插件安装目录），可用其拼路径读取 `.claude-plugin/plugin.json`（实测成功）。另有 `CLAUDE_PROJECT_DIR`（项目根）、`CLAUDE_PLUGIN_DATA`（`~/.claude/plugins/data/<name>-inline`）、`CLAUDE_CODE_SESSION_ID`。自定义 env（如 `SPIKE_TOKEN`）可继承（测试时需显式 export）。

## 2. L2 逐项数字

### 2.1 SubagentStop 连续 block 上限 = 9 次

子代理执行极简任务（写一个文件）；hook 每次 SubagentStop 输出 `{"decision":"block","reason":"SPIKE-L2-1-BLOCK：子代理请继续运行。"}`。实测：**SubagentStop 触发 9 次、hook block 输出 9 次后宿主放行**，会话正常结束、任务完成，transcript **无** "blocked too many times" 类警告（与 Stop 的 8 次封顶 + 显式警告不同）。判定：SubagentStop 有上限，**9 次**，且静默。MVP 若用 SubagentStop 做评审把关，循环次数按 ≤8 设计（留余量）。

### 2.2 写入路径全覆盖 —— 无致命盲区

实测矩阵（全部在 `spike/scratch/`，hook 全事件记录）：

| 写入方式 | 触发事件 | 结果 |
| --- | --- | --- |
| Bash `>` 重定向 | PreToolUse bash + PostToolUse bash | ✓ 覆盖 |
| Bash `>>` 追加 | 同上 | ✓ |
| Bash `tee` | 同上 | ✓ |
| Bash `sed -i` | 同上 | ✓ |
| Bash `cp`/`mv` 目的地 | 同上 | ✓ |
| 子代理内 Write（Agent 工具） | PreToolUse write + PostToolUse write，**带 agent_id/agent_type 字段** | ✓ 覆盖（子代理内工具事件照常触发） |
| NotebookEdit | PreToolUse notebookedit + PostToolUse notebookedit | ✓ 覆盖（工具可用，须先 Read） |
| `@` 引用读文件 | **无任何事件** | 读路径，非写入；文档已证实不触发 PreToolUse |

**致命问题判据（"是否存在写入文件系统而不触发任何 hook 事件的路径"）：未发现。** 全部测试写入路径都触发 PreToolUse/PostToolUse。已知残余缺口（设计明示，非 spike 新发现）：解释器任意写入（`python -c` 等）在事件层面触发 PreToolUse Bash，但语义上检不出写入目标——计划 §3.1/§8 已将其列为明示残余风险。

### 2.3 裸 node hook P50/P95

- **脚本内执行**（80 样本，5 会话 × 每会话 6 次 Write + 1 次 Bash + SessionStart/UPS）：SessionStart P95=3ms、UserPromptSubmit P95=1ms、PreToolUse P95=2ms、PostToolUse P95=2ms（含 mode 文件读取与事件日志写入）。
- **node 冷启动**（`node -e ''`，100 次）：P50=16.3ms、P95=18.4ms、max=32.1ms。
- **shell-form hook 全进程生命周期**（`sh -c 'node …'`，100 次，即本插件 hooks.json 的实际执行形态）：**P50=20.0ms、P95=26.4ms、max=49.7ms**。加真实脚本逻辑 ≈ **28ms 量级**。

**两级 hook 预案裁决**：瓶颈 100% 是 sh+node 进程冷启动（脚本内逻辑仅 2ms）。结论：**单级 node hook 即可满足"事件延迟不拖反馈环"**（模型回合内工具调用间隔数百 ms 起，28ms 无感）；两级 hook（bash 快筛）收益有限，非必需。若后续 P95 目标线定严（≤20ms）：优先用 **exec form**（`args` 直接 spawn node，跳过 sh，省 ~4ms）+ 精确 matcher；bash 快筛仅在"挂载面大、无关事件多"时才有意义。**第一批验收前 P95 目标线建议定为 ≤30ms（本数据支持）**，写入验收判据。

### 2.4 /reload-plugins 摩擦 + plugin validate

- **plugin validate**：`claude plugin validate spike/dev-flow-spike` → `Validating plugin manifest … Validation passed with warnings`，警告恰为 version/description/author 缺失（"只写 name"符合计划 §2.2）。
- **/reload-plugins**：本环境（Kimi provider 配置）`-p` 模式下返回 `isn't available in this environment`（与 `/login` 同受限）。
- **摩擦步数实测**：改 hook 代码 → **新会话即生效，0 步**（全部 L1/L2/L3 实验均验证：每次 `claude -p` 重新读取 hooks.json，无需任何 reload）。交互模式长期会话中，文档称 settings 文件改动通常被 watcher 自动捡起（"normally"），必要时 `/reload-plugins` 一步兜底。**结论：改码→真机验证的摩擦低于计划假设（0 步），无约束收紧需求。**

## 3. L3 端到端假流程 —— 过

流程与判据（MVP 计划 1.1 L3）：SessionStart 注入真实意图块规则 → 模型写被 deny 带理由 → **模型读懂理由并改正** → 用户说"好了"被 UserPromptSubmit 识别。

**对照 A（强制直接写，验证 fail-visible 真实性）**：prompt 要求"不要输出任何计划/意图块/解释文本，直接 Edit"。事件轨迹：

```
08:59:22 deny-intent-missing edit transcriptHasIntent=false   ← 首写被拦
08:59:45 allow-retry edit                                     ← 模型改正后重试放行
```

transcript 关键摘录（证据）：

```
TOOL_RESULT(deny理由): "SPIKE-L3-DENY：未检测到意图块。规则：第一次写入前必须先输出
意图块（做什么/动哪些文件/风险标签/verify 命令，以"#意图块"开头）。
模板：#意图块\n做什么：…\n文件：…\n风险：…\nverify：…"

ASSISTANT text（模型改正）: "#意图块
做什么：将 spike/scratch/l3-target.txt 中的 "hello world" 替换为 "hello dev-flow"。
文件：spike/scratch/l3-target.txt
风险：无
verify：文件内容为 "hello dev-flow" 即完成。"
```

**一次 deny 后模型按模板输出完整四要素意图块——fail-visible 的真实性实证，非 API 存在性。** 文件最终内容 `hello dev-flow` ✓。

**对照 B（正常任务 + 用户通道）**：

- 会话 1：模型正常执行任务，**主动输出意图块**（SessionStart 规则注入生效），`allow-intent-found edit transcriptHasIntent=true`（跨回合 transcript 检测命中，无需 deny）——规则常驻注入的引导作用实证。
- 会话 2（`--resume` 同一会话，prompt="好了"）：UserPromptSubmit hook 收到原文 `"好了"`，命中完成确认，注入 `SPIKE-L3-UPS-DONE … 请展示摘要并确认验收`；模型响应："本次改动已验收。改动摘要：文件 l3-target.txt，内容 hello world → hello dev-flow，验证：已读取确认…"——**用户通道完成确认闭环走通**。

**检测模式与注入文本重叠坑（L3 踩到，MVP 必防）**：SessionStart 注入的规则文本本身含"#意图块"字样，若检测直接搜全 transcript 该词则**永远命中（自注入污染）**。修正：检测限定在 **assistant 消息的 text 块**（`transcriptAssistantHas`），排除注入规则/deny 模板所在的 user 消息。MVP 意图块检测/审计必须同样限定来源，或用与规则文本可区分的标记。

## 4. 对 MVP 设计的影响（实现必须遵守）

1. **拦截/注入 JSON 一律 hookSpecificOutput 格式**（`hookEventName` + 事件字段）。顶层 `permissionDecision`/`additionalContext` 在 2.1.234 被静默忽略（unrecognized keys），deny 会 fail-open——**这是本 spike 最大的版本坑**。验收时用 `--debug-file` 核对无 `unrecognized keys` 日志。
2. **意图块检测**：主通道"一拦二放+审计"（首写 deny 给模板、重试放行记 `intent.blocked`）；transcript 检测仅作放行加分（限定 assistant text 块、跨回合才可靠）。不把拦截押在实时 transcript 上。
3. **hook 脚本进程**：仓库 `package.json` 是 `"type":"module"`，hook 脚本必须 `.cjs`（或 bundle 成单文件后改名）；输出 JSON 必须同步写（`fs.writeSync(1,…)`），`process.stdout.write` + `process.exit()` 会丢输出。
4. **P95 目标线建议 ≤30ms**（实测 shell-form 全进程 P95=26.4ms）；预算紧张时用 exec form（省 sh 冷启动）。
5. **SubagentStop 把关循环 ≤8 次**（实测 9 次封顶，静默）；payload 直接给 `last_assistant_message`，无需解析 transcript。
6. **执行顺序与 matcher**：SessionStart matcher 用 `startup|resume|clear|compact|fork` 正常（之前误判不触发，实为 hook 脚本崩溃）；`--allowedTools`/`--debug` 是变参 flag，位置参数 prompt 必须放其前。

## 5. 计划外坑清单（全部已解，MVP 直接规避）

| # | 坑 | 现象 | 解法 |
| --- | --- | --- | --- |
| 1 | 本机 claude 未登录 Anthropic；`/login` 不可用 | `claude -p` 报 Not logged in | 用 settings.json 中的 Kimi key 注入 `ANTHROPIC_AUTH_TOKEN` + `ANTHROPIC_BASE_URL` |
| 2 | **base_url 语义坑** | 官方 claude 的 base_url 由 SDK 追加 `/v1/messages`；settings.json 里 `…/coding/v1`（Kimi fork 语义）直连 404 | base_url 必须写 `https://api.kimi.com/coding`（模型名 `kimi-for-coding`） |
| 3 | `process.stdout.write` 异步 + `process.exit()` 丢输出 | hook 输出 JSON 丢失 → deny 静默失效 | `fs.writeSync(1, json)` 同步写 |
| 4 | `type:module` 仓库 + `.js` 脚本 | hook 用 `require` 崩（ESM scope） | 脚本全部 `.cjs` |
| 5 | `--allowedTools`/`--debug` 吞位置参数 | 报 "Input must be provided" | prompt 参数放在这些 flag 之前 |
| 6 | 顶层决策字段被忽略（见 1.1） | deny 不生效、注入不生效 | hookSpecificOutput 格式 |
| 7 | 模型把长随机 token 打码（`SPIKE-TRANSCRIPT-��`） | marker 检测测试前提失效 | 改用 `payload.tool_use_id` 客观法 |
| 8 | `/login`、`/reload-plugins` 在本环境不可用 | 报 "isn't available in this environment" | 新会话 0 步生效，不依赖 reload |

## 附录 A：认证配置（环境事实，MVP 验证环依赖）

本机 claude 是"Claude Code CLI + Kimi provider"形态：`~/.claude/settings.json` 配 `[providers."managed:kimi-code"]`（type=kimi、base_url、api_key），官方 claude 二进制不识别该 provider 段，需 env 注入。可复跑入口：

```bash
export ANTHROPIC_BASE_URL="https://api.kimi.com/coding"   # 坑：不能带 /v1
export ANTHROPIC_AUTH_TOKEN="$(awk -F'"' '/^api_key *=/{print $2; exit}' ~/.claude/settings.json)"
export ANTHROPIC_MODEL="kimi-for-coding"
claude -p "…" --plugin-dir spike/dev-flow-spike --allowedTools "…" --settings <空settings>
```

`--settings <空文件>` 用于隔离用户级 settings.json 里的全局 hook（`check-bash.mjs` 挂 PreToolUse Bash）与 permission rules，保证 spike 实验纯净。
