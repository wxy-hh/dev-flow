## P0-1 计划修订后 artifact sha 同步（真实缺陷）

**文件**：plugins/dev-flow/src/core/plan-revision.ts

现状：revisePlanDuringImplementation 预览时把 .md 的 sha 存入交互 basis（:113-117）；resolvePlanRevisionForAnswer 确认时在异步预备阶段已读出 currentArtifactSha256（:190）用于 PLAN_REVISION_STALE 检查，但 mutate 回调里 applyPlanRevision(draft, live, host)（:210）只删步骤、不写 draft.artifacts["implementation-plan"].sha256。随后 createReviewBatch 的 deriveReviewInput → assertArtifactCurrent 发现磁盘 sha ≠ state sha → ARTIFACT_INTEGRITY_FAILED（审计日志已记录该死胡同）。

**施工口径**：

1. 修改 `applyPlanRevision(draft, interaction, host, artifactSha256)` 签名；确认分支把 `currentArtifactSha256` 从预备阶段闭包传入，函数内写回 `draft.artifacts["implementation-plan"].sha256`（Q1=B）。
2. applyPlanRevision 的文档注释更新：确认修订即登记动作，必须同步 sha（防止未来分支再漏）。
3. revisePlanDuringImplementation 预览阶段不变（预览不落账）。

**测试**：tests/unit/v5-plan-revision.test.mjs 新增用例——修订确认后 state.artifacts["implementation-plan"].sha256 === 磁盘 .md 的 sha，且随后 createReviewBatch 不再抛 ARTIFACT_INTEGRITY_FAILED（可改写现有「修订后需重登记」类用例为「无需重登记」）。

## P0-2 代码审查隔离门禁被 reused 绕过（门禁漏洞）

**文件**：plugins/dev-flow/src/core/review-jobs.ts

现状（两处缺口）：

- reviewGate（:1622-1630）的 missingIsolation 只收集 status === "submitted" && !job.submission?.isolationProof 的 job；reused job 无 submission（policy/review-store.ts 校验 reused 必须无 submission），永不进隔离检查 → 全 reused 批次直接放行。
- createReviewBatch 的复用搜索（:530-536）只按 role + roleBasisHash + submitted 匹配，不校验源提交是否带隔离证明 → 同上下文审查的旧提交可被后续批次复用。

**施工口径**：

1. 新增 helper：reusedJobHasIsolationProof(ledger, job)——按 job.reusedFrom.batchId/jobId 定位源 batch/job，返回「源 job.status === "submitted" && Boolean(源 job.submission?.isolationProof)」。
2. reviewGate 隔离分支：missingIsolation 增加 status === "reused" && !reusedJobHasIsolationProof(...) 的 job；jobIds 语义不变（仍是需补隔离证明的 job）。
3. createReviewBatch：phase === "code" 且 controls.codeReview 为 independent/full 时，复用源必须满足 reusedJobHasIsolationProof；不满足则落为 pending 新 job（携带 carriedFindings），而不是 reused。
4. 错误文案（REVIEW_ISOLATION_REQUIRED 的 recoveryHint）补充「复用批次同样需要隔离证明；可在隔离子代理中重做 job 或经质量例外接受风险」。
5. （Q2=B）同 basis 下，若隔离必需且 current batch 缺有效 proof，幂等返回不得复用旧 batch；允许创建新 pending batch，旧 batch 转 stale。已提交 job 仍不可 release / 换 attestation（设计不变）。
6. （Q3=A）有效 quality-exception 继续跳过 isolation 检查，submitted / reused 均适用。

**测试**：tests/unit/v5-review-isolation-gate.test.mjs 新增：(a) 无隔离证明的 submitted 源在 code 相位不被复用（新 job 为 pending）；(b) 全 reused 且源无隔离证明 → gate 返回 isolation；(c) 源带隔离证明 → 复用后 gate 通过；(d) plan 相位行为不变。

**行为收紧提示**：修复后「同上下文审查 → reused 绕过」的路径关闭，L 级 code_review 必须真隔离或质量例外——正是 audit-log 遗留偏差 1 的目标状态；与 P1-4 配套后流程可顺畅走完。

## P0-3 code review role basis 绑定 feature-owned 内容指纹（交叉验证新增）

**文件**：plugins/dev-flow/src/core/review-jobs.ts、plugins/dev-flow/src/core/basis-state.ts

现状：`roleBasisHash`（review-jobs.ts）对 code-quality / requirement-fidelity 只 hash `role + route + level + artifacts + traceSlice`，不包含 governed 代码内容。因此修复 warning 后源码已变，旧 code review submission 仍被当作“语义未变”复用（audit-log 遗留偏差 1 的另一半根因）。

**施工口径**：

1. 在 review basis 中增加/复用 `featureOwnedFingerprint`（`fingerprintFeatureOwned`，只含 `workspace.ownership === "feature"` 的 governed 文件）。
2. `roleBasisHash` 对 code-quality / requirement-fidelity 把该指纹纳入最终 hash 输入。
3. plan-review 角色不纳入该指纹，避免实现阶段每次代码变更强制全量 plan review。
4. 旧批次在代码内容变化后自然不再命中复用。

**测试**：tests/unit/v5-review-isolation-gate.test.mjs 或 tests/unit/v5-review-changes.test.mjs 新增：修改任一 feature-owned governed 文件后，code role basis hash 变化；恢复原内容后 hash 恢复；plan 角色 hash 不变。

## P1-3 非 implementation 阶段 governed 写不被跟踪

**文件**：plugins/dev-flow/src/core/state-store.ts（recordTrustedWriteIntent :815、recordTrustedWriteOwnership :827）

现状：两个函数的 early-return 都含 currentOpenStep(state) !== "implementation"，因此 code_review / verification 阶段的 governed 写既不记 intent 也不把 ownership 置为 feature；observedPathFingerprints 又只在 reconcile 时刷新 → 改动要到下一次手动 reconcile_workspace 才被发现（审计日志流程记录）。

**施工口径**：

1. 两处 early-return 放宽为 state.mode !== "routed" || state.lifecycle !== "active"（去掉阶段限制）；函数体已按 governedRoots 过滤，非 governed 路径不受影响。approval / 单元越界等拦截语义仍在 write-gate.ts 负责，本处只管归属与指纹跟踪。
2. 效果：code_review 阶段的 governed 写立即把文件置为 feature 归属 → fingerprintFeatureOwned 变化 → 下一门禁（recordStep/checkpoint/verify/finalize 的 invalidateAffectedClaims、createReviewBatch 的 basis 校验）自动检出，无需手动 reconcile。
3. （Q5=A 必做）write-gate.ts evaluateFileWrite 对 routed 非 implementation 阶段的 governed 写返回 { decision: "allow", advisory: "governed-write-observed" }，让 agent 立即感知「该写会失效审查/验证」；adapter 已有 advisory 通道（hook-adapter.ts presets）。

**测试**：tests/unit/write-gate.test.mjs + tests/unit/v3-git-reconciliation.test.mjs：code_review 阶段 governed 写后 ownership=feature 且指纹变化；verification 阶段同；非 governed 写不记录。

**施工口径**：（Q20=A）只改投影/展示层。reused job 的 summary/投影不再把源 submission 的 warning 当「当前未解决」展示——源 job 所在批次转 stale 时，其 finding 在投影中标记 superseded（warning 不阻塞，但展示要准确）；ledger 保持不变；blocking 的 carried 语义不变。

**测试**：tests/unit/v3-review-carry-forward.test.mjs、tests/unit/v5-review-changes.test.mjs。

## 顺序与验证

| 序 | 条目 | 依赖 | 风险 |
| --- | --- | --- | --- |
| 1 | P0-1 计划修订 sha 同步 | 无 | 低，独立 |
| 2 | P0-2 隔离门禁修复 | 无 | 中高（行为收紧，需 P1-4 配套） |
| 3 | P0-3 code role basis 绑定 | P0-2 同批 | 中（使旧 code review 证据失效） |
| 4 | P1-3 governed 写跟踪 | 无 | 中（级联触发面变化） |
| 5 | P1-5 验证覆盖 | 无 | 中 |
| 6 | P1-4 宿主接缝 | P0-2 语义 | 高（跨宿主、skill、hook） |
| 7 | P2-6/7/8 诊断小改 | 无 | 低，可并行 |
| 8 | P2-9 决策入账 | 无 | 中（合同扩展，单独成批） |
| 9 | P3-10 陈旧 finding | 无 | 低 |

每条的验证习惯：先跑目标单测，再 npm run typecheck、npm run test:unit；P1-4 另跑 npm run test:interop；验证/审查相关改动另跑 npm run test:routes。**中间不跑 npm run build**；统一交付 bundle 时再 build + build:check。

## 不做的事

- 不改路线合同（contract.json）、不新增规模/风险判定。
- 不改「已提交 job 不可 release / 不可换 attestation 重交」的不可变性（REVIEW_JOB_ALREADY_SUBMITTED / REVIEW_SUBMISSION_CONFLICT 是设计）。
- 不新增 npm 依赖；不实现服务端采样之外的第三方审查源。
- 审计日志中的「流程学习」类条目（如 BOUNDARY_AUDIT_UNRESOLVED 的处置方式、evidence path 合同）只通过上述诊断改进降低试错成本，不改合同。
