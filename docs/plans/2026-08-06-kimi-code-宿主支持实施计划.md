# Dev Flow Kimi Code 宿主支持实施计划

> 状态：已实施(2026-08-06);剩 TUI 真机人工验收(见 §5 人工验收清单)
> 日期：2026-08-06
> 目标版本：Dev Flow 4.x(新增第三个受支持宿主 host = "kimi")
> 状态 schema：v3(不 bump;host 字段仅作成员校验扩展)
> 问题来源：将 Dev Flow 从双宿主(Claude Code / Codex CLI)扩展为支持 Kimi Code CLI
> 用途：交给其他模型按里程碑实施;新增宿主必须同步更新支持矩阵、manifest、hook 与分发合同测试

## 0. 决策记录与背景

### 0.1 为什么是 Kimi Code

Dev Flow 的 MCP server 是标准 MCP,任何 MCP 客户端都能连通并调用 `dev_flow_*` 工具,但完整工作流保障依赖宿主 hooks(写守卫、可信用户事件、授权记账)与插件分发。Kimi Code CLI 官方文档证明其具备所需机制,不属于 README 中"无 hook 批准旁路"的第三方 MCP 客户端情形:

- Hooks:19 个事件,可阻断 `PreToolUse` / `UserPromptSubmit` / `Stop`;观察型含 `PostToolUse` / `PermissionRequest` / `PermissionResult` / `SessionStart` / `SessionEnd` 等。
- 阻断方式:stdout JSON `{"hookSpecificOutput":{"permissionDecision":"deny","permissionDecisionReason":...}}`,或退出码 2 + stderr 原因。
- 内置工具:Read / Write / Edit / Bash / Grep / Glob 等;写入与执行类默认需审批。
- 权限模型:未命中规则的调用弹审批,支持会话级 "Approve for this session" 放行;`config.toml` 可预置 `[[permission.rules]]`;`PermissionRequest` / `PermissionResult` 为观察型事件(hooks 不能代做审批决定);YOLO 模式自动批准全部调用。
- MCP:标准 stdio / HTTP / SSE;工具命名 `mcp__<server>__<tool>`;配置在 `mcp.json`(用户级 `~/.kimi-code/mcp.json` / 项目级 `.kimi-code/mcp.json`),plugin 可在 manifest 声明 `mcpServers`。
- 分发:manifest 为 `kimi.plugin.json` 或 `.kimi-plugin/plugin.json`(必须位于 plugin root);支持本地路径 / zip / GitHub URL 安装;hooks 工作目录为 plugin root;目前仅用户级安装,无项目级 scope。
- Skills:SKILL.md 格式兼容;`sessionStart.skill` 可自动注入一个 skill;`commands` 可注册 `/dev-flow:<名>` 斜杠命令。

### 0.2 对既有决策的推翻

本计划正式推翻 `docs/plans/3.0执行计划.md` 的两条红线:

- "持久化 state 的 host 仍只接受 `"claude"|"codex"`,不新增第三方枚举"。
- "不为第三方 MCP 客户端(OpenCode 等)增加无 hook 批准旁路、不宣称其受支持"。

前提已变:Kimi Code 有完整 hooks + plugin 分发,不属于"无 hook 批准旁路"情形,故新增 `host = "kimi"` 与新增 codex 宿主同类。

### 0.3 逐题拷问后的边界确认(Q1–Q6)

1. **Q1 正式新增 `host = "kimi"`**:是。不再停留在"可直连诊断"。
2. **Q2 授权账本策略**:观察记账,不自动放行。Kimi 的 `PermissionRequest`/`PermissionResult` 是观察型事件,hooks 无法代宿主做审批决定,故 Claude 上"查账本→返回 allow 自动放行"机制在 Kimi 上物理不可用;task-reusable 复用交给 Kimi 原生 session 级审批与用户预置 `[[permission.rules]]`;adapter 只把 `PermissionRequest`/`PermissionResult` 与成功的 `PostToolUse` 写入 feature 授权账本(审计用),永不输出 allow 决定。
3. **Q3 分发形态**:仓库内双 manifest,无独立发布物。`plugins/dev-flow/.kimi-plugin/plugin.json`(短路径,本地目录安装)+ 仓库根 `.kimi-plugin/plugin.json`(薄包装,`./plugins/dev-flow/...` 相对路径,GitHub URL 安装)。构建/发布管线零新增,仅 `dist/kimi-hook.mjs` 随构建产出。前置 spike 验证 MCP stdio 相对路径解析,失败则回退为"文档注明 GitHub 安装需本地 clone 后 `/plugins install` 本地路径"。
4. **Q4 支持矩阵定位**:「支持(实验性/Beta)」,写明降级清单与转正条件;doctor 增加 kimi manifest/hook/bundle 接线检查。
5. **Q5 真机验证范围**:三层验证——① `kimi-hook.mjs` invokeHook 载荷单测;② 隔离 `$KIMI_CODE_HOME`(hooks/`mcp.json`/`[[permission.rules]]`)下 `kimi -p` 跑通一条真实路线断言 `.dev-flow/` 产物;③ `/plugins install` TUI 流程与 `PermissionRequest`/`PermissionResult` payload 实录为发布前人工验收清单。`kimi -p` 模式下 hooks 是否触发作为前置 spike,若不触发则②退化为 invokeHook + 人工复核。
6. **Q6 入口**:`sessionStart.skill` 指向一个引导 skill(新建 `kimi-session`),不配置 `commands` 斜杠命令;用户侧仅需一次性 `/plugins install` + 信任确认,以及建议(非强制)预置 `[[permission.rules]]` allow `mcp__dev-flow__*`。

其余默认决策:host 字符串取 `"kimi"`;schema v3 不 bump,host 字段运行时校验仅两处枚举(详见 Phase 1)需扩展。

### 0.4 权限边界的诚实承诺

Kimi 的 `PermissionRequest`/`PermissionResult` 为观察型事件,hooks 返回值与主流程无关;**不存在**可以"静默放行"的 hook 通道。文档不得宣称 Kimi 侧支持 feature-level 授权记忆(Claude/Codex 的自动放行也只在"宿主确认被 hook 代决"时生效;Q2 确认在 Kimi 上不做)。真实打断频率以 `mcp__dev-flow__*` 权限规则预置与否为界:预置后 MCP 与内置 Bash/Write/Edit 借助 "Approve this session" 几乎无弹窗;未预置则每次 MCP 调用需审批——此行为必须写进安装文档。

## 1. 施工红线(继承 4.0)

1. 智能体不得执行 git commit / push / 创建 PR / 发布;提交由用户审核后手动完成并保持仓库 AGENTS.md 约束。
2. 不得手工编辑 `.dev-flow` 控制文件、snapshot、projection 或 active pointer。
3. 不得为提升第三方宿主通过率而降级 fail-closed 门禁;缺少可信 host-event 时保持拒绝,不得伪造用户证据。
4. 不得新增"无 hook 批准旁路";Kimi 侧 hooks 仅做记录与写守卫,不做授权决定。
5. 未经正式批准不得修改 protected 业务文件;中间阶段不运行 `npm run build`(只最终 bundle 收尾)。
6. host 泛化只扩展联合类型,不改变 schema v3 语义,不新增迁移路径。

## 2. 功能范围(已完成确认)

- **支持能力**:新增 Kimi Code CLI 为第三个宿主;host 值 `"kimi"`。
- **接入方式**:`.kimi-plugin/plugin.json`(仓库内 + 仓库根双 manifest);hooks(PreToolUse 写守卫 / UserPromptSubmit / PostToolUse / Stop / PermissionRequest / PermissionResult 记账);MCP server 不变(标准 stdio,插件 root 解析基于 `import.meta.url`,宿主无关)。
- **权限与审计**:写守卫通过 PreToolUse 阻断(Kimi 识别 stdout JSON `permissionDecision:"deny"` 或退出码 2);授权账本观察记账、不自动放行;task-reusable 复用由 Kimi 原生 session 审批承接。
- **入口**:`sessionStart.skill` 注入引导 skill `kimi-session`(极短文案:无 active 先 `dev_flow_start`,有 active 先 `dev_flow_status`);不配置 commands。
- **文档**:README 支持矩阵第三行改为「Kimi Code | 支持(实验性)」;安装节新增 Kimi 段落(安装/信任/权限规则建议);宿主基线加 Kimi Code 0.33.0(实验性)。

#### Spike 结论(2026-08-06,隔离 `$KIMI_CODE_HOME` 真机实录)

1. **`kimi -p` 触发 hooks**:SessionStart → UserPromptSubmit → PreToolUse → PostToolUse → Stop。**spike-1 风险排除**,层②验证可行。
2. **写守卫生效**:PreToolUse stdout JSON `{"hookSpecificOutput":{"permissionDecision":"deny","permissionDecisionReason":...}}` + exit 0 成功阻断 Write(模型见拒绝原因,目标文件未创建)。退出码 2 通道未实测,保留为回退。
3. **Payload 全 snake_case**。关键字段:`tool_name`、`tool_input`(object)、`tool_call_id`、`tool_output`(成功时);`UserPromptSubmit.prompt` 是**数组** `[{type:"text",text}]` 而非字符串;kimi adapter 必须从中提取文本;`Stop` 含 `stop_hook_active`;`SessionStart` 含 `source:"startup"|"resume"`。
4. **PermissionRequest / PermissionResult 在 `-p` 模式永不触发**(写工具被直接放行,即使 `[[permission.rules]]` 的 `decision="ask"` 也只对交互会话生效)。二者仅在交互 TUI 触发 → 观察记账路径只在交互会话产出记录;`-p` 模式无 pending/result 记录。真实 payload 实录列入人工验收清单。
5. **PostToolUse 仅成功时触发**;被 PreToolUse 阻断的工具走 PostToolUseFailure(不记成功)。
6. **MCP stdio**:绝对路径连通成功(工具被调用);用户级 `mcp.json` 的 `./` 相对路径**不解析**(server 被静默忽略)。插件级 `./` 解析到 plugin root 为文档承诺、无法 headless 验证,列入安装验收。→ Q7 方案保留(`command:"node"` + `./` 相对 args),但 README 必须注明 GitHub 安装回退(本地 clone 后 `/plugins install <本地路径>`)。
7. 本地安装运行 `$KIMI_CODE_HOME/plugins/managed/<id>/` 副本;e2e 每次 build 后需重装才生效。
