## 工作流 1 — 第 4 条：启动失败状态可见性

日常入口仍是 `dev_flow_status`（已投影路线 / 下一步 / 待决问题）。Doctor 只附带一份可判定摘要，避免模型把健康检查当成工作流状态机。

### 1a. doctor 输出状态投影

**文件**：`plugins/dev-flow/src/mcp/doctor.ts`

在 activeFeature 可读分支（`traceState` 已赋值处，约 :104-112）扩展返回的 `activeFeature` 对象，新增可判定字段（加法式，不改既有字段）：

- `mode`：`state.mode`（intake / routed）
- `stage`：routed 时的 `state.currentStage`
- `pendingDecision`：`pendingDecisionForState(state)` 存在时给 `{ kind, question }`
- `nextStep`：轻量派生（**不调** `nextAction`）——有 pending → `回答待决问题：<question>`；intake → `完成调查后调用 dev_flow_lock_classification`；routed → `继续 <stage>（详情看 dev_flow_status）`；其余 → `查看 dev_flow_status`

`pendingDecisionForState` 对旧版 grill 会抛 `GRILL_INTERACTION_RESTART_REQUIRED`。必须 try/catch：失败时不写 `pendingDecision`，`nextStep` 改为「待决问题不可读，查看 `dev_flow_status`」，doctor 整份报告不得因此失败。

同时加一条诊断 `ACTIVE_FEATURE_STATE`，**status 始终为 `ok`**（pending 是正常工作流，不是健康故障）。message 陈述 mode / 是否有待决 / nextStep。文案点明：日常看 `dev_flow_status`，doctor 只是附带投影。不要用 warning——warning 会诱使模型走 recover / 重建，正是本条要消掉的行为。

**测试**：unit——(a) intake 且有 pending → 返回含 mode / pendingDecision / nextStep，诊断为 ok；(b) 旧版 grill pending 抛错时 doctor 仍成功，不带 pendingDecision。

### 1b. task-switch 恢复指令修正

**文件**：`plugins/dev-flow/src/core/state-store.ts`（`startFeature` :903-934）

当前缺陷：旧 feature 已有 pending decision 时，跳过 task-switch 交互创建却仍抛 `TASK_SWITCH_REQUIRED`，`recoveryInstruction`「请通过 dev_flow_answer 逐题选择处理旧任务的方式」指向不存在的 task-switch 题。

修法：throw 前记录是否新建了 task-switch 交互；读取当前 pending（同样 try/catch，避免旧 grill 把 start 打成别的错误码）。据此分支：

- 已创建 task-switch 交互（无旧 pending）→ 维持「逐题选择处理旧任务的方式」；
- 未创建（有旧 pending）→ `recoveryInstruction: "旧任务有待决问题未解决。先调用 dev_flow_answer 回答该问题，再重试开始新任务。"`，`cause` 同步说明。

错误详情**必须带上**当前 pending 的 `{ kind, question }`（读得到时），让模型不必再绕一次 doctor。

**测试**：unit——两条分支的 `recoveryInstruction` / `cause` 文案；有旧 pending 时 details 含 `kind` + `question`。

## 工作流 2 — 第 5 条：同一批准确认次数收敛

### 2a. recordDecision 整句级自动追认

**文件**：`plugins/dev-flow/src/core/decision-workflow.ts`、`plugins/dev-flow/src/mcp/server.ts`

在 `recordDecision`（:27）创建 ratification 交互**之前**，尝试自动追认。先抽出「只写 credential + decision」的 helper（现有 `ratifyDecision` 依赖 `interaction.id` 生成 `CRED-ratify-...`，自动路径不要为了复用去造幽灵交互）。自动路径的 credential id 用稳定前缀，例如 `CRED-auto-ratify-<decisionId>`。

自动追认**同时**满足以下条件才走，任一不满足则维持现状创建 ratification 交互：

1. 当前 feature **没有** pending interaction（`pendingDecisionForState` 为空）。已有 route-confirmation / grill / ownership 等待决时禁止自动追认，避免把用户答句抢走后待决题绑不上。
2. 读 `readFeatureEvents`；取 `promptFrom` 中 host 匹配、未消费（`consumedPromptEventIds`）的 user-prompt 事件，按 revision 降序，取**最新**一条。
3. 整句级匹配：`normalizeReplyText(event.text) === normalizeReplyText(evidence)`（精确归一相等，复用 `text-normalization.ts`）。**不用** `textCompatible`。
4. 只匹配 evidence，不匹配 conclusion。这是已接受风险：用户原话被解释成更宽的 conclusion 时不会再问一次。返回面必须回显 `question` / `evidence` / `conclusion`，让模型和用户能看见登记了什么。

命中后：

- 一次 `mutate` 落账（credential + decision），`basis = { kind: "event", eventId }`；
- mutate 的 event data **必须**带 `promptEventId`——`consumedPromptEventIds` 只认这个字段，不认 `eventId`，否则同一句还能被下一轮再消费；
- 不创建交互。

未命中（有 pending、最新消息不匹配、无未消费事件、片段 / 改写）→ 维持现状创建 ratification 交互。

**返回面**：`DecisionRatificationResult.interaction` / `interactionId` 改为可选。`dev_flow_record_decision` 派发处（`server.ts:1143-1151`）按 `interaction` 是否存在分支：

- 无交互：不要 `emitAttentionNotification`，不要 `elicit`。返回 `{ state, decisionId, ratifiedFrom: eventId, question, evidence, conclusion }`（内容视图：「已依据你最近的回答自动登记」）。
- 有交互：保持现有 elicit / envelope 路径。

既有调用方（`state-store` 再导出、`tests/unit/v5-decision-ratification.test.mjs` 等）凡假定 `presented.interaction` 必有的，按「无匹配 prompt → 仍建交互」保持绿；新增自动路径单测。

**测试**：unit——

- (a) 无 pending，evidence 整句等于最新未消费消息 → 无交互、落账、credential basis=event、后续 `consumedPromptEventIds` 含该事件；
- (b) 片段 / 前缀 → 仍建交互；
- (c) evidence 匹配较旧消息、最新不匹配 → 仍建交互；
- (d) 无未消费事件 → 仍建交互；
- (e) 已有 pending（任意 kind）即使 evidence 整句命中 → 仍建交互或因 `MULTIPLE_PENDING_DECISIONS` 失败，**不得**消费该 prompt。

### 2b. Skill 硬化

**文件**：`plugins/dev-flow/skills/task/SKILL.md`、`plugins/dev-flow/skills/grillme/SKILL.md`

- task SKILL 锁定流程（约 :10-12）追加：**「classify 预览（`dev_flow_classify` 输出）是给模型的分类依据，不向用户讨确认；路线确认只由 lock 后 route-confirmation gate 承担一次。」**
- task / grillme SKILL 的待决回答段追加：**「待决问题只能由用户真实回复解析，模型不得用转述自答；失败时只呈现一次问题并等待新用户消息。」**
- **必须改掉** grillme SKILL 第 8 行「不会仅凭历史消息中的相同文字自动落账」。改为与 2a 一致：仅当最新未消费用户消息与 evidence 整句归一相等、且当前无待决问题时，Core 自动登记；否则仍先展示原话与拟登记结论，经用户确认后落账。

### 3c. lock 失败诊断

**文件**：`plugins/dev-flow/src/core/route-workflow.ts`（源码 :46 / :59 / :65，**不是** dist `:4666`）、`plugins/dev-flow/src/policy/route.ts`（`assertBoundaryAuditComplete` :407，同一错误码）

## 工作流 4 — 第 1 条：归属零提问自动纳入

语义（与定案正文一致，标题「自动纳入」不要理解成启动时全收）：

- 启动不弹归属问题；
- 预存脏文件默认排除，不阻塞关键门禁；
- 任务在 implementation 写入时 `trusted-hook` 静默纳入（含启动前改动，这是已接受风险）；
- finalize 对「预存脏 + 任务写过」给一行非阻塞提示；
- 未触碰的预存脏文件被 `git add`/`commit` 时**提示不拦**。

`recordTrustedWriteOwnership` 只在 `mode=routed && currentStage=implementation` 生效；intake 本身不能写 governed 文件，与现有写门禁对齐，不必改 hook 写路径。

### 4a. 合同 + 启动零提问 + 预存脏文件默认排除

**文件**：

- `plugins/dev-flow/src/policy/types.ts`（`WorkspaceLineage.ownershipSource`，:88）
- `plugins/dev-flow/policy/state.schema.json`（`ownershipSource.additionalProperties.enum`，:41）
- `plugins/dev-flow/src/core/git-reconciliation.ts`（`ownershipForScope`，:222）
- `plugins/dev-flow/src/core/state-store.ts`（`startFeature` :959-965）

`ownershipSource` 已枚举死为 `"user-adopted" | "trusted-hook"`。新增 `"startup-excluded"` 是本合同步骤，不是实现时再看的脚注。`validateFeatureState` 目前不校验该枚举，但 schema 测试会。types 与 `state.schema.json` 必须同步；无需 bump `schemaVersion`（加法枚举）。

`ownershipForScope`（仅 `startFeature` 调用，改它不会在 reconcile 时打回已有 `trusted-hook`）：

- 已有 ownership 的路径不覆盖；
- `outOfScope` 命中 → `excluded`（可保持不写 source，或沿用现状）；
- 其余全部 `startedDirty` 路径 → `ownership="excluded"`、`ownershipSource="startup-excluded"`。

startFeature 删除启动的 `presentWorkspaceOwnership` 呈现块（:962-965），不再创建启动归属交互；`unownedPaths` 因默认排除而为空。任务期间新出现的未知路径仍由 `reconcileWorkspace` → `queueNextOwnershipDecision` 提问，行为不变。

### 4b. 门禁与交付推导对齐

**文件**：`plugins/dev-flow/src/core/state-store.ts`（`assertWorkspaceOwnershipComplete`，:733）、`plugins/dev-flow/src/core/delivery-snapshot.ts`（`deriveImplementationFiles`，:104）

- 两者**不改逻辑**：默认排除后未触碰预存脏文件不再是 unowned/unknown；门禁只拦截**任务期间新出现**的未知路径（新文件、用户新增）；
- 任务写入预存脏文件 → `recordTrustedWriteOwnership`（:806）覆盖 excluded→feature（source `trusted-hook`），无需改动；
- **回归确认**：`DELIVERY_FILE_PREEXISTING_DIRTY`（:279-291）只过滤 `featureOwned`，排除文件不触发——无需收窄。

### 4c. finalize 非阻塞透明提示

**文件**：`plugins/dev-flow/src/core/delivery-snapshot.ts`（`createDeliverySnapshot` manifest 渲染段，约 :316-345）

新增一行非阻塞提示：对 `initialDirty.has(file) && ownershipSource[file] === "trusted-hook"` 的交付文件，在交付清单「归属记录」段输出 `包含启动前已存在改动的文件：<files>`（与 `excludedChangedPaths` 同样式，只提示不拦截）。不加进 patch、不阻塞 finalize。

已接受风险：任务写过的预存脏文件，启动前改动会静默进入交付，只靠这一行提示。用户明确放弃了「写入时懒提问」。

### 4d. git 门禁：预存脏 + 默认排除 → 提示不拦

**文件**：`plugins/dev-flow/src/hosts/adapter-policy.ts`（`gitPathPolicy`，:728-748；`DEV_FLOW_GIT_GUARD` 组装处 :939-964）

定案是「提示不拦」，不是「保持拦截再加一行」。现状 `gitPathPolicy` 对所有 `ownership==="excluded"` 直接 `createPreToolBlock`。启动默认排除后，若不收窄，摩擦只会从开场问归属挪到提交。

收窄规则：

- `excluded ∩ startedDirty`（启动默认排除、任务未写入）→ **不拦截**，在允许通过的返回面上附 advisory / 提示行：「该路径启动前已有改动、已默认排除出交付；本次 Git 操作未拦截，但这些文件不会进入交付快照。如需计入请先在工作区对账纳入。」
- 其它 `excluded`（用户显式排除、非 `startedDirty`）以及未知路径 → **维持拦截**。
- `git add -A` / `git add .` 等 `unsafePathForm` 本就整单拦截，不在本条放开。

`startedDirty` 用 `workflow.state.workspace.startedDirty` 判定。trusted-hook 纳入后 ownership 已是 `feature`，走正常 feature-owned 路径，不必特殊处理。

## 跨条目验证

每条完成后按仓库习惯：

1. 新增 / 更新聚焦 `*.test.mjs`；
2. 先跑目标单测 → `npm run typecheck` → `npm run test:unit`；
3. 受影响 routes / interop（第 1 条跑 `npm run test:routes`，确认脏工作区路线全绿）；
4. 仅交付 bundle 时 `npm run build` + `npm run build:check`；
5. 不改 `policy/contract.json`（不涉及路线合同）。第 1 条只加法扩展 `ownershipSource` 枚举（types + `state.schema.json`），见 4a。

## 不做（明确排除）

- 第 2 条独立机制；第 3 条 Core 改动；第 7 条 CLAUDE.md 混写修正；
- 批量工具之外的「幂等不推进 revision」特例（单条路径语义不动）；
- 预览确认与 lock 共享呈现事件的「共享确认」方案（选了更简单的预览不讨确认）；
- 自动追认再匹配 conclusion（已接受「只匹配 evidence」的解释风险，靠返回面回显）；
- 写入预存脏文件时再弹一次确认（用户明确放弃懒提问，只留 finalize 提示）。
