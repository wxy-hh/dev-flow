## 1. 最终目标

在启用 Dev Flow 后，模型原本可以正常执行的命令不应因为命令写法、解释器、管道、heredoc、重定向组合或日志位置不同而被 Dev Flow 的 Bash 分析器独立判定为非法。

完成后必须满足：

1. 合法的 intake 状态不再被误报为 `DEV_FLOW_WORKFLOW_STATE_UNREADABLE`。
2. `DEV_FLOW_WRITE_TARGET_UNRESOLVED` 不再作为流程中断错误；“无法静态解析”只表示分析器不知道，不表示命令违法。
3. Dev Flow 保留自己的工作流门禁：已确定目标位于 protected roots、`.dev-flow` 控制区或 Git 写入受限阶段时，仍按现有工作流合同处理。
4. Dev Flow 不再建立一套与 Claude/Codex 权限系统竞争的 Bash 安全边界。系统级危险操作交给宿主原生 sandbox、permissions 和 `PermissionRequest`。
5. 所有确实中断原操作的 Dev Flow 结果都必须说明具体原因、影响、可执行解决方案，以及解决后是否自动重试原操作。
6. 不改变用户意图且可逆的修复优先自动完成；需要用户决定的修复只询问一次，确认后由模型继续解决并自动重试原操作。
7. 普通风险权限按当前 active feature 记忆；发布、部署、生产变更等重大外部动作不复用 Dev Flow 授权，每次仍走宿主确认。
8. Claude 与 Codex 使用各自当前支持的 Hook 输出协议，不输出宿主已明确不支持的字段。

## 2. 已确认的产品原则

实施模型不得重新选择以下方向。

### 2.1 判断目标和结果，不规定模型必须使用哪种命令写法

不同模型可能使用 `Edit`、`apply_patch`、`printf`、`tee`、Node/Python 脚本、shell wrapper 或 heredoc。Dev Flow 可以在能够可靠识别目标时执行工作流判断，但不得把“解析器未覆盖这种写法”等同于“命令不合法”。

### 2.2 Dev Flow 不是第二套操作系统权限系统

Dev Flow 只负责：

- 工作流控制状态不可被普通文件工具直接修改。
- 已确定的 protected-root 写入遵守 intake、实施批准和 RU/checkpoint 合同。
- logic-complete 之前遵守既有 Git 写入门禁。

文件删除、Git 历史改写、网络发布、部署等通用风险继续由 Claude Code/Codex 自己的权限机制处理。这样保证“启用 Dev Flow 前宿主怎么控制危险操作，启用后仍然怎么控制”，不会因为插件再增加一层脆弱的 Bash 语法判断而改变模型能力。

### 2.3 分析不确定时默认不由 Dev Flow 中断

以下情况不得再返回 `DEV_FLOW_WRITE_TARGET_UNRESOLVED`：

- `bash -c`、`zsh -c` 等 shell wrapper。
- Node、Python、Ruby 等解释器命令。
- `xargs`、复杂管道、heredoc 或分析器未覆盖的重定向组合。
- 验证日志写入 `/tmp` 或其他仓库外路径。
- 目标包含分析器无法静态求值的变量或展开。

默认静默放行，只在内部分析或调试日志中记录 unresolved 原因；不要给用户或模型持续注入无行动价值的警告。

### 2.4 已可靠解析出的目标仍执行工作流合同

“解析不确定放行”不等于取消工作流：

- 明确写入 `.dev-flow` 控制文件：继续拒绝并引导改用 MCP/Core。
- 明确写入 active feature 已登记的 Markdown 资产：按现有规则允许。
- 明确写入未登记资产：引导先 scaffold/register。
- 明确写入 protected roots：继续执行 intake、批准、实现单元判断。
- Git 写命令：继续保留 logic-complete 门禁。

本任务不承诺对任意 shell 程序做完整副作用证明。若未来需要“任何解释器都绝不可能绕过 protected-root 门禁”的强保证，必须使用操作系统 sandbox、受控文件系统代理或执行后事务回滚，另立设计任务，不能继续扩张正则表达式解析器。

### 2.5 自动解决和用户确认的边界

无需询问、可自动处理：

- 刷新 active/state 并重试一次。
- 运行只读 doctor。
- 已批准实现阶段自动开始第一个 RU。
- 清理插件自身的临时缓存或重新加载只读配置。

必须询问用户：

- 确认需求、计划或实现批准等用户所有的工作流决定。
- doctor 判断必须执行 recover、重建或放弃 feature。
- 解决方案会改变用户目标、范围或批准依据。
- 宿主判定需要确认的重大外部动作。

用户确认后，模型应直接执行解决步骤并重试原始操作，不要求用户再回复一次“继续”。

## 3. 已定位根因

### 3.1 intake 合法状态触发运行时异常

`plugins/dev-flow/src/hosts/adapter-policy.ts` 中的 `prepareImplementationWrite` 在判断目标是否位于 protected roots 之前调用：

```ts
currentOpenStep(workflow.state)
```

合法 intake 状态没有 `route`。`plugins/dev-flow/src/core/step-order.ts` 的 `currentOpenStep` 直接把 `state.route` 传给 `routeDefinitionForFeature`，随后读取不存在定义的 `orderedSteps`，实际异常为：

```text
TypeError: Cannot read properties of undefined (reading 'orderedSteps')
```

两个宿主 adapter 又用宽泛 `catch` 把任何策略异常都改写成 `DEV_FLOW_WORKFLOW_STATE_UNREADABLE`，因此用户得到错误的 doctor/recover 建议。

### 3.2 Bash 分析器把能力边界当成合规边界

`analyzeBashWriteTargets` 正确表达了三种事实：只读、已解析目标、未解析语法。但 `preToolBlock` 把 `unresolved` 直接映射成 `DEV_FLOW_WRITE_TARGET_UNRESOLVED`，导致所有分析器不认识的合法写法被拒绝。

此外，已解析出的仓库外绝对路径经过 `projectRelative` 后得到 `undefined`，`classifyTarget` 仍把它映射为相同错误，所以 `tee /tmp/xxx.log` 也会被 Dev Flow 拦截。

### 3.3 宿主 adapter 掩盖内部错误且输出协议过时

当前 adapter 对所有异常采用相同的“状态不可读”兜底，无法区分：

- active/state 确实损坏。
- 策略代码存在 bug。
- 分析器无法识别命令。
- 临时 I/O 或实现单元准备失败。

当前 Codex `PreToolUse` 允许路径输出 `{ "continue": true }`。Codex 当前文档明确说明，`PreToolUse` 不支持 `continue`；允许时应退出 0 且不输出决策。Codex 当前也不支持 `permissionDecision: "ask"`，不得为了实现确认弹窗而伪造该输出。

Claude Code 当前支持 `PreToolUse` 的 `allow`、`deny`、`ask` 和 `defer`，但旧的顶层 `decision` 已弃用。两个宿主必须分别序列化，不能假定完全相同。

### 3.4 测试覆盖缺口

`tests/unit/v2-adapter-overlay.test.mjs` 现有用例先执行 `lockClassification`，没有覆盖 start 后仍处于 intake 的 Hook 调用，因此没有捕获上述异常。当前测试也没有把记录中的复杂 Bash 命令作为回归 fixture。

## 4. 目标行为模型

### 4.1 PreToolUse 结果类型

把策略层从“只有 block 或 undefined”调整为显式结果，但保持兼容包装函数：

```ts
type PreToolOutcome =
  | { kind: "allow"; advisory?: PreToolAdvisory }
  | { kind: "block"; block: PreToolBlock };

interface PreToolAdvisory {
  code: "DEV_FLOW_HOOK_EVALUATION_FAILED";
  message: string;
}

interface PreToolBlock {
  code: PreToolBlockCode;
  reason: string;
  impact: string;
  recovery: {
    mode: "automatic" | "guided" | "user-decision";
    action: string;
    retryOriginal: boolean;
  };
}
```

兼容要求：

- 保留 `preToolBlock` 和 `preToolBlockReason`，供已有调用方和测试使用。
- 新 adapter 使用 `evaluatePreToolUse`，不要靠异常或字符串反解析决定宿主输出。
- `DEV_FLOW_WRITE_TARGET_UNRESOLVED` 从 `PreToolBlockCode` 移出；unresolved 仅是分析器内部结果，不再成为宿主输出错误码。

### 4.2 宿主输出矩阵

| 场景 | Claude Code | Codex |
| --- | --- | --- |
| 允许且无提示 | 退出 0，无 stdout | 退出 0，无 stdout |
| 允许但有分析提示 | `hookSpecificOutput.additionalContext` | `hookSpecificOutput.additionalContext` |
| Dev Flow 硬门禁 | `hookSpecificOutput.permissionDecision = "deny"` | `{ "decision": "block", "reason": "..." }` |
| 宿主需要权限确认 | 不由 Dev Flow PreToolUse 强制；进入原生权限流 | 不由 Dev Flow PreToolUse 强制；进入原生权限流 |
| 普通风险已有 feature 授权 | PermissionRequest 返回 allow | PermissionRequest 返回 allow |
| 重大外部动作 | PermissionRequest 不代决，继续显示原生确认 | PermissionRequest 不代决，继续显示原生确认 |

禁止输出：

- Codex `PreToolUse` 的 `continue`、`stopReason` 或 `permissionDecision: "ask"`。
- Claude `PreToolUse` 已弃用的顶层 approve/block 形状。
- 允许路径上的假 JSON；退出 0 且无输出才是最稳定的“无意见”。

### 4.3 中断消息格式

所有 block 必须稳定包含：

```text
<ERROR_CODE>
原因：<为什么这次操作不能继续，必须是当前事实>
影响：<原操作是否执行、影响哪些目标>
解决方案：<模型下一步可以执行的具体 MCP/doctor/工作流动作>
确认：<是否需要用户决定；如果需要，模型应怎样询问>
继续方式：解决后自动重试原操作，无需用户再次回复“继续”
```

不得再出现只有“请拆分命令”“请使用 MCP 工具”“运行 doctor”但没有原因和下一步动作的提示。

### 4.4 错误码处理表

| 错误码 | 原因与处理要求 |
| --- | --- |
| `DEV_FLOW_GIT_GUARD` | 明确说明尚未 logic-complete；给出 verify、feature-check、finalize 的下一实际动作；完成后自动重试 Git 操作。 |
| `DEV_FLOW_IMPLEMENTATION_APPROVAL_REQUIRED` | 明确当前 open step 或未满足的 approval obligation；向用户展示现有批准问题，用户确认后继续并重试。 |
| `DEV_FLOW_IMPLEMENTATION_UNIT_REQUIRED` | 先自动调用 begin implementation unit；成功后直接重试，不额外询问。 |
| `DEV_FLOW_IMPLEMENTATION_UNIT_OUT_OF_SCOPE` | 刷新 Trace；能自动修复失效引用则自动修复，否则展示差异并询问用户。 |
| `DEV_FLOW_STATE_MUTATION_FORBIDDEN` | 说明目标是 Core 控制文件；询问是否改用对应 MCP 完成相同意图，确认后自动执行并重试必要步骤。 |
| `DEV_FLOW_ARTIFACT_NOT_REGISTERED` | 指出资产种类和路径；提供 scaffold/register 动作，而不是笼统说“使用 MCP”。 |
| `DEV_FLOW_WORKFLOW_STATE_UNREADABLE` | 只在读取证据确实表明 active/state/project/recovery 数据不可读时使用；先自动刷新和只读 doctor，只有 doctor 证明需要 recover 时才询问用户。 |
| `DEV_FLOW_WRITE_TARGET_UNRESOLVED` | 不再作为外部错误码；只保留内部 analysis kind，默认静默继续并交给宿主权限。 |

### 阶段 B：修复 intake 崩溃和类型前置条件

修改：

- `plugins/dev-flow/src/hosts/adapter-policy.ts`
- `plugins/dev-flow/src/core/step-order.ts`

要求：

1. `prepareImplementationWrite` 必须先判断 `workflow.state.mode === "routed"`，再调用 `currentOpenStep`。
2. `currentOpenStep` 自身也增加 intake 防御：非 routed state 直接返回 `undefined`。

### 阶段 C：把 Bash 分析器从拦截器降为辅助分析器

修改 `plugins/dev-flow/src/hosts/adapter-policy.ts`：

1. 保留 `analyzeBashWriteTargets`，因为它对已识别目标仍有价值。
2. `analysis.kind === "unresolved"` 时默认静默 allow，不返回 block；可写入内部 debug telemetry，但不得持续污染模型上下文。
3. `projectRelative` 无法把目标归入仓库时，不再返回 unresolved block：
   - 仓库外目标不是 Dev Flow 工作流资产，由宿主权限处理。
   - 明确位于仓库内的绝对路径仍应转换成相对路径并执行现有判断。
4. direct write/patch 工具缺少可解析目标时，不因“补丁无可解析目标”伪装成 implementation approval；默认 allow，只有明确命中 `.dev-flow` 控制路径时才 block。
5. unreadable workflow 分支中，unresolved Bash 命令不得自动升级成 state unreadable。
6. 删除所有要求模型“拆分命令才能继续”的恢复文案。

不要做：

- 不继续扩充支持命令白名单来追赶所有模型写法。
- 不把 Bash parser 变成完整 shell AST 项目。
- 不因为目标不确定而猜测它写了 protected roots。

### 阶段 D：结构化中断和自动恢复

修改：

- `plugins/dev-flow/src/hosts/adapter-policy.ts`
- 必要时新增 `plugins/dev-flow/src/hosts/hook-outcome.ts`

要求：

1. 把 `PreToolBlock` 改为包含 reason、impact 和 recovery 的结构化对象。
2. `formatPreToolBlock` 统一生成第 4.3 节格式，禁止各分支随意拼接不完整提示。
3. `prepareImplementationWrite` 的自动 begin-unit 成功时不产生用户可见中断。
4. 自动准备失败时保留真实错误类别；不要再次伪装成 state unreadable。
5. `unreadableBlock` 必须携带具体读取失败来源，例如：
   - `active.json invalid`
   - `project.json invalid`
   - `active pointer revision mismatch`
   - `state invalid`
   - `recovery journal open`
6. adapter 最外层只捕获真正的意外异常。对普通操作采用 fail-open + diagnostic；对能够静态确认的 `.dev-flow` 控制写入采用 fail-closed。不得把代码 bug统一翻译为 doctor/recover。

自动恢复动作由模型执行，不允许 Hook 子进程直接递归调用原工具。Hook 只返回机器可读恢复意图；宿主中的模型完成恢复后重试原操作。

### 阶段 E：按宿主分别修正输出协议

修改：

- `plugins/dev-flow/src/hosts/claude-adapter.ts`
- `plugins/dev-flow/src/hosts/codex-adapter.ts`

Claude adapter：

1. allow 且无 advisory：退出 0，无 stdout。
2. block：输出 `hookSpecificOutput.hookEventName = "PreToolUse"`、`permissionDecision = "deny"` 和完整 reason。
3. advisory：仅输出 `additionalContext`，不阻断。
4. 不再输出旧的顶层 `continue/decision` 组合。

Codex adapter：

1. allow 且无 advisory：退出 0，无 stdout。
2. block：使用当前支持的 `{ decision: "block", reason }`。
3. advisory：使用 `hookSpecificOutput.additionalContext`。
4. 禁止返回 `continue: true/false`、`permissionDecision: "ask"`、`stopReason`。

两个 adapter 都要保持 UserPromptSubmit、PostToolUse 和 Stop 的审计写入不影响正常宿主操作。

### 阶段 F：复用 PermissionRequest，实现 feature 级普通授权记忆

修改：

- `plugins/dev-flow/hosts/claude/hooks.json`
- `plugins/dev-flow/hosts/codex/hooks.json`
- `plugins/dev-flow/src/hosts/claude-adapter.ts`
- `plugins/dev-flow/src/hosts/codex-adapter.ts`
- `plugins/dev-flow/src/core/state-store.ts` 或独立的 Core-owned host authorization store
- 建议新增纯函数文件 `plugins/dev-flow/src/hosts/risk-policy.ts`

设计：

1. 两个 manifest 注册 `PermissionRequest`。
2. 风险分类只用于决定“宿主询问后是否可以在本 feature 复用”，不得在 PreToolUse 中独立拒绝命令。
3. 风险至少分两类：
   - `task-reusable`：当前仓库内递归删除、破坏工作树的 Git 操作等；用户通过宿主确认且工具成功后，可在当前 active feature 复用。
   - `always-confirm`：publish、push、deploy、生产变更、云资源删除等重大外部动作；不创建可复用授权。
4. 第一次 PermissionRequest：
   - 没有授权时 Hook 不代决，退出 0，让宿主显示自己的确认界面。
   - 记录 pending 风险指纹，但不得记录为已授权。
5. 用户批准且工具成功后，PostToolUse 根据 tool input 指纹匹配 pending 请求：
   - `task-reusable` 追加 feature-scoped authorization event。
   - `always-confirm` 不追加授权。
6. 后续相同风险类别再次触发 PermissionRequest：
   - active feature 相同且存在 `task-reusable` grant，Hook 返回宿主支持的 allow 形状。
   - feature 已 finalize/abandon、active feature 改变或类别为 `always-confirm`，不复用。
7. 用户拒绝时不会出现 PostToolUse，因此不得产生 grant。
8. 授权记录放在 active feature 的事件账本或 Core-owned 独立文件中；禁止 adapter 直接手写 `state.json`。
9. 授权事件至少包含 host、featureId、riskClass、command fingerprint、grantedAt 和来源 tool event；不得保存 secret、token 或完整敏感命令。

宿主限制：

- `PermissionRequest` 只有在宿主本来准备询问时才触发。用户若启动了 bypass/dontAsk/never 等模式，Dev Flow 不得声称自己还能强制弹窗。
- Codex `PreToolUse` 当前不能强制 ask；不得用 block + 假 ask 模拟原生确认。
- Claude 可以在 PreToolUse 返回 ask，但本计划不使用它作为通用 Bash 风险系统，以保持 Claude/Codex 语义一致并避免重复确认。

- `docs/architecture.md` 或当前权威 Hook/宿主文档
- 如存在错误码文档，更新对应表格

文档必须说明：

1. Bash target analyzer 是工作流辅助，不是命令合法性裁判。
2. `unresolved` 默认继续，由宿主权限负责安全判断。
3. Dev Flow 仍会拦截哪些确定目标和工作流状态。
4. 出现 block 时，用户会看到原因、影响、解决动作和自动重试说明。
5. Claude/Codex 的确认能力差异，尤其是 Codex PreToolUse 不支持 ask。
6. doctor 仅用于有读取证据的状态问题，不用于普通 parser 未识别。
7. feature-scoped authorization 的范围和重大外部动作每次确认规则。

## 6. 测试矩阵

### 6.1 策略单元测试

至少覆盖：

- intake 普通写允许。
- intake protected 写保持门禁。
- routed 未批准 protected 写保持门禁。
- routed 已批准写自动准备 RU 并允许。
- `.dev-flow` 控制文件保持拒绝。
- registered artifact 允许、未注册 artifact 给出具体恢复动作。
- unresolved wrapper/interpreter/xargs/heredoc 不 block。
- `/tmp` 日志不 block。
- logic-complete 前 Git write 保持拒绝。
- state 真损坏与策略代码异常使用不同结果。
- 每个 block 格式都包含原因、影响、解决方案和继续方式。

### 6.2 宿主 adapter 子进程测试

直接启动源码构建后的 Hook，向 stdin 输入真实事件 JSON，断言：

- Claude allow stdout 为空。
- Claude block 使用 `hookSpecificOutput.permissionDecision = "deny"`。
- Codex allow stdout 为空。
- Codex block 使用受支持的 block 形状。
- Codex 输出从未包含 `permissionDecision: "ask"` 或 `continue`。
- advisory 在两个宿主都不阻止原工具。

### 6.3 授权记忆测试

- 首次普通风险 PermissionRequest 不代决。
- 没有 PostToolUse 时不生成授权。
- 用户批准并成功执行后生成 active-feature grant。
- 同 feature 后续同类 PermissionRequest 自动 allow。
- 切换 feature 后旧 grant 不生效。
- finalize/abandon 后 grant 不生效。
- publish/deploy 等 `always-confirm` 即使成功也不生成 grant。
- Claude 生成 Claude 协议，Codex 生成 Codex 协议。

### 6.4 记录复现测试

把问题记录中的两类命令简化为稳定 fixture：

```sh
printf '%s\n' '=== 验证：单一确定性写入 ===' >> docs/dev-flow/usage-experience.md
```

```sh
node verification-script.mjs | tee /tmp/dev-flow-verification.log
```

验收断言：

- 第一条在普通 docs 目标上不触发 state unreadable。
- 第二条不触发 write-target-unresolved block。
- 两条都不要求模型为了迎合 parser 改写成特定命令形式。

## 7. 实施顺序和验证命令

严格按以下顺序执行，某一步失败先修复，不要跳过：

1. 新增失败回归测试，确认旧代码能够复现问题。
2. 修复 intake guard，运行目标测试。
3. 修改 unresolved/仓库外目标策略，运行目标测试。
4. 引入结构化 outcome 和完整恢复消息，运行全部 unit。
5. 分别修正 Claude/Codex adapter 输出并增加子进程测试。
6. 实现 PermissionRequest 授权记忆并运行 host/interop 测试。
7. 更新文档。
8. 源码验证通过后再运行构建脚本更新受版本控制 bundle。

建议命令：

```sh
node --test tests/unit/v2-adapter-overlay.test.mjs
npm run typecheck
npm run test:unit
npm run test:routes
npm run test:interop
npm run test:host-e2e
npm run build
npm run build:check
npm run test:e2e
```

最后运行发布级验证：

```sh
npm test
```

约束：

- 源码测试不得依赖 `dist/`。
- 不得手工编辑 `plugins/dev-flow/dist/*.mjs`。
- 只有源码和目标测试通过后才运行 `npm run build`。
- 实施智能体不得 commit、push、创建 PR 或发布插件。

## 8. 验收标准

### 8.1 必须通过

- 问题记录中的两类命令不再触发原错误。
- 合法 intake state 不再被任何 adapter 报为 unreadable。
- parser unresolved 不再直接中断流程。
- 已确定的 protected/control 写入门禁无回归。
- 所有 Dev Flow block 都有具体原因、影响、解决方案和重试说明。
- 可自动解决的问题不会要求用户手工运行一串命令。
- 需要用户决定时只询问一次，确认后模型继续解决并重试。
- 普通风险授权只在当前 feature 复用，重大外部动作不复用。
- Claude/Codex Hook 输出均符合各自当前协议。
- typecheck、unit、routes、interop、host-e2e、e2e 和 build check 全部通过。

### 8.2 明确不承诺

- 不承诺用静态 Bash 分析识别任意解释器的全部副作用。
- 不承诺在宿主关闭确认或 bypass permissions 时强制弹窗。
- 不承诺 Hook 子进程自己暂停并重新执行任意工具；自动继续由宿主原生权限流或模型恢复循环完成。
- 不在本任务中重构全部 FeatureState 类型、工作流阶段或批准证据模型。
