## 1. 目标与完成标准

本计划处理报告中的 P1、B1 至 B4、U1 至 U7，并保留现有证据链、严格批准、review basis 级联失效、checkpoint 恢复和跨宿主一致性。

完成后必须满足：

1. standard-m 在 checkpoint 后修订实施计划，可以完成重新审查、重新批准并开始下一实现单元，不再出现 REVIEW_BASIS_STALE 死锁。
2. 测试与修复被拆成不可 checkpoint 的两个回撤单元时，计划审查阶段即可发现，而不是等到实现阶段才失败。
3. Git 忽略的构建产物不进入 protected-root 指纹、checkpoint、rollback 或 drift。
4. checkpoint 能明确区分环境前置失败和回归验证失败，MCP 客户端能够直接读取失败输出。
5. dev_flow_classify 可以仅根据结构化事实返回确定性推荐，并且其 classification 可原样传给 lock。
6. approval、grill、review job 和 implementation evidence 的公开提示与 Core 行为一致。
7. 普通 MCP mutation 不再返回完整 FeatureState；完整状态仍可通过 dev_flow_status 获取。
8. 当前仓已有的 feature-check 与 plan-review/code-review 正确语义得到自动化保护，不因缓存或打包重新退化。
9. CLAUDE.md 不再硬编码过期版本号。
10. 所有 MCP tools/call 参数在进入 handler 前按公开 inputSchema 做服务端运行时校验；缺少 expectedRevision、字段拼错或未知字段不再退化成误导性的 Core 错误或被静默忽略。
11. review job 的租约到期时间、失败后是否保留 claim 和安全释放路径对调用方可见，同时不泄露或弱化 capability。
12. README 与架构文档明确：当前受支持宿主只有 Claude Code 和 Codex CLI；其他客户端直连 MCP 仅可用于诊断，不能视为完整、受保护的 Dev Flow 工作流。

## 2. 已锁定的设计决策

实施模型不得重新选择以下方案。

### 2.1 分级推荐不解析自由文本关键词

现有 2.0 设计明确禁止关键词分级和业务案例映射。因此不对 scopeFacts、topologyFacts 等自然语言做关键词匹配，而是在 classificationBasis 中增加可机器判定的 signals。

signals 是事实，不是调用方直接填写的 level、topology 或 execution 结论。Core 根据 signals 生成这些结论，并返回逐项理由。

### 2.2 standard-m 增加 rollback-operability 审查

standard-m 与 standard-l 都需要 rollback-operability。增加一次计划审查的成本，换取在实现前发现无法独立 checkpoint 的 RU。当前 Trace 不包含足够语义，禁止新增基于任务标题的脆弱静态文本检查。

### 2.3 protected roots 默认采用 Git 权威忽略语义

Git 仓库使用 git ls-files 的 tracked 加未忽略 untracked 文件集合。暂不增加 protectedRootsExclude，避免同时维护 Git ignore 与自定义 glob 两套规则。

### 2.4 MCP mutation 默认 brief

mutation 只返回精简状态和操作特有数据。dev_flow_status 是获取完整 FeatureState 的唯一常规入口。此改动与插件技能、测试和宿主适配器同批更新，不保留 mutation 的 full 响应模式。

### 2.5 不在本任务中决定下一发布版本号

package.json 保持实施开始时的权威版本。CLAUDE.md 删除“当前 x.y.z”的硬编码文字。若维护者之后决定发版，再单独执行 version:sync。

### 2.6 已存在的能力不重复实现

- RU 的 forwardVerification 已支持引用项目配置中的精确 command ID，只补配置、模板、错误呈现和测试。
- feature-check 已并入 finalize，当前 skill 文案正确，只补合同测试。
- plan-review 与 code_review 已有不同阶段和技能，只强化文档与合同测试。

### 2.7 OpenCode 直连只作为非受信客户端测试

本次不把 OpenCode 加入支持矩阵。OpenCode 具备本地 MCP、插件事件和工具权限机制，理论上可以另行实现宿主适配器；但当前仓只有 Claude/Codex 的 manifest、hook 事件映射、写入保护和跨宿主测试。

审计依据：

- 仓内 docs/architecture.md、.claude-plugin/plugin.json、.codex-plugin/plugin.json、hosts/claude/hooks.json、hosts/codex/hooks.json 和两个 adapter 源文件。
- OpenCode 官方 Plugins 文档：https://opencode.ai/docs/plugins/。
- OpenCode 官方 MCP servers 文档：https://opencode.ai/v2/docs/mcp-servers。
- OpenCode 官方 Permissions 文档：https://opencode.ai/v2/docs/permissions。

因此：

- OpenCode 直接启动 dist/mcp-server.mjs，只能验证 MCP/Core 对异常调用方的鲁棒性。
- 直连不提供本仓要求的 UserPromptSubmit、PreToolUse、PostToolUse、Stop 语义，不能保证真实用户证据、写入拦截、回合边界或工具审计。
- 禁止通过“执行模型代替用户决定”、手工伪造 hook 事件或增加无 hook 的批准旁路来宣称兼容。
- 若未来正式支持 OpenCode，必须另立计划实现并测试 OpenCode adapter、事件归一化、权限/写入守卫、分发清单和端到端路线，不夹带在本优化任务中。

### 2.8 review capability 保持机密且由持有者控制

- claimRequestId 是调用方生成并保存的高熵 capability；相同值用于幂等重试。
- Core 不提供“查询当前 capability”，不接受短值或可预测值，也不在公开 job 中返回 requestSha256。
- 新增的释放只能由持有匹配 capability 的调用方执行。
- 增加可观测性和安全释放，不把单租约改成可被其他调用方抢占的锁。

## 4. 公共接口与类型变更

### 4.1 ClassificationSignals

在 plugins/dev-flow/src/policy/types.ts 增加：

    export interface ClassificationSignals {
      impactScope: "single-location" | "single-module" | "cross-module";
      sharedContract: boolean;
      independentChains: number;
      coordinatedRollback: boolean;
      requirements: RequirementsState;
      formalControls: Array<
        "trace" | "independent-review" | "multiple-rollback-units"
      >;
    }

ClassificationBasis 增加可选 signals：

    export interface ClassificationBasis {
      scopeFacts: string[];
      topologyFacts: string[];
      uncertaintyFacts: string[];
      riskFacts: Partial<Record<RiskLabel, string[]>>;
      decisionRefs: string[];
      signals?: ClassificationSignals;
    }

兼容约束：

- state schema 中 signals 可选，旧 2.0 state 继续可读。
- basis-only classify 调用必须提供 signals。
- 旧的手工 level/topology classify 输入在本次继续支持。
- 新 lock 结果必须持久化完整 classificationBasis，包括 signals。

### 4.2 Classification 推荐规则

新增纯函数 recommendClassification(basis)，规则固定如下：

1. topology：
   - coordinatedRollback 为 true：coordinated-rollback。
   - 否则 independentChains 大于等于 2：multi-chain。
   - 否则 sharedContract 为 true：shared-contract。
   - 否则：local。
2. scope 基础 level：
   - single-location：XS。
   - single-module：S。
   - cross-module：M。
3. 最终 level 为 scope 基础 level 与 topologyMinimumLevel 的较高者。
4. riskLabels 为 riskFacts 中具有至少一条非空事实的合法 key，排序后去重。风险不提高 level。
5. M/L execution：
   - requirements 不是 provided-confirmed：standard。
   - formalControls 非空：standard。
   - 其他情况：light。
6. XS/S 不返回 execution；requirements 可以保留用于 warning 和审计。
7. independentChains 必须是大于等于 1 的整数。
8. riskFacts 的非法 key、空事实、互相矛盾的 signals 都返回结构化 issue。

建议结果定义为可判别联合：

    type ClassificationPreview =
      | {
          readyToLock: true;
          classification: Classification & {
            classificationBasis: ClassificationBasis;
          };
          route: RouteId;
          classificationBasis: ClassificationBasis;
          obligations: ClassificationObligation[];
          reasons: ClassificationReason[];
          issues: [];
        }
      | {
          readyToLock: false;
          classification?: Classification;
          route?: RouteId;
          classificationBasis?: ClassificationBasis;
          reasons: ClassificationReason[];
          issues: ClassificationIssue[];
        };

ClassificationIssue 至少包含 code、path、message、recoveryHint；ClassificationReason 至少包含 field、value、basisPaths 和 message。

### 4.3 classify 与 lock schema

dev_flow_classify 接受二选一输入：

1. 推荐模式：只传 classificationBasis，且其中包含 signals。
2. 兼容模式：传 level、topology 等旧字段，可附 classificationBasis。

行为：

- 推荐模式调用 recommendClassification。
- 兼容模式仍校验拓扑最低级别、execution 和 risk basis。
- M/L 缺 execution 不再返回一个看似有效的 standard route，而是 readyToLock: false 和 missingFields issue。
- 字段错误必须给出完整 JSON path。

dev_flow_lock_classification 的 classification 首选 classifyResult.classification 的原样形状：

    {
      level,
      topology,
      execution?,
      requirements?,
      riskLabels,
      acceptanceAssistSuggested,
      classificationBasis
    }

兼容一个发布周期的旧平铺 basis 字段。若嵌套与平铺同时存在：

- 内容完全相同：接受并规范化为嵌套形状。
- 内容不同：返回 CLASSIFICATION_BASIS_CONFLICT，列出冲突字段路径。

### 4.4 ProjectConfig 前置验证

ProjectConfig.verification 增加可选字段：

    preflightCommands?: string[];

规则：

- 每个 ID 必须引用 verification.commands 中的已配置命令。
- 去重并保持声明顺序。
- 不存在时等价于空数组。
- 项目 schemaVersion 保持 1；这是可选向后兼容字段。

checkpoint 顺序：

1. 执行 preflightCommands。
2. 任一失败时抛 CHECKPOINT_PREFLIGHT_FAILED，RU 保持 active，不创建 manifest。
3. 全部通过后执行 RU.forwardVerification。
4. forward 失败使用 CHECKPOINT_VERIFICATION_FAILED。
5. 成功 manifest 的 verificationAttempts 增加 phase: preflight | forward；解析器接受旧 manifest 缺少 phase。

dev_flow_verify 同样先执行 preflightCommands，再执行用户选择或默认 verification commands。preflight 失败作为普通 verification attempt 持久化，但输出必须标明 phase。

### 4.5 MCP 工具错误结果

tools/call 内的 DevFlowError 不再转换成 JSON-RPC protocol error。返回：

      isError: true,

        {
          type: "text",
          text: "结构化错误 JSON"

只有未知 RPC method、无法解析的协议消息等协议级错误继续使用 JSON-RPC error。

- attemptId
- phase
- commandId

- cwd
- exitCode
- outputTail，最多 4000 字符

### 4.7 MCP tools/call 运行时输入校验

公开 JSON Schema 不能只依赖客户端自觉执行。server 在 dispatch 前调用统一的 validateToolInput(toolName, arguments)，直接以 toolSchemas[toolName].inputSchema 为权威校验同一份数据，禁止另建一套易漂移的字段表。

第一版验证器必须完整支持本仓 inputSchema 已使用的关键字：

- type：object、array、string、integer、boolean。
- required、properties、additionalProperties（boolean 或子 schema）。
- items、minItems、maxItems、uniqueItems。
- enum、const、oneOf。
- minLength、minimum、pattern。
- 空 schema {} 表示接受任意 JSON 值。

schema 构造器同步改造：

- featureMutation 接收 requiredExtras 与 optionalProperties，语义必填的 approvalId、host、completion 等必须进入 required，不能因为使用 helper 而仅声明 featureId/expectedRevision。
- 系统审计全部 tool schema 的 handler 解构字段，确保每个无默认值的字段都在 required 中。
- 只有合同明确可选的字段才允许 handler 设置默认值；不得用 undefined 进入 Core 后再产生无关错误。
- 所有 object 默认 additionalProperties: false；确需开放字典时，仅允许 additionalProperties 使用明确的 value schema。

校验失败返回第 4.5 节的 isError 结果，固定为：

    {
      code: "INVALID_TOOL_INPUT",
      message: "dev_flow_xxx input does not match its schema",
      details: {
        tool,
        issues: [
          { path: "$.expectedRevision", keyword: "required", message: "required field is missing" }
        ],
        mutationApplied: false
      }
    }

issues 按 path、keyword 稳定排序；未知字段使用 additionalProperties，并在 issue 中包含 unknownField 与 allowedFields。至少保证：

- record_decision 传 revision 而不是 expectedRevision，同时报告 $.expectedRevision 缺失和 $.revision 未知，不进入 state CAS。
- classify 顶层传 riskFacts 被拒绝并指向 $.riskFacts；正确位置为 $.classificationBasis.riskFacts。
- completion、traceDelta 等嵌套对象的未知字段同样被拒绝。
- tools/list 暴露的 schema 与运行时验证使用同一个对象；增加合同测试防止两者漂移。

### 4.8 review job 租约与释放合同

新增公开类型，不暴露 capability 哈希：

    interface PublicReviewLease {
      claimedAt: string;
      leaseExpiresAt: string;
    }

    interface PublicReviewJob extends Omit<ReviewJob, "claim"> {
      lease?: PublicReviewLease;
    }

claim_review_job、get_review_job 以及其他返回当前 job 的只读视图使用 PublicReviewJob。claimed 状态必须带 lease，pending/submitted 不带。

新增 dev_flow_release_review_job：

    {
      featureId,
      expectedRevision,
      batchId,
      jobId,
      capability
    }

行为：

- 只接受 current batch 中 status=claimed 且 capability 哈希匹配的 job。
- 成功后原子改回 pending、删除 claim，返回 brief state 与 PublicReviewJob。
- submitted、sampling、未 claim、错误 capability 分别返回稳定错误码；错误 capability 不泄露租约或持有者信息。
- 即使租约按当前时间已到期，只要 ledger 中仍是同一 claim，原持有者仍可安全释放；其他调用方继续通过 claim_review_job 的既有过期恢复路径重新 claim。

提交诊断：

- MCP schema 失败明确 mutationApplied: false。
- capability 已验证后，completion、finding scope 或 attestation 校验失败时，错误 details 包含 claimRetained: true、leaseExpiresAt 和 retryHint；不得清除 claim。
- REVIEW_JOB_LEASE_EXPIRED 包含 leaseExpiresAt 与 recoveryHint，提示用新的高熵 claimRequestId 重新 claim。
- 增加显式时钟注入测试：过期后新 claim 能立即恢复。不得改用只存在于单进程内的单调时钟，因为租约状态需要跨进程持久化解释。

## 5. 分阶段、分批实施步骤

必须按下列顺序实施。每批先写失败测试，再改源码；不得在中间批次运行 npm run build。

### 5.0 交付阶段与审核边界

吸收 Kimi 计划“阻塞修复、可用性优化、破坏性合同分开审核”的优点，但不在计划中预设 2.0.2 或 3.0.0。版本号仍由维护者在准备发布时根据实际兼容面决定。

| 阶段 | 包含批次 | 目标 | 审核边界 |
| --- | --- | --- | --- |
| 阶段 I：阻塞与数据安全 | A、B、C | 修复计划修订死锁、RU 原子性、Git-aware 快照和 checkpoint 诊断 | 完成后可独立做源码/测试审核；不得夹带 mutation 响应破坏性调整 |
| 阶段 II：合同与可用性 | D、E、F | 完成 MCP 输入严格化、classification/U1-U6、租约、宿主证据和文档一致性 | 明确列出 fail-fast 合同收紧；维护者可选择与阶段 I 同一兼容发布或分开发行 |
| 阶段 III：响应合同调整 | G | 单独实施 U7 mutation brief | 属于外部 MCP 响应合同变更；必须在开始前由维护者确认目标版本与发布说明 |

阶段规则：

1. 每个阶段结束先完成该阶段目标测试、typecheck、unit、受影响 routes/interop，再进入下一阶段。
2. 阶段 I 或 II 审核未通过时，不得用阶段 III 的响应改造掩盖或批量改写测试断言。
3. 只有维护者明确决定阶段性发布时，才在该阶段源码稳定后修改 package.json 版本并运行 version:sync；version:sync 只同步 manifest，不负责升级 package.json。
4. 默认仍只在全部选定阶段稳定后运行一次正式 build；若维护者选择分阶段发布，则每个发布边界各自执行完整构建与发布验证。

## 8. 风险与失败处理

### 8.1 Git 枚举风险

- git ls-files 返回的路径必须再次做项目相对路径、NFC 和 symlink 校验。
- protectedRoots 重叠时必须去重。
- Git worktree 中 Git 命令失败不得使用文件系统 fallback，防止忽略策略悄然变化。
- 非 Git fixture 才允许 fallback。

### 8.2 计划修订时的活动单元

- active RU 的 begin baseline 已固定，计划修订可能使其无法安全归属。
- 因此直接拒绝计划登记；不自动 checkpoint、不自动 rollback。
- 错误必须给出 activeUnitId 和明确恢复动作。

### 8.3 classification 推荐过度自动化

- Core 只根据结构化 signals 推导，不判断自然语言事实真伪。
- reasons 必须引用 basis path，不能声称做了语义证明。
- 用户/模型仍负责通过仓库调查提供真实 signals。
- risk 继续只增强义务，不改变 level。

### 8.4 preflight 误分类

- Core 不分析命令输出文本来猜环境问题。
- 只有项目显式配置为 preflight 的命令失败才使用 PREFLIGHT 错误码。
- 未配置时保持原验证行为。

### 8.5 第三方 MCP 客户端造成“部分可用”错觉

- MCP 工具能推进 Core state，不代表宿主写入保护、用户证据捕获和 Stop 边界已经安装。
- 文档必须使用“支持矩阵 + 必需组件”描述兼容性，doctor 不能输出未验证的第三方宿主支持结论。
- 缺少可信 host-event 时保持 fail-closed；不得为提升第三方客户端通过率降低门禁。

### 8.6 租约恢复的安全边界

- capability 丢失不等于允许查询或抢占；只能由持有者 release，或在过期后由新 claim 自动回收。
- invalid completion 必须保持原 claim，避免调用方误判“提交失败即释放”。
- 使用持久化 UTC 时间戳并通过注入时钟测试前跳/到期；不把进程内 monotonic clock 写入跨进程合同。
