# Dev Flow 5.0.0 动态治理与可靠性优化计划

## Summary

- 发布单个破坏性大版本 `5.0.0`：不兼容 4.x active state、project config、review/checkpoint schema 或旧 MCP 调用合同，不提供迁移器。
- 基础分类收敛为 `XS / S / M / L`；删除 `light/standard` 轴。模型负责调查取证，Core 根据变更表面、行为复杂度和拓扑计算最低级别，再独立派生治理控制并编译成完整有序路线。
- 解决两次实践中的系统性问题：交互重复作答、决策状态分裂、错误不可诊断、符号链接阻塞、文件证据遗漏、reconcile 全量 stale、finalize 无恢复链、受保护范围外交付物、全量复审与检查点验证成本。
- 保留严格用户溯源和治理下限；效率优化只通过可信弹框、语义 diff、角色级复用、精确 freshness 和 targeted verification 实现。

## Core Contract and Public Interfaces

### 1. Schema 与项目范围

- `FeatureState` 升为 schema v4，contract 升版；project config 升为 schema v2，review ledger 与 checkpoint manifest 升为 v2。
- 用单一 `governedRoots` 替代 `protectedRoots`，同时负责写门禁、归属、指纹、checkpoint、验证和交付快照；支持目录和精确文件，exclude 在安全检查前应用。
- verification command 新增 `provides: ("targeted" | "behavior" | "integration" | "full")[]`；`preflightCommands` 只负责环境准备，不计验证证据。
- 5.0 启动时发现旧 schema，返回明确 `UNSUPPORTED_*_SCHEMA`，要求先用 4.x finalize/abandon、备份审计目录，再重新初始化。

### 2. 分类与动态路线

分类信号改为：

- `changeSurface`：single-site→XS、single-component→S、multi-component→M、system-wide→L。
- `behaviorChange`：mechanical→XS、bounded-rule→S、new-capability→M、systemic-change→L。
- topology 下限：local→XS、shared-contract→M、multi-chain/coordinated-rollback→L。
- 最终 level 取三者最高值；风险不改变 level，只增加控制。
- 模型必须附仓库证据和理由；可有依据向上加强，不允许直接低于 Core 下限。

`dev_flow_lock_classification` 必须提交结构化 `boundaryAudit`：

- 每个已识别边界只能处置为仓库事实或已解决用户决策，并带 evidence/decision reference。
- Skill 必须扫描默认假设、自由空间、TBD、fallback、范围和验收留白；存在未处置项时拒绝锁定。
- M/L 或含任一风险标签时，lock 先展示“事实依据、level、完整路线、启用及未启用控制原因”，创建 route-confirmation；确认后由 `dev_flow_answer` 原子锁定。普通无风险 XS/S 展示后直接锁定。
- 用户可直接增加控制；要求减弱时必须纠正触发事实并重新分类。
- 首次 governed write 前允许重算控制；实现开始后只能单调增加。预实现阶段若有实质路线变化，原 route-confirmation 失效并重新呈现。

治理控制按以下规则派生：

- `requirements`：L、new-capability/systemic-change 或 shared-contract 必须有持久需求证据；优先冻结已有已确认材料，否则生成需求工件。
- `plan`：XS 仅定位、S 使用简报、M/L 使用正式计划；plan-review、unit-chain 或 operational recovery 会强制升级为正式结构化计划。
- `trace`：L 必有；M 在共享契约、多 RU、正式恢复策略或 plan-review 启用时开启。
- `plan-review`：L 默认开启；M 在共享契约、多 RU、恢复控制或专项风险存在时开启。角色按事实派生，包括 requirements-coverage、architecture-testability、rollback-operability 及 security、data-irreversibility、money-safety、contract-failure、recovery-observability、critical-correctness。
- `execution-approval`：L 必有；M 在共享契约、plan-review、多 RU、恢复控制或高后果风险存在时开启；XS/S 仅由 security、money、critical-correctness、irreversible 等事实追加。
- `checkpoints`：所有任务有自动 baseline；L、多 RU、可执行回撤或不可逆风险升级为 unit-chain。
- `recovery`：所有任务生成 delivery reverse；L 或 data/money/availability/多单元耦合需要 operational strategy；只有真实可逆且有 unit-chain 时声明 executable rollback；irreversible 改为 backup/preview/abort/compensation/full verification，不伪称可回滚。
- `code-review`：XS 无独立阶段、S 聚焦自审、M/L 独立实现审查；专项风险提升深度和角色。
- `verification`：始终包含 targeted；新能力/安全边界增加 behavior，多组件/共享契约/data/money/external/availability 增加 integration，systemic L、critical-correctness、irreversible 增加 full。

`dev_flow_classify/status` 返回 level、控制集、逐项理由和确定的 ordered route，不再返回 light/standard。用户视图完整展示实际路线，而非只显示当前步骤。

### 3. MCP 交互与工具简化

- 删除 `dev_flow_resolve_decision`。现场取舍只能走 `request_grill_decision → elicitation/dev_flow_answer`；既有用户结论由 `dev_flow_record_decision` 一次性记录 resolved evidence/conclusion，并绑定 feature 启动后的可信用户事件。
- `dev_flow_present_approval` 删除 `approvalId` 参数，由 Core 选择当前唯一可呈现审批。
- `dev_flow_record_step(implementation)` 删除 `evidence.files`；Core 从可信写事件、checkpoint、Git 基线和已确认 ownership 派生完整文件集合。
- 删除公开 `dev_flow_feature_check`；完整性检查并入 finalize。
- 新增受限的 `dev_flow_repair_feature`，只允许重建 active pointer、current stage、freshness 和 review/status 投影等派生状态；不得改写用户决策、ownership、原始证据或 checkpoint 历史。

原生交互默认启用：

- 使用现行 MCP form elicitation 的 `oneOf + const + title` 选项格式，替代旧 `enumNames`；用户 accept 后直接可信落账。[MCP Elicitation](https://modelcontextprotocol.io/specification/draft/client/elicitation)、[SEP-1330](https://modelcontextprotocol.io/seps/1330-elicitation-enum-schema-improvements-and-standards)
- 默认最长等待 60 秒；超时发送 `notifications/cancelled`，忽略迟到响应，并对当前 MCP 会话熔断到文本。[MCP Cancellation](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)
- decline、cancel、协议错误或缺少能力都保留 pending decision，并提示用户直接回复完整中文选项。
- 普通 AskUserQuestion/request_user_input 面板若没有可信宿主事件，不得冒充原生 elicitation。

所有 MCP 文本错误始终包含稳定 code、中文原因、影响、恢复动作和白名单安全细节；可显示文件、字段、允许范围、缺失证据和命令失败，不显示 capability、内部 hash、token 或秘密。

## Implementation Changes

### 1. Governed 文件、符号链接与交付

- Hook 为每次放行的智能体写入记录规范化路径、host、event 和前后内容摘要，自动标为 feature-owned。
- IDE、人工或无法归因的变更创建唯一 ownership decision；不得按“位于 scope 内”静默接纳。
- implementation inspect 提供 Core 派生文件预览；code-review 修复产生的新可信写入自动进入交付。
- finalize 仍拒绝未知归属，但错误正文直接列出具体文件和恢复动作。

符号链接规则：

- 仅允许 Git 跟踪、解析目标仍位于仓库且不进入 `.git/.dev-flow` 的 symlink。
- 指纹与 checkpoint 保存链接类型及 link target blob，不跟随读取目标；rollback 原子重建链接本身。
- 未跟踪链接、仓外逃逸链接和控制目录链接继续 fail-closed。
- exclude 路径在 symlink 校验前过滤。

### 2. Freshness、reconcile 与恢复链

- 删除“一次 contentChanged 将 review/verification/checkpoint/implementation 全部 stale”的逻辑。
- 每类证据保存自己的规范化 basis：
  - review 按 role basis；
  - execution approval 按执行语义 basis；
  - checkpoint 按单元 scope、依赖和内容；
  - verification 按 governed-root fingerprint；
  - implementation 文件集合实时派生，不再维护人工 freshness。
- reconcile 只更新 lineage、ownership 和受影响证据；仅 HEAD 变化或对账晚于验证但文件字节未变时，不产生 stale。
- 真实过期时撤销最早受影响步骤及下游 feature-check/finalize claim，使 status 可从 finalize 精确回到 planning、implementation 或 verification；reconcile 本身不运行长测试。
- 已确认 checkpoint 只有在外部改动触及其文件且不属于合法后续 unit 时才使链失效。

### 3. Trace、审查与性能

- 实施计划登记时执行阶段完整的 Trace 校验，提前拦截 AC 无 TEST、RU scope/依赖/命令不完整等问题，避免 implementation 阶段才发现。
- Review ledger v2 为每个角色保存独立 `roleBasisHash`；新 batch 中未受语义 diff 影响的角色以 `reused` 状态引用旧提交，受影响角色才创建新 job，未知 diff 保守全量重审。
- 角色依赖固定为：coverage 看需求/AC/TASK/TEST，architecture 看组件/任务/测试与契约，rollback 看 RU/scope/dependency/recovery commands，专项角色只看对应风险切片。
- jobs 标记 parallel-safe；宿主支持子代理或 sampling 时并行优先，不支持时顺序回退。Assurance 仍只按真实 attestation/sampling 证据计算。
- finding target 接受 governed project path 或当前 frozen trace 中存在的 REQ/AC/TASK/TEST/RU ID；evidence 还可引用当前 job 包里的冻结需求/计划工件，其他自由字符串继续拒绝。
- RU checkpoint 只运行计划明确声明的 targeted forward verification；final verification 根据 `provides` 选择覆盖全部保证类型的最小命令集合并去重。
- `.next` 等缓存清理只能由项目显式 preflight 配置，Core 不内置框架识别或目录删除。

## Skills, Documentation, and Release

- 删除 `feature-check` skill、agent metadata 和公开工具。
- 全量重写其余技能：
  - `task/status`：动态分类、完整路线预览、控制原因、条件式路线确认。
  - `requirements/grillme`：boundaryAudit、现有材料复用、原生弹框优先、文本降级、现场决策与既有结论分流。
  - `plan/coverage-review`：动态正式计划、前置 Trace 校验、语义 diff、targeted RU。
  - `plan-review`：动态角色、parallel-first、role-basis 复用和新 finding 定位合同。
  - `implement`：baseline/unit-chain，不再手填 files；可信写入自动归属。
  - `code-review`：按 Core 返回的 none/focused/independent/full 深度执行，不复制风险映射。
  - `verify`：按 guarantee 集与 command `provides` 执行；preflight 不算 evidence。
  - `rollback-safety`：三层恢复保证与不可逆补偿。
  - `doctor/finish`：稳定错误码、安全细节、派生 repair 和精确阶段恢复。
- README、路线文档和工具示例全部移除六路线、approvalId、resolve_decision、protectedRoots 和手填 implementation files。
- 发布说明明确 4.x 收尾/备份/重新初始化步骤；源码与测试稳定后统一构建受版本控制的三个 bundle，执行版本同步。

## Test Plan and Acceptance

- 分类矩阵：README 单点→XS；局部规则→S；星座多职责新能力→M；Vite lifecycle/API→M + shared-contract controls；跨包迁移→L；风险只增控制不抬 level。
- 路线编译：验证同为 M 的本地单单元与共享契约/多 RU 生成不同但确定的完整流程；M/L 与风险路线确认、增强控制、事实修正重算、实现后禁止降级。
- 交互：标准 elicitation schema、accept 原子落账、cancel/timeout cancellation 与会话熔断、文本 provenance、跨宿主/重放拒绝、普通面板结果拒绝。
- 决策：不存在公开 resolve 工具；grill 与 ledger 无法形成 pending/resolved 分裂；record_decision 只生成可信 resolved 记录。
- 文件治理：docs/根级 Markdown 纳入 governed roots；阶段写门禁；可信写自动归属；IDE 改动触发确认；implementation 无 files 输入仍完整；code-review 新文件进入 snapshot。
- Symlink：安全 tracked 仓内链接可启动、checkpoint、rollback；未跟踪、仓外、控制目录链接拒绝；excluded symlink 不阻塞。
- Freshness：manual commit 但字节不变不 stale；同字节 reconcile 不破坏 verification；真实 verification drift 从 finalize 回退并可重跑；review/approval 只按相关语义失效；checkpoint 按路径交集判断。
- Review/Trace：计划登记即拒绝缺失覆盖；Trace ID/冻结工件 finding 合法；越界 target 拒绝；角色复用、未知 diff 全重审、并行与顺序 fallback、assurance 不夸大。
- Verification：RU 只跑 targeted；final 覆盖 guarantee 并去重；preflight 失败不记验证成功；项目未配置所需 guarantee 时明确阻塞。
- Doctor/repair：检测派生状态不一致并安全重建；任何 repair 都不能改变决策、ownership 或原始证据。
- 完成目标测试后运行 `npm run typecheck`、`npm run test:unit`、`npm run test:routes`、`npm run test:interop`、宿主 E2E；最后运行 `npm test` 与 `npm run build:check`。

## Assumptions and Non-goals

- 5.0 继续要求 Git 仓库和受支持的 Claude/Codex hook；第三方无可信 hook 客户端只用于诊断。
- 4.x 未完成 feature 不迁移；升级前由用户自行完成、放弃或备份。
- Vite worker 的 SIGINT、pnpm wrapper 与 tsx 循环导入属于业务仓测试实践，不进入 Dev Flow Core。
- 不自动删除 `.next` 或其他缓存，不自动 stash/reset，不自动接纳人工文件，不允许风险接受绕过最低 level/control。
