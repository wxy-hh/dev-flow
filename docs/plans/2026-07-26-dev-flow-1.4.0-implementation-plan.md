> **状态：** 可直接实施  
> **日期：** 2026-07-26  
> **基线：** 1.3.0 / `main`  
> **目标版本：** 1.4.0  
> **设计权威：** `docs/plans/2026-07-26-dev-flow-plugin-real-world-optimization-plan.md`  
> **适用执行者：** 可读写本仓库、能运行 Node.js 20+ 测试的编码模型或工程师

## 1. 交付目标

在不新增 route、HUMAN GATE、必需 Markdown artifact、MCP tool 或 FeatureState 持久化字段的前提下完成：

1. 风险 evidence 在 `risk-minimal`、`light-l`、`standard-m`、`standard-l` 中一致强制。
2. HUMAN GATE 只接受 presentation 后、宿主真实捕获、整句明确批准的回复。
3. MCP 在调用前暴露合法 riskLabels 和当前步骤所需 evidence。
4. status 明确区分 verification 缺失、fresh、stale。
5. verification 命令证据与人工/UI 验收证据可同时保存，且不互相伪装。
6. 设计完备任务可以安全地优先使用 light-L。
7. Skills 明确门禁顺序、批量实现、压缩恢复、artifact 编辑和 finalize 前验收。
8. 发布 1.4.0，并通过自动化、Claude、Codex 和跨宿主回放。

本实施文档是决策完整的执行规范。遇到与 feedback 分析稿冲突的内容，以本文件和其设计权威为准。

## 2. 不可变约束

- FeatureState `schemaVersion` 保持 `1`，不编写迁移。
- 不增加 FeatureState 顶层字段；`manualAcceptance` 只扩展既有 `verification.attempts[]` 和 `steps.verification.evidence` 的内部形状。
- `NextAction.kind`、`NextAction.step`、route ID、step ID、gate ID 保持不变。
- 不增加 `plan_bundle`、partial implementation、`implementationProgress`、UI 专用路线/步骤/门禁。
- 不允许 present 前证据追认，不允许同回合自确认。
- 不冻结 `verification.md`；它继续承载人工叙述证据。
- 不降低 topology 最低 level，不静默把 `provided-confirmed` 改为 light。
- 不放宽 `.dev-flow` 控制文件、artifact allowlist、protected roots、Git guard。
- 新的只读响应字段必须向后兼容：旧消费者忽略未知字段时行为不变。
- 切片 C 不得早于或脱离切片 A 发布。

## 3. 最终接口定义

### 3.1 Evidence 类型

在 `plugins/dev-flow/src/policy/types.ts` 增加：

```ts
export type VerificationKind =
  | "targeted"
  | "behavior"
  | "integration"
  | "full";

export interface RequiredEvidence {
  fields: {
    reviewType?: "plan" | "code";
    reviewDepth?: "full";
  };
  checks: string[];
  verificationKinds: VerificationKind[];
}
```

`targeted` 是无风险标签路线的现有验证基线，必须保留，不能因优化计划只列风险增强 kinds 而删除。

扩展 `NextAction`，仅增加可选字段：

```ts
| {
    kind: "run-step";
    step: string;
    requiredEvidence?: RequiredEvidence;
  }
| {
    kind: "feature-check";
    requiredEvidence?: RequiredEvidence;
  }
```

`deriveNext()` 仍可返回不含可选字段的原始动作；由 core `nextAction()` 使用完整 FeatureState 补充 evidence。

### 3.2 Evidence 形状

```ts
// plan_review
{
  reviewType: "plan"
}

// code_review
{
  reviewType: "code",
  reviewDepth?: "full",
  checks?: ["security"]
}

// risk_controls | rollback_safety | rollback_unit
{
  checks: ["rollback", "full-rollback"]
}

// verification step evidence
{
  kinds: ["targeted" | "behavior" | "integration" | "full"]
}
```

`rollback` 与 `full-rollback` 是不同义务；同时必需时必须同时存在于 `checks`。

### 3.3 Manual acceptance

在 `plugins/dev-flow/src/core/verification.ts` 增加非必填类型：

```ts
export interface ManualAcceptance {
  mode: "browser" | "user-signoff";
  source: string;
  scenarios: Array<{
    name: string;
    evidence: string;
  }>;
}
```

扩展 `runVerification`：

```ts
runVerification(
  root,
  id,
  expectedRevision,
  host,
  commandIds?,
  manualAcceptance?,
)
```

扩展 `dev_flow_verify` input schema，增加可选 `manualAcceptance`：

- `mode`、`source`、`scenarios` 必填；
- scenarios 至少一项；
- 每项 `name`、`evidence` 为非空字符串；
- 不设置 `outcome`。传入该对象即表示列出的场景已由对应方式接受；失败场景不得调用 feature-check。

`manualAcceptance` 同时写入：

- verification attempt；
- verification 成功时的 `state.steps.verification.evidence.manualAcceptance`。

它不是 FeatureState 顶层字段，也不触发 `schemaVersion` 升级。失败 attempt 可以保存本次 manualAcceptance 以供审计，但 pending verification step 不得把它表示成已经满足的验收证据。

未声明 UI/人工验收的任务省略该字段，保持原行为。

### 3.4 Verification freshness

在 status 的只读 `Progress` 增加：

```ts
export interface VerificationFreshness {
  status: "missing" | "fresh" | "stale";
  reasonCode?: "VERIFICATION_STALE";
  recoveryHint?: string;
}

interface Progress {
  // existing fields
  requiredEvidence?: RequiredEvidence;
  verificationFreshness: VerificationFreshness;
}
```

语义：

- 没有 `verifiedFingerprint` → `missing`
- fingerprint 等于当前 protected-root fingerprint → `fresh`
- fingerprint 不同 → `stale`，同时给出 `VERIFICATION_STALE` 和重新运行 verification 的提示

status/next 读取不得修改 revision 或写 invalidation event。

### 3.5 Classify 响应

`dev_flow_classify` 在现有 `{ classification, route }` 上增加：

```ts
riskRequirements: {
  checks: string[];
  verification: VerificationKind[];
}
```

这是只读兼容扩展。`dev_flow_start` 持久化状态不增加该字段。

## 4. 切片 A：安全完整性

切片 A 必须先完成并通过测试。未完成前禁止合入 light-L 分类引导。

### A1. 建立统一 evidence policy

**新增文件：**

- `plugins/dev-flow/src/policy/evidence.ts`

**导出：**

```ts
export function requiredEvidenceForStep(
  route: RouteId,
  riskLabels: RiskLabel[],
  step: string,
): RequiredEvidence;

export function missingRequiredEvidence(
  required: RequiredEvidence,
  evidence: unknown,
): RequiredEvidence;

export function requiredEvidenceIsEmpty(
  required: RequiredEvidence,
): boolean;
```

**映射规则：**

1. 基础 review 字段：
   - `plan_review` → `reviewType: "plan"`
   - `code_review` → `reviewType: "code"`
2. `full-code-review`：
   - `code_review` → `reviewDepth: "full"`
   - 可以继续存在于 `deriveRiskRequirements().checks` 的原始派生结果中，但 `requiredEvidenceForStep()` 必须消费并转换该 token；
   - 永不写入 `RequiredEvidence.checks` 或任一步骤的 `evidence.checks`。
3. `security`：
   - route 包含 `risk_controls` → `risk_controls.checks`
   - 否则 route 包含 `code_review` → `code_review.checks`
4. `rollback`、`full-rollback`：
   - route 包含 `risk_controls` → `risk_controls.checks`
   - 否则 route 包含 `rollback_safety` → `rollback_safety.checks`
   - 否则 route 包含 `rollback_unit` → `rollback_unit.checks`
5. verification：
   - step 为 `verification` 或 `feature_check`
   - 无 riskLabels → `["targeted"]`
   - 有 riskLabels → `deriveRiskRequirements(riskLabels).verification`
6. 其他步骤返回空对象：

```ts
{ fields: {}, checks: [], verificationKinds: [] }
```

`missingRequiredEvidence()` 必须：

- reviewType/reviewDepth 按字面值比较；
- checks 从 `evidence.checks` 读取；
- verificationKinds 从 `evidence.kinds` 读取；
- 非对象、字段类型错误、数组缺失均视为缺失；
- 只返回缺失项，便于错误 details 直接使用。

### A2. recordStep 首次校验

**修改：**

- `plugins/dev-flow/src/core/feature-check.ts`

在 `recordStep()` 的顺序检查和 grill 校验后：

1. 调用 `requiredEvidenceForStep(state.route, state.classification.riskLabels, step)`。
2. 计算 missing。
3. 若 `reviewType` 缺失/错误，保留错误码 `REVIEW_TYPE_MISMATCH`，details 包含完整 `requiredEvidence` 和 missing。
4. 若 reviewDepth/checks 缺失，返回 `RISK_EVIDENCE_INCOMPLETE`，details 同上。
5. 全部满足后才写 `state.steps[step]`。

删除当前分散的：

- plan/code `reviewType` 硬编码；
- `risk_controls` checks 特判；
- code-review full-depth 特判。

校验行为全部转由统一 evidence policy 决定。

### A3. featureCheck 二次校验

仍在 `feature-check.ts`：

1. 在写 `feature-checked` 前，只遍历 route orderedSteps 中位于 `feature_check` 之前的步骤。
2. 对每一步调用 `requiredEvidenceForStep()`；结果为空时直接跳过，不维护第二份硬编码 evidence 步骤名单。
3. 非空 requirement 从 `state.steps[step]?.evidence` 读取并校验。
4. verificationKinds 始终读取 `state.steps.verification?.evidence.kinds`；不得从 `steps.feature_check` 读取 evidence。
5. `requiredEvidenceForStep(..., "feature_check")` 只用于 next/status 在调用 feature-check 前展示 verification 义务；二次校验以已经完成的 verification step 为证据源，不重复校验同一义务。
6. 任一步缺失时返回：
   - reviewType 问题 → `REVIEW_TYPE_MISMATCH`
   - 其他 → `RISK_EVIDENCE_INCOMPLETE`
7. details 必须包含：

```ts
{
  step,
  requiredEvidence,
  missing,
}
```

保留 fingerprint freshness、artifact integrity、grill 和当前 step 校验。

这一步必须能拦截由旧版本 state、跨宿主接力或直接 MCP 调用留下的不完整 evidence。

### A4. 路线 helper 与正向测试

**修改：**

不再手写 reviewDepth/risk-controls 判断。加载 `policy/evidence.ts`，按当前 route/step 生成测试 evidence：

### B6. Manual acceptance

**修改：**

- `plugins/dev-flow/src/core/verification.ts`
- `plugins/dev-flow/src/mcp/server.ts`

行为：

- manualAcceptance 可选；
- runVerification 在运行命令前验证 scenarios 非空、字符串非空；

增加测试：

- browser evidence 保存；
- user-signoff evidence 保存；
- 空 scenarios 拒绝；
- 失败 attempt 保留 evidence 但不满足 verification；
- protected root 改变后重新 verify 不复用旧 manualAcceptance。

- 每个 risk label 必须能说出具体后果；
- 禁止用 `product-ux` 等领域词发明标签；
- 禁止因为“相关”堆标签；
- task Skill 必须先调用 classify，再以完全相同的分类输入调用 start；
- start 返回 FeatureState 保持不变；start 后的摘要使用此前 classify 返回的 riskRequirements 展示额外 checks/kinds；
- 不在 Skill 内重新实现或复制 `deriveRiskRequirements`；
- 范围、接口、回滚、验收均锁定且无关键分叉时优先 light；
- multi-chain 仍为 L；
- `provided-confirmed` 只是 light 候选信号，不自动改 route；
- standard 偏重时只提示现有安全 reclassify，不提 plan_bundle。

### C4. 条件化人工/UI 验收

verify Skill：

1. 从 requirements、implementation plan、boundary card、verification narrative 中读取明确验收标准。
2. UI/浏览器/交互/视觉关键词只做发现提示，不由 core 解析。
3. 无明确 UI/人工验收标准时不启动浏览器、不传 manualAcceptance。
4. 有浏览器能力：
   - 跑声明场景；
   - 失败先修复并重新验证；
   - 全部通过后传 `mode: "browser"`。
5. 无浏览器能力：
   - 告知用户未执行浏览器验收；
   - 列出场景；
   - 等待用户书面签收；
   - 后续调用传 `mode: "user-signoff"`。
6. 不得把 user-signoff 描述成 browser pass。
7. 用户签收不能替代 security/money/irreversible 等机器 evidence。
8. route 要求 `verification.md` 时同步写入人类可读叙述并 record；其他路线依靠 verification step evidence 保存。
9. protected-root stale 后重新验证时，必须重新执行浏览器场景或重新取得用户书面签收；历史 attempt 的 manualAcceptance 不得自动复用。

feature-check/finish Skills：

- UI/人工验收被明确要求但 manualAcceptance/verification narrative 缺失时停止；
- 不调用 feature-check/finalize；
- 不新增 core 关键词解析或新 gate；
- Core 只验证“已传入的 manualAcceptance 是否合法”，不得仅因缺少 manualAcceptance 拒绝 feature-check；是否需要人工/UI 验收由 Skills 根据已声明验收标准负责。

## 8. 双宿主真实回放

真实回放是发布阻断，不是可选 smoke。

切片 A 合入并通过风险矩阵后，立即执行一个不依赖新 Skills 文案的 MCP/core smoke：

1. 直接启动带 security/data/critical_correctness 的 light-L；
2. 分别验证 rollback_safety、code_review 和 verification 缺 evidence 时会被拒绝；
3. 补齐 evidence 后确认 feature-check 可通过。

这个 smoke 只提前验证切片 A 的 enforcement，不能替代下面的完整回放。完整回放 2 还覆盖切片 B 的 next/status 可发现性和切片 C 的 Skill 行为，必须等 A/B/C 完成后执行。

### 回放 1：明确批准

Claude、Codex 各自执行：

1. 启动 standard-M provided-confirmed。
2. present 前输入“确认需求”不得被追认。
3. present 后输入“确认需求”通过。
4. “确认需求，可以”被拒并显示精确回复提示。
5. implementation gate 用“批准实现”通过。
6. status replyHint 与 core 词表一致。

### 回放 2：高风险 light-L

Claude、Codex 各自执行：

1. L + multi-chain + light + security + data + external + critical_correctness。
2. rollback_safety 缺 rollback check 时拒绝。
3. code_review 缺 security/full 时拒绝。
4. next/status 提前展示所需 evidence。
5. full/integration/behavior verification kinds 满足后才能 feature-check。
6. finalize 成功。

### 回放 3：跨宿主

1. Claude start/present，Codex 用词表内批准完成。
2. Codex start/present，Claude 完成。
3. event provenance、basisHash、revision 继续有效。
4. 旧自由文案不能通过。

### 回放 4：verification 双轨

1. verify 成功；
2. 只更新 verification narrative；
3. commands 仍 fresh，feature-check 重新待办；
4. 修改 protected root；
5. status 显示 `VERIFICATION_STALE`，next=verification；
6. 重新 verify 后恢复。

### 回放 5：UI 验收

1. 使用八字合盘事实记录中的验收场景。
2. 有浏览器时保存 browser manualAcceptance。
3. 无浏览器时明确提示并走用户书面签收。
4. 不把签收描述成浏览器执行。
5. UI 验收发生在 feature-check/finalize 前。

每次回放记录宿主版本、Node 版本、route、输入、结果和失败日志。
