# Dev Flow 2.0 工作流重构设计

> 状态：已确认
> 日期：2026-08-01
> 输入：两轮真机实战反馈、`dev-flow-notes.md`、#6851 实录与本轮 grilling 决策
> 实施计划：[2026-08-01-dev-flow-2.0-implementation-plan.md](./2026-08-01-dev-flow-2.0-implementation-plan.md)
> 前置稳定性计划：[2026-08-01-second-round-issue-6851-fix-plan.md](./2026-08-01-second-round-issue-6851-fix-plan.md)

## 1. 背景与问题定义

Dev Flow 1.9.0 已能严格维护状态、Trace、Review、Checkpoint、回撤和跨宿主交接，但真实需求验证暴露出一个结构性问题：工作流更多地约束了模型的操作过程，而不是约束不可破坏的语义结果。

具体表现为：

- standard M 有 12 个顶层步骤，需求确认、计划审查、执行批准及多份资产登记形成连续停顿。
- Hook 按命令形式、路线名称和预先声明的精确路径拦截写入；等价命令也可能失败。
- `risk-minimal` 把风险与基础路线耦合，增加路线、步骤、技能、资产和测试分支。
- plan review、Trace、rollback unit、checkpoint 等有价值的严格能力以用户可见步骤出现，内部保障转化成外部摩擦。
- 任一技术错误都可能表现为流程停止；模型缺少明确的自动恢复状态。
- 模糊需求会过早进入正式分类，容易因为 `missing-or-unclear` 机械膨胀到重路线。

2.0 的目标不是放松质量要求，而是把严格性放到正确的位置：Core 约束事实、状态、证据和后果，模型在安全能力范围内自由发挥。

## 2. 产品愿景与长期不变量

### 2.1 小任务不过度治理

- 清晰的 XS/S/light M 不设置形式化人工门禁。
- 工作流成本随真实范围、拓扑、风险和不确定性增长，不随业务关键词或模型使用习惯增长。
- 没有事实依据时，不得为了“看起来安全”堆叠风险标签或升级路线。

### 2.2 高风险不能越级

- 风险不创建新路线，但风险派生的审查、验证、回滚和必要确认义务不能被 light 路线绕过。
- 降级只能在事实依据仍成立时发生；改变拓扑、风险或验收约束必须重新评估。
- 同一批准 basis 未变化时不得重复询问；出现新事实时也不得以“确认次数已用完”为由闷头执行。

### 2.3 约束语义，不约束等价操作

- Core 约束阶段、控制文件、资产合同、Trace、审查、验证、实际 diff 和批准 basis。
- 模型可以自由选择 Write、Edit、apply_patch、heredoc、宿主编辑器等等价方式。
- Hook 不因命令形式不同而拒绝语义合法的操作。
- 优先验证后置条件；只在不可恢复或会越过语义边界前拦截。

### 2.4 扩展义务，不扩展路线

- 新风险通过覆盖层增加 obligation，不增加 route、专用 step、专用 skill 或领域分支。
- 新能力通过纯策略解析器组合到阶段中，不在多个消费者里复制路线判断。
- 策略不得维护任何业务领域案例名单或关键词映射。

### 2.5 默认自治，必要时才打断

- 可自行修复且目标未变：自动修复并继续。
- 技术错误有确定恢复路径：自动 status、retry 或使用等价操作。
- 只有实质语义偏航、残余重大风险取舍、破坏性回撤或安全恢复路径耗尽时才询问用户。
- 每次询问必须给出事实、影响和推荐方案。

## 3. 范围与非目标

### 3.1 2.0 范围

- 先完成并发布 1.10.0 稳定性修复，再开始 2.0 状态机重构。
- 引入 intake、事实分级、基础路线、风险覆盖层和阶段能力模型。
- 删除 `risk-minimal` 及其全部专属运行时逻辑。
- 合并 standard M/L 的顶层步骤，嵌入 plan review、Trace、rollback 和 checkpoint。
- 将写入控制改为阶段化、语义化策略。
- 增加自动修复、偏航检测和可执行恢复提示。
- Feature State 与 contract 升级为 schema v2，并进行硬切换。

### 3.2 非目标

- 不负责生产部署、云配置、密钥轮换或外部系统操作审批。
- 不实现通用 JIT 生产操作门禁。
- 不提供 1.x feature 自动迁移、旧路线继续执行或旧状态只读兼容层。
- 不维护业务领域分类案例库。
- 不把模型内部推理方式、命令习惯或工具选择写进合同。

## 4. 总体架构

2.0 将现有“路线等于完整步骤清单”的模型拆为四层：

```text
Intake 与事实层
  objective + repository facts + decision ledger + classificationBasis
                              ↓
基础路线层
  XS / S / light M / standard M / light L / standard L
                              ↓
义务覆盖层
  risk + topology + uncertainty + project policy
  → review / verification / rollback / approval / checkpoint obligations
                              ↓
阶段能力层
  当前允许什么、完成条件是什么、什么才算偏航
```

Host adapter 只归一化工具事件、识别真实写入目标并执行 Core 的阶段判断，不再维护路线 allowlist。Skills 负责理解需求和组织内容，不得自行伪造状态、审查或验证完成。MCP/Core 仍是状态与证据事实源。

## 5. Intake、grillme 与正式分级

### 5.1 先理解，再锁定路线

用户指定使用 dev-flow 后，先创建未分级 intake feature：

```text
开始 intake
  → 读取需求、代码、文档与测试
  → 提取可核查事实
  → 有用户决策缺口时调用 grillme
  → 决策树收敛
  → 生成 classificationBasis
  → 正式分类并原子锁定基础路线
```

允许形成不持久化的初步判断以指导调查，但在理解需求前不得锁定 route。清晰需求通常在同一回合完成 intake；模糊需求可跨会话、跨宿主恢复。

### 5.2 grillme 的两种模式

`grillme` 是独立能力，不属于任何 level 或 route：

- 独立模式：用户未启动 dev-flow 时也可手动调用；默认只输出澄清摘要。
- 工作流模式：任何阶段出现真实决策缺口时调用，答案登记到 decision ledger。

提问规则：

- 提问前必须先调查仓库和已有材料。
- 能通过代码、文档、测试或工具查明的事实不得询问用户。
- 只询问必须由用户决定的边界、优先级和取舍。
- 每次解决一个有依赖关系的决策，说明已知事实、冲突、选项及推荐答案。
- 没有固定题数上限；直到决策树收敛，或用户明确合并/结束剩余问题。

工作流 decision ledger 中每个问题具有 `open | resolved | merged | dismissed` 状态。影响范围、拓扑、风险或验收的 open decision 会阻止正式分类或实现。XS/S/light 路线不因使用 grillme 被迫创建需求文档。

### 5.3 事实分级

`classificationBasis` 是内部结构化事实，不是新步骤或门禁，至少包括：

- `scopeFacts`：真实影响范围与已知边界。
- `topologyFacts`：共享契约、调用链与回滚耦合事实。
- `uncertaintyFacts`：仍需解决或已经锁定的决策。
- `riskFacts`：每个 risk label 对应的具体后果依据。
- `decisionRefs`：支撑上述结论的 decision ledger ID。

Core 校验结构、拓扑最低级别、risk label 是否有依据以及明显矛盾；事实真伪由仓库调查、独立计划审查和后续实际 diff 共同验证。禁止关键词分级、领域案例映射和无依据标签堆叠。

`execution` 在 grillme 收敛后根据事实选择：范围、接口、回滚和验收都已锁定且实现边界可由轻量阶段表达时选择 light；需要正式 Trace、独立计划审查或多个受控实现单元时选择 standard。用户最初描述是否简短、是否使用某个业务词，以及是否曾经需要 grillme，都不能单独决定 light/standard。

## 6. 基础路线与顶层阶段

| 路线 | 用户可见阶段 | 可编辑文档 |
| --- | --- | --- |
| XS | 定位 → 实现 → 验证 → 完成 | 无 |
| S | 边界 → 实现 → 验证（含自审）→ 完成 | 无 |
| light M | 轻量计划 → 实现 → 代码审查 → 验证 → 完成 | 无 |
| standard M | 需求对齐 → 实施计划 → 执行确认 → 实现 → 代码审查 → 验证 → 完成 | 《需求文档.md》《实施计划.md》 |
| light L | 实施计划 → 执行确认 → 实现 → 代码审查 → 验证 → 完成 | 《实施计划.md》 |
| standard L | 需求对齐 → 实施计划 → 执行确认 → 实现 → 代码审查 → 验证 → 完成 | 《需求文档.md》《实施计划.md》 |

内部 artifact kind 继续使用稳定英文标识 `requirements` 与 `implementation-plan`，用户可见路径固定为中文文件名并进行 Unicode NFC 归一化。

以下 1.x 顶层步骤改为阶段内部义务：

- `coverage_review`
- `rollback_unit`
- `planning`
- `feature_check`
- `rollback_safety`
- `self_review`

以下步骤直接删除：

- `risk_review`
- `risk_controls`
- `execution_approval`

`feature-check` 变成 finalize 的 Core 自动前置检查，不再要求 agent 单独推进。

## 7. 风险覆盖层

`risk-minimal` 不再存在。风险标签只派生 obligation，永不改变基础路线。

默认策略：

| 风险标签 | 审查/控制义务 | 验证义务 | 默认执行确认影响 |
| --- | --- | --- | --- |
| `security` | 安全边界审查 | behavior | 触发 |
| `data` | 数据完整性与回滚检查 | behavior/integration | 单独不触发；不可逆时须同时标记 `irreversible_consequence` |
| `money` | 幂等、对账与回滚检查 | behavior/integration | 触发 |
| `external` | 契约与失败模式检查 | integration | 单独不触发 |
| `availability` | 降级、恢复与可观测性检查 | integration | 单独不触发 |
| `critical_correctness` | full code review | full | 触发 |
| `irreversible_consequence` | full rollback + full review | full | 触发 |

L 路线默认具有执行确认义务。上述“触发”是默认策略，不是确认次数上限：如果批准后出现新的实质事实，仍可生成新的 decision；同一 basis 未变化时不得重复询问。

新增风险能力必须扩展覆盖层定义和矩阵测试，不得增加 route、专用步骤或领域 skill。

## 8. 实施计划与独立审查

`planning` 从顶层路线步骤改为“实施计划”阶段内的 Core 强制子状态：

```text
计划草稿
  → 冻结不可变计划快照
  → 创建 review batch
  → 独立角色审查
  → 汇总 findings
  → 自动修复 blocking findings
  → 受影响角色增量复审
  → 生成只读 plan-review 投影
  → 计划阶段 ready
```

角色派生：

- standard M：需求覆盖、架构与可测试性。
- light/standard L：增加回滚可操作性。
- `security`：增加安全视角。
- `data + irreversible_consequence`：增加数据不可逆视角。

`plan-review` skill 保留：既可作为 review job 的执行说明，也允许用户独立调用；它不再要求用户完成一个 route step。`plan-review.md` 保留为 Core 生成的只读投影。

Assurance 必须诚实分级：隔离视角、独立采样、宿主 agent 证明和真实模型身份验证不得混称。宿主缺少异构模型能力时可降级到隔离上下文并明确展示，不得伪称多模型。除项目策略另有要求外，不因缺少最高 assurance 卡死普通任务。

## 9. 执行确认与决策去重

standard M/L、light L 和重大风险任务通常在计划审查完成后展示一份 Execution Brief，合并呈现：

- 已确认需求与边界。
- classificationBasis 与风险依据。
- 实施计划与 Trace 摘要。
- 独立审查结果和 assurance。
- rollback/checkpoint 策略。
- 验证方案与已知残余风险。

确认不是固定配额。额外询问只允许由新的真实决策触发，例如需求/范围/拓扑/风险实质变化、多个合理业务方案、重大残余风险接受或破坏性回撤。

每个用户决策具有稳定 `decisionId` 与 `basisHash`：

- 同一 basis 不得重复询问。
- 相关决策尽量合并展示。
- 技术错误、命令差异、普通 finding、同范围补充文件和可自动修复验证失败不得生成用户确认。

## 10. 自动自适应 checkpoint

保留“手术刀式回撤”的产品价值，但取消写前精确 `fileScope` 管制。

### 10.1 路线策略

- XS/S：首次实现写入前自动保存单一安全基线，不拆多个 RU。
- light M：默认一个实现单元；复杂度显著增长时触发偏航检查。
- standard M：按可验证行为切片生成多个自动 checkpoint 单元。
- light/standard L：按多链/回滚边界生成多个自动 checkpoint 单元。
- `coordinated-rollback`、`irreversible_consequence` 或项目显式策略：启用更严格的回撤验证。

### 10.2 单元生命周期

```text
自动捕获单元前置快照
  → 模型自由完成一个可验证行为切片
  → 计算实际变更集
  → 检查语义偏航
  → 运行单元定向验证
  → 通过后封存 checkpoint
  → 自动进入下一单元
```

`fileScope` 降级为预期范围。实现期间普通写入不因漏列文件立即失败；Core 在单元边界比较计划范围与实际 diff。测试与对应修复必须组成可独立通过的行为切片，避免红测试单元阻塞后续修复。

### 10.3 验证失败与修复循环

验证失败不自动丢弃当前单元，也不立即打断用户：

- 保持当前 RU active，进入 `repairing`。
- 在已确认目标内自动诊断、修改并重跑定向验证。
- 失败集合缩小、错误签名变化或产生有效新证据视为有进展。
- 相同失败签名且无实质变化连续两次判定 stalled。
- 单个 RU 默认最多自动修复 5 轮，项目配置可调整。
- stalled、达到上限、出现实质偏航或需要丢弃工作时才询问用户。

回撤当前单元会丢弃工作区内容，因此必须有明确用户决定；回撤事务内部的失败补偿仍由 Core 自动执行以保证原子性。

## 11. 阶段能力与写入策略

`dev_flow_next` 从“唯一动作调度器”改为“阶段能力与完成条件说明器”，返回：

- 当前 stage/activity。
- 允许的操作类别。
- 完成条件。
- 当前自动恢复动作。
- 真正阻止推进的 blocker。
- 是否需要用户注意。

写入策略：

- `.dev-flow` 控制文件始终禁止直接修改。
- intake、需求和计划阶段的源码写入属于流程偏航；合法工作流资产和 `scratch/` 放行。
- implementation 阶段普通源码写入直接放行，单元结束时审计实际 diff。
- review/verification 的明确修复自动回到当前实现单元，不重新走整条路线。
- logic-complete 前继续禁止 Git 写入，保护 checkpoint 与交付快照一致性。
- Host adapter 调用统一的 Core write decision，不复制 route allowlist。

复杂 Shell 命令只有在真实影响无法界定且可能越过当前语义边界时才能阻止；错误必须明确为“影响范围无法确定”，并提供等价操作。heredoc、`/dev/null` 等常见安全形式必须正确支持。

## 12. 自动恢复、状态与错误合同

StatusView 增加统一 activity：

- `running`：正常推进。
- `repairing`：当前单元自动修复。
- `waiting-user`：存在真实用户决策。
- `blocked-system`：工具/环境阻塞且安全恢复路径已耗尽。

只有 `waiting-user` 与 `blocked-system` 可以中断用户。所有可恢复错误必须返回结构化恢复动作，例如：

- `retry`：携带当前 revision 和幂等 key。
- `refresh-status`：状态冲突后重新读取。
- `use-equivalent-operation`：命令无法解析时提供语义等价路径。
- `repair-current-unit`：验证或 finding 的自动修复上下文。
- `reclassify`：事实变化导致基础路线不再成立。

失败 mutation 必须保持原子性：不得关闭步骤、消费用户证据或留下半提交状态。Skills 不得在遇到普通错误后笼统停止，而应按 recovery action 继续。

## 13. 实质偏航定义

只有以下变化会阻止进入下一实现单元并可能请求用户决策：

- 改变已确认需求或验收标准。
- 进入明确的 out-of-scope 范围。
- 改变共享契约、调用链或回滚拓扑。
- 新增或移除有事实依据的风险。
- 实际变更使当前路线最低级别不再成立。
- 无法继续满足既定回滚或验证策略。

同模块补充文件、调整内部结构、增加测试、修复审查 finding 和其他不改变 classificationBasis 的实现差异只记录，不打断用户或使批准失效。

Core 可强制结构与路径事实；语义偏航由实际 diff 摘要、classificationBasis、计划审查与模型判断共同给出。系统不得把无法机器证明的语义判断描述成绝对强制保证。

## 14. State v2 与硬切换

Feature State 使用 discriminated union：

- `IntakeFeatureStateV2`：无 route，保存 objective、调查摘要、decision ledger。
- `RoutedFeatureStateV2`：保存 classificationBasis、基础路线、派生 obligations、stage state、approval basis、review/trace/checkpoint 指针。

`schemaVersion` 升至 2。contract 同步升至 schema v2。项目配置若结构未变化可保持独立版本，但必须记录兼容的 feature schema 范围。

由于目前没有外部项目依赖，2.0 采用硬切换：

- 1.10.0 doctor 在升级前报告所有未完成 1.x feature，要求先完成或放弃。
- 2.0 读取 `schemaVersion: 1` 时只返回 `LEGACY_STATE_UNSUPPORTED`。
- 不解析旧 route、不生成旧状态视图、不允许旧 feature mutation。
- 测试项目清理 `.dev-flow/` 后重新初始化。
- 不提供自动迁移或兼容执行器。

## 15. `risk-minimal` 删除边界

2.0 删除：

- `RouteId`、contract route 和 selectRoute 分支。
- `risk_review`、`risk_controls` 和 `risk-card`。
- `risk-review` 专用 skill。
- 路线专属 gate、status、artifact invalidation 和 evidence placement 判断。
- 三条 risk-minimal E2E 及所有专属 fixture/断言。
- README、routes、architecture 中作为现行路线的说明。

保留并重构：

- RiskLabel 与事实依据。
- 风险派生审查角色、verification kinds、rollback 和 approval obligations。
- 风险证据在 record、feature-check/finalize 的双重校验。

运行时源代码与现行 skill/route 文档不得再出现 `risk-minimal`；历史计划或 changelog 可保留说明。

## 16. 验收标准

- 1.10.0 先完成两轮稳定性修复并通过真机验证。
- 清晰 XS/S/light M 不出现形式化人工门禁。
- standard M、light/standard L 默认合并执行确认；每个额外确认都有新的 decision/basis 和事实依据。
- 同一 basis 不重复询问。
- plan review、checkpoint、普通验证修复不打断用户。
- 实现阶段常规等价写操作无误拦。
- 高风险 obligation 无法通过选择 light 或更换 route 绕过。
- `risk-minimal` 及专属资产/技能/测试从运行时完全删除。
- 无需求文档的路线仍通过 decision ledger 保证关键需求与边界已收敛。
- 自动 checkpoint 能恢复当前单元，失败验证不会自动丢弃工作。
- 偏航提示包含事实、影响、受影响 basis 和推荐方案。
- 失败 mutation 原子、可重试、不会把 feature 留在不可恢复的半状态。
- unit、route、interop、cross-host、host E2E、build check 全部通过。
- 至少完成一次 M 和一次 L 的真实需求验证，并记录用户打断次数、误拦次数和自动恢复结果。
