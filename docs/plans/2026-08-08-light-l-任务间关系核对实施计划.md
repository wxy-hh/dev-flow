# light L 补"任务间关系核对"——真校验接入

日期：2026-08-08

## Context

light L 路线在计划阶段缺少"任务间关系核对"。动机链条：

- plan 技能（`skills/plan/SKILL.md`）已完整覆盖**单任务**质量：每个任务必须可独立验证、说明范围/验收/验证/可恢复策略。全套多视角审查批次在 light 上加边际收益小。
- 但 plan 技能管不到**任务之间**的关系——回滚次序、依赖闭合。这是 light L（多链拓扑）最贵的错误源，也是唯一没有下游网兜底的错误（其他错误会被实现 drift / 代码审查 / verification 阶段兜住，回滚次序错只在事故现场暴露）。
- 明确选择：**真校验，接入点清晰**——不是再勾一个 check 字样（那和现有 `rollback-strategy` 同级别），而是让 Core 在计划登记时真实解析并硬拦。

**边界约束（必须遵守）**：不改 light/standard 判定规则；不引入需求文档、trace 图、多角色审查批次；light L 保持轻量，只是计划证据从"字符串存在"升级为"结构有效"。

## 现状（探索已核实）

- light L 计划走 **`recordArtifact`**（非 trace 路径，`core/artifacts.ts:167`），不是 `recordArtifactWithTrace`（trace 强制路线才用）。
- light L 计划证据目前只有 `{ reviewType: "plan", checks: ["rollback-strategy"] }`，`missingRequiredEvidence` 只做字符串存在检查（`policy/evidence.ts:103-106`），**不读计划内容**。
- `parseTraceSourceBlocks`（`core/traceability-anchors.ts:39`）已能从 Markdown 解析出全部 `TASK-xxx`/`RU-xxx` 锚点及对应源码块（`TraceSourceBlock` 含 `id`、`kind`、`sourceBlockSha256`）——这是校验器解析计划结构的现成基础。
- light L 计划模板（`core/artifact-templates.ts:27-35`）目前**只渲染 TASK 锚点 + `rollback_unit` 字段，不渲染 RU 定义块**（RU 块仅 standard-m/l 有）。→ 模板必须先补 RU 块，否则没有可校验的图结构。
- 测试辅助 `tests/helpers/trace-fixtures.mjs` 已存在 TASK↔RU 配对、`dependsOn` 字段的形状，可对齐。

## 设计

**核心思路**：light L 计划中，每个任务必须声明其回撤单元（`rollback_unit`），每个 RU 必须声明 `depends_on`。Core 在计划登记时解析这份结构，校验：任务↔RU 双射完整、depends_on 目标存在、依赖图无环（即回滚次序可确定）。通过才允许登记，失败抛错。这是"轻量但真实"的结构校验——比 standard 的三角色批次轻得多，但比字符串存在检查硬得多。

### 改动清单

1. **模板补 RU 块** — `plugins/dev-flow/src/core/artifact-templates.ts` 的 `implementationPlanTemplate`：
   - 将 RU 块渲染条件从 `["standard-m", "standard-l"]` 扩为 `["standard-m", "standard-l", "light-l"]`（RU 块本身字段不变：`tasks`、`depends_on`、`covers` 等；对 light L 只要求有结构，标准字段照旧渲染）。
   - 这样 scaffold 出来的 light L 计划天然带 `TASK-001 → RU-001`、`RU-001.depends_on = []` 的合法结构，现有 e2e（`v2-standard-routes.test.mjs` 的 light-l 流程、`light-l-risk-overlay.test.mjs`）无需改 fixture 也能过——它们经 `materializeScaffold` → `recordArtifact` 登记模板渲染的计划。

2. **新增纯函数校验器** — 新建 `plugins/dev-flow/src/core/plan-graph.ts`（纯逻辑，无 I/O）：
   - `export function validatePlanTaskGraph(markdown: string): string[]`：
     - 复用 `parseTraceSourceBlocks` 解析锚点，从每个 `TASK`/`RU` 源码块内提取 `rollback_unit`、`depends_on`、`tasks` 字段（用现有模板的 `- key: [..]` 行格式解析）。
     - 校验并返回错误数组（空 = 通过）：
       - 每个 TASK 的 `rollback_unit` 指向已定义的 RU
       - 每个 RU 的 `tasks` 反向包含引用它的 TASK（双向一致）
       - 每个 RU 的 `depends_on` 目标都已定义
       - 依赖图无环（DFS，可参照 `core/traceability.ts` 的 `assertRollbackDag` 思路，但独立实现、不依赖 ledger）
   - 复用 `policy/traceability.ts` 的 `RollbackNode` 类型形状（`tasks`、`dependsOn`），避免另造类型。

3. **登记时硬拦** — `plugins/dev-flow/src/core/artifacts.ts` 的 `recordArtifact`（:167）：
   - 在 `kind === "implementation-plan" && state.route === "light-l"` 时，读取 `contents` 后调用 `validatePlanTaskGraph`；若返回非空错误，抛 `DevFlowError("PLAN_TASK_GRAPH_INVALID", ...)`，阻止 CAS 提交，计划保持旧 hash。
   - 保持纯 `recordArtifact` 路径不动 standard 的 trace 流程。

4. **证据校验对齐** — `plugins/dev-flow/src/policy/evidence.ts` 的 `missingRequiredEvidence`：
   - 不改 `reviewType`/`checks` 语义（`rollback-strategy` 字符串保留，兼容 light-l/standard-l 共用义务满足机制），结构校验由 `recordArtifact` 层负责，证据层不重复。
   - 可选：`checks` 里补 `"inter-task-graph"` 作为显式义务字样，但**不依赖它做真校验**——真校验在登记层。此项是否加由实现时权衡，非必需。

5. **计划技能提示** — `plugins/dev-flow/skills/plan/SKILL.md` 第 12 行补充一句：light L 计划的任务必须声明 `rollback_unit`，RU 必须声明 `depends_on`，并检查依赖闭合与回滚次序（成环或悬空引用会导致登记被拒）。

### 测试改动

- **新增** `tests/unit/plan-graph.test.mjs`：覆盖——合法图通过；TASK 引用不存在 RU 失败；RU.tasks 不包含引用它的 TASK 失败；depends_on 悬空失败；成环失败；多 RU 链合法通过。
- **回归**：现有 `v2-standard-routes.test.mjs`（light-l 流程走 `recordArtifact` 登记模板计划）、`light-l-risk-overlay.test.mjs`、`v2-risk-obligations.test.mjs`（evidence 断言不变）应继续通过——模板补 RU 块后这些流程天然合法。

## 验证

```bash
node --test tests/unit/plan-graph.test.mjs   # 新校验器
npm run test:unit                            # 证据/义务断言不回归
npm run test:routes                          # light-l e2e 仍能走通
npm run typecheck                            # 严格 TS
```

不跑 `npm run build`（中间改动，除非最后需要统一更新 dist）。

## 不做

- 不改 light/standard 判定、不踢 coordinated-rollback 出 light
- 不引入需求文档、trace 图、多角色审查批次
- 不把代码图谱(codegraph)作为流程依赖（用户项目无法保证装有；只作可选增强）
