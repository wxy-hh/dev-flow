## 1. 背景与痛点

当前修复一个真实项目反馈的 bug，完整链路是：

1. 用户口述症状，维护者靠猜或让用户翻 `.dev-flow/` 手动打包现场；
2. 手写一个场景测试复现（8-16 那轮的 scene B/E/F 全部是手写，见 `tests/e2e/routes/v6-real-project-flow.test.mjs:250/321/416`）；
3. 修完后手动跑测试；
4. 改版本号 → `npm run version:sync` → `npm run build` → 提交 dist → push/tag → 发 marketplace；
5. 在真实项目里重装插件，人工再走一遍流程验证。

痛点集中在三处：

- **现场丢失**：真实项目里出问题时，没有任何机制记录「刚才那次失败的调用是什么」，事后无法确定性还原。
- **复现靠手写**：每个 bug 的复现测试都是一次性手工工程，格式不统一，也无法从现场直接生成。
- **真机验证断档**：`test:host-e2e`（真实 CLI 安装/升级）不在 `npm test` 也不在 CI 默认链路；装上之后的真实 agent 行为完全没有自动化验证，只有 `docs/publishing.md:17` 口头要求的人工回放记录（连模板文件都没有）。

## 4. 总体设计

```
真实项目出 bug
  │
  ├─ [运行时自动] .dev-flow/incidents.jsonl 记下失败调用          ── Phase 1
  │
  ├─ node scripts/capture-incident.mjs <项目>                     ── Phase 2
  │    └─ incidents/<ts>-<featureId>/（本地，gitignore）
  │         ├─ manifest.json
  │         └─ dev-flow/（.dev-flow 脱敏快照）
  │
  ├─ node scripts/repro-from-incident.mjs incidents/<id> --name <slug> --approve
  │    └─ tests/e2e/incidents/<slug>.test.mjs + fixtures/         ── Phase 3
  │         （npm run test:e2e 自动发现，即回归）
  │
  ├─ node scripts/fix-loop.mjs tests/e2e/incidents/<slug>.test.mjs [--patch f.patch | --agent-cmd "..."]
  │    └─ .scratch/fix-loop/<ts>/ git worktree 沙箱               ── Phase 4
  │         红确认 → 修复 → 绿确认 → 全套件 → report.json
  │
  ├─ 用户审核 diff、手动提交（agent 不碰 git）
  │
  └─ 发版前 npm run canary                                        ── Phase 5
       check-build 新鲜度闸门 → 真实 claude CLI 从临时 marketplace
       安装当前 dist → claude -p headless 跑最小旅程 → 断言账本副作用
```

设计原则：

- **单数据源**：复现的输入就是 `incidents.jsonl` 里的失败调用 + `.dev-flow` 状态快照，不发明第二套录制格式。
- **快照重放而非全程重放**：恢复到出事时刻的状态，重放那一次失败调用。覆盖绝大多数真实 bug（状态损坏、闸门误判、错误处理缺陷），且实现量远小于全旅程重放。
- **一切本地**：无遥测、无上传；入库前必须经 `--approve` 人工闸门。
- **回归零接线**：生成的测试直接落在 runner 递归发现的目录里。

## 5. Phase 1：运行时失败记账

### 5.1 新文件 `plugins/dev-flow/src/core/incident-journal.ts`

仿 `host-health.ts` 的 jsonl 追加模式，并加有界旋转。对外只暴露一个函数：

```ts
export interface IncidentEntry {
  at: string;                       // ISO 时间戳
  kind: "mcp-error" | "hook-block" | "hook-error";
  host: "claude" | "codex" | null;  // MCP 侧无法确知宿主时为 null
  name: string;                     // MCP 工具名或 hook 事件名（如 "PreToolUse"）
  code: string | null;              // DevFlowFailure.code 或 write-gate block code
  cause: string | null;             // failureFrom(error).cause（已归一的安全文本）；hook-block 为 block 原因摘要
  featureId: string | null;         // 见 §5.2 提取规则
  revision: number | null;
  payload: Record<string, unknown>; // 结构化重放输入：mcp-error=原样 args；hook-*={ hook_event_name, tool_name, tool_input }
  payloadTruncated: boolean;        // 由 recordIncident 截断时回填，调用方不传
  detail: string;                   // 人类可读单行摘要（≤500 字符），仅供阅读，不参与重放
  pluginVersion: string;            // __DEV_FLOW_VERSION__，source 测试环境 fallback "dev"
}

export async function recordIncident(root: string, entry: IncidentEntry): Promise<void>;
```

**截断规则（重放可靠性的根基）**：对 `payload` 做深遍历，**逐个字符串值**超过 2000 字符才截断并回填 `payloadTruncated: true`；对象结构本身始终保持合法 JSON。绝不截断序列化整体——否则 replay 端 `JSON.parse` 会必坏（初稿缺陷，本轮修复）。

行为契约：

- 追加写 `<root>/.dev-flow/incidents.jsonl`。
- **有界旋转**：写入前若已有 ≥200 行，读全文件 → 保留最新 199 行 + 新行 → tmp 文件 + rename 原子重写（沿用 state-store 的写盘范式）。
- **旋转失败回退**：旋转任一环节失败（读盘失败、rename 失败等）→ 回退为纯 append；append 也失败 → 静默放弃。**任何路径下不抛异常、不损坏原文件。**
- `.dev-flow/` 不存在（项目未初始化）时**静默跳过**。
- 内部全 try/catch，**承诺永不 reject**——调用方直接 `await`，不需要再包。
- `detail` 只做人类可读摘要；重放一律走结构化 `payload`，两通道职责分离。

### 5.2 改 `plugins/dev-flow/src/mcp/dispatch.ts`（:665）

包装而非入侵函数体：

```ts
// 原 dispatch 改名为 dispatchTool（不导出），函数体一行不动
export async function dispatch(root: string, name: string, a: any, ports: DispatchPorts) {
  try {
    return await dispatchTool(root, name, a, ports);
  } catch (error) {
    const failure = failureFrom(error);
    // 直接读 details：featureId 不在 safeFailureDetails 白名单（errors.ts:30-35），
    // 走 failure.technical 会被过滤掉；journal 是纯本地数据，无泄露顾虑。
    const details = error instanceof DevFlowError ? error.details : {};
    await recordIncident(root, {
      at: new Date().toISOString(),
      kind: "mcp-error",
      host: null,
      name,
      code: failure.code,
      cause: failure.cause,
      featureId: typeof details.featureId === "string" ? details.featureId : null,
      revision: typeof details.expectedRevision === "number" ? details.expectedRevision
        : typeof details.currentRevision === "number" ? details.currentRevision : null,
      payload: (a ?? {}) as Record<string, unknown>,
      detail: `${name} 失败:${failure.cause}`,
      pluginVersion: currentPluginVersion(),
    });
    throw error; // 原样重抛，server.ts 的 failure() 行为不变
  }
}
```

注意点：`failureFrom` 对未知错误归一为 `INTERNAL_ERROR`，记账用归一后的 code/cause，不泄露内部堆栈到 journal。

### 5.3 改 `plugins/dev-flow/src/hosts/hook-adapter.ts`（3 处，全部 fire-and-forget）

1. `:93-94` PreToolUse block 写出后，记 `hook-block`：`code` = block code，`cause` = block 原因摘要，`payload = { hook_event_name, tool_name, tool_input }` **完整保留 tool_input**。
   - 保真度理由（评审问题 6）：`evaluatePreToolUse` 的判定依赖完整 `tool_input`——git 命令分类（`adapter-policy.ts:101-104`）、写目标分析（`analyzeBashWriteTargets(command)`，`:118`）。只存「tool+路径」会让 GIT_GUARD 类事故重放时走进 allow 分支，红确认假阴性。
2. `:84-87` PermissionRequest catch、`:100-103` PreToolUse catch、`:109-112` SubagentStop catch 内，记 `hook-error`（`detail` = `String(error)` 截断，`code = null`，`payload` 存原事件的安全子集）。

约束：不改变任何现有分支的输出与控制流；记账失败被 `recordIncident` 自身吞掉。

### 5.4 性能与并发考量

- PreToolUse 每次工具调用都触发，但**只在 block/异常时写盘**（allow 路径不记），正常开发几乎零开销。
- 记账是单行 append；旋转只在 ≥200 行时发生，且失败有回退，代价有界。
- 多进程并发追加 jsonl 存在交错风险，与 `host-health.jsonl` 现状一致，接受（记账是诊断数据，不是合同状态）。

## 8. Phase 4：编排式修复环 `scripts/fix-loop.mjs`

### 8.1 CLI

```bash
node scripts/fix-loop.mjs tests/e2e/incidents/stale-trace-gate.test.mjs \
  [--patch fix.patch | --agent-cmd "kimi -p \"$(cat brief.md)\""] \
  [--verify "npm run typecheck && npm run test:unit && npm run test:routes"] \
  [--timeout-min 30]
```

- `--patch`：直接 `git apply` 一个现成补丁。
- `--agent-cmd`：在沙箱内执行任意外部修复命令（先把事故摘要写成 `brief.md` 供其读取）。命令内容完全由用户决定，harness 不内置任何 AI 调用。
- `--verify`：绿确认后要跑的回归套件，默认 `npm run typecheck && npm run test:unit && npm run test:routes`。
- 二者都不给：只做红确认 + 环境就绪检查，然后停在「等待人工在沙箱里修」。

**安全声明（评审问题 8 采纳）**：`--agent-cmd` 是**以执行者本人身份运行的任意 shell 命令**，与手动在终端敲命令等价。harness 不做 GIT_DIR 级隔离——那会破坏 worktree 自身的 git 元数据解析，反而让沙箱不可用。真正的边界是：文件改动限制在 worktree 内 + 永不 commit/push + 人工审 diff 后才合入 + brief 写明边界约束 + 超时熔断。

### 8.2 状态机与裁决矩阵

```
INIT → SANDBOX（git worktree prune → git worktree add --detach + node_modules）
     → RED_CONFIRM（沙箱内跑目标测试，必须失败）
     → FIX（apply patch / exec agent-cmd / 人工）
     → GREEN_CONFIRM（重跑目标测试，必须绿）
     → REGRESSION（跑 --verify 套件）
     → REPORT
```

| 条件 | 裁决 | 退出码 |
|---|---|---|
| 红确认阶段测试通过 | NOT_REPRODUCED（修了个寂寞或已修复；若 incident `payloadTruncated=true` 需人工复核重放可信度） | 2 |
| patch 应用失败 / agent-cmd 非零 | PATCH_FAILED | 3 |
| 修复后复现测试仍红 | FIX_INEFFECTIVE | 4 |
| 复现绿但回归套件红 | REGRESSED | 5 |
| 全绿 | FIXED | 0 |

### 8.3 实现要点

- 沙箱：先 `git worktree prune` 清理 crash 残留的 worktree 元数据（评审问题 7 采纳为一次性加固），再 `git worktree add --detach .scratch/fix-loop/<ts>/ HEAD`——`--detach` 不建分支，分支冲突面不存在。
- node_modules：把主仓 `node_modules` symlink 进沙箱（typecheck/单测依赖 esbuild+typescript，不重复装）。**实施第一步先做 30 秒冒烟验证**（symlink 后在沙箱跑 `npm run typecheck`，评审问题 9 采纳为验证步骤）；若个别工具链对 symlink 敏感，回退 `npm ci --prefer-offline`。
- 红/绿确认命令：`node --test --test-timeout=300000 <目标测试>`，环境与 `run-tests-silently.mjs` 一致（`DEV_FLOW_DISABLE_ATTENTION=1`、`NODE_ENV=test`）。
- `brief.md` 内容：incident manifest 摘要、复现测试路径、红阶段的失败输出全文、边界约束（不改测试、不改 dist、遵守 AGENTS.md、不执行任何 git 变更）。
- 报告：`.scratch/fix-loop/<ts>/report.json`——`{ verdict, reproTest, redOutputTail, greenOutputTail, verifyOk, diffstat, wallClockMs }`；控制台同步打印，FIXED 时提示 `git -C .scratch/fix-loop/<ts> diff` 去审核。
- **纪律**：永不 `git commit`、永不碰主工作区；结束时保留沙箱供审核，加 `--clean` 才删除（`git worktree remove --force`）。
- 超时：agent-cmd 默认 30 分钟上限（可 `--timeout-min` 调），防止失控。

### 8.4 可测性

命令执行器（spawn）与「当前时间」依赖注入。`tests/unit/fix-loop.test.mjs` 用假 runner 覆盖：五种裁决路径、patch 失败、worktree 创建失败时的清理，**不真跑套件**（秒级完成）。

### 9.2 已知风险与对策（评审时重点关注）
