## 1. 启动时对预存脏文件的全量归属提问造成交互摩擦

### 现状问题

`startFeature`（`plugins/dev-flow/src/core/state-store.ts:962`）在启动时对全部 in-scope 预存脏文件立即呈现 workspace-ownership 交互（"路径 X 是否属于当前任务？"），要求用户在任务开始前逐项表态：

- 真实开发中，用户不会为了使用 dev-flow 而刻意先提交一次代码，预存脏文件是常态；每个任务开始都被问一次，属于不必要的交互摩擦；
- 关键缺陷：任务真正会写到的文件会被 host hook 自动归属（`recordTrustedWriteOwnership` → `ownership = "feature"`，`state-store.ts:806`），启动时那一次提问覆盖的文件，大概率是任务**根本不会碰**的；
- 因此启动提问是"全量问 + 大部分多余"：任务不会碰的文件被问一次，任务会碰的文件问的也不是必需时刻；
- 更糟的是启动只呈现不强制，真正强制点在关键推进门禁（`assertWorkspaceOwnershipComplete`，`state-store.ts:733`，要求**所有 unowned 路径**都解决）——脏文件多的仓库，用户在启动、implementation unit begin、checkpoint、finalize 可能被同一批路径反复打扰。

### 优化原因

- 摩擦的根因是"提问时机早于信息到达"：启动时无法判断哪些预存脏文件与任务相关，此时问是纯摩擦；
- 信息量最高、最不可省的提问时机是**任务第一次真正写入某个预存脏文件时**——此时 `startedDirty` 信号仍在，hook 正要把它覆盖为 `feature`，是唯一能拦住"预存改动静默并入交付"的时刻；
- 未被触碰的预存脏文件默认排除即可，不需要任何用户表态。

### 涉及的阶段与时机

- **启动**（`dev_flow_start` 的 ownership 呈现）：移除全量归属提问，改为非阻塞提示（可选）；
- **实现阶段**（`recordTrustedWriteOwnership` 写入前）：新增懒触发定向提问——任务首次写入预存脏文件时确认；
- **关键推进门禁**（`assertWorkspaceOwnershipComplete`）：放宽为只对"被任务触碰过的预存脏文件"要求归属；
- **finalize 交付快照**（`createDeliverySnapshot`，`delivery-snapshot.ts`）：保留 `DELIVERY_FILE_PREEXISTING_DIRTY` 兜底，但收窄为只检查真正交付的文件。

### 优化方向

1. **启动不弹归属问题**：基线（`startedDirty` + 内容 sha256 + `baseHead`）静默记录，不强制用户表态；
2. **懒触发定向提问**：任务第一次写入预存脏文件时，由 hook 弹一次"此文件启动前已有改动，这些预存改动将计入本次交付，确认？"——只在相关时刻问，且只问相关文件；
3. **未被触碰的预存脏文件默认排除**：不进 feature-owned、不进 patch、不阻塞任何门禁；仅当用户主动 `git add/commit` 它们时，git 门禁（`adapter-policy.ts` 的 `DEV_FLOW_GIT_GUARD`）在命令时刻提示；
4. **finalize 兜底收窄**：`DELIVERY_FILE_PREEXISTING_DIRTY` 只检查被交付的 feature-owned 文件，作为懒触发漏网时的最后防线；
5. **可选**：启动时用非阻塞提示替代阻塞提问（"检测到 N 个预存改动，任务未触碰将默认排除；若任务会修改将另行确认"），给用户预期但不强制表态。

### 关键发现（支撑理由）

- **finalize 不能替代懒触发**：`recordTrustedWriteOwnership`（`state-store.ts:806`）对任务写过的 governed 文件**无条件**标记 `ownership = "feature"`；而 `DELIVERY_FILE_PREEXISTING_DIRTY` 的判断条件是 `initialDirty ∩ ownership !== "feature"`。任务写过的预存脏文件 ownership 已是 `"feature"`，守卫条件不成立，信号已被 hook 自动归属覆盖——最需要问的类别（预存改动 + 任务真的改了）在 finalize 时已不可检测，必须靠写入时刻的懒触发拦截。这也是"只保留 finalize 那一次提问"不可行的直接原因。

## 2. 任务输入文件被问归属：真实会话把"启动提问错位"坐实

### 现状问题

真实使用会话（`/dev-flow:task @docs/architecture-review-destiny-2026-08-12.md 这是架构审查出来的问题，全部解决一下`）中，第一个待决问题就是：

> ▎ 路径 `docs/architecture-review-destiny-2026-08-12.md` 是否属于当前任务？

用户用 `@` 引用的文件正是**任务的输入与全部依据**（模型自己都判定 "it does, that's the whole basis"），dev-flow 却问它是否属于当前任务。根因链条：

- 该文件是**未跟踪（untracked）** 的（刚生成的审查文档），`captureWorkspaceLineage` 必然把它记进 `startedDirty`（`git-reconciliation.ts:122`）；
- `ownershipForScope` 只自动排除 `scope.outOfScope` 里的路径（`git-reconciliation.ts:222`），而 `dev_flow_start` 此刻 scope 为空；
- 于是它落入 `unknownOwnershipPaths` → 启动时 `presentWorkspaceOwnership`（`state-store.ts:962`）立即弹出。

**设计上没有"任务输入文件自动 in-scope"这一说。** 而 untracked 文件恰是真实使用里的常态（刚写的文档、刚生成的报告），所以几乎每个任务开篇都会被问一次这种"明显到荒谬"的问题。

### 优化原因

- 任务输入是 in-scope 的**最强证据**：用户显式引用即声明归属，无需用户再确认；
- 启动提问错位（第 1 条）在真实会话中得到实证——不是理论摩擦，而是把任务依据文件当未知路径问；
- 修掉它同时缩小第 1 条里"全量问"的范围：任务输入类路径自动排除在未知归属之外。

### 涉及的阶段与时机

- **启动**（`dev_flow_start` 的 `scope` 校验与 `ownershipForScope` 调用处）：任务输入文件注入 in-scope；
- **分类**（`dev_flow_classify` 的 classificationBasis）：`changeSurface` 等字段已隐含任务输入，应与之对齐。

### 优化方向

- `dev_flow_start` 增加"任务输入文件"语义：将 `@` 引用/显式传入的文件自动纳入 `scope.inScope`，不落入未知归属；
- 或在 `ownershipForScope` 前将任务输入路径直接标记 `ownership = "feature"`（来源 `task-input`），不触发归属交互；
- 技能层对齐：task SKILL 的取证阶段把任务输入文件列为 in-scope 依据，避免与 Core 判定脱节。

## 3. 归属回答的匹配与绑定机制脆弱：一个归属问题 3 轮用户往返

### 现状问题

同一个真实会话中，一个归属问题走了 4 次 `dev_flow_answer`、3 条用户消息才通过。拆开是三处叠加：

- **模型"自答"被防伪机制拦截**：模型直接拿自己的转述调 `dev_flow_answer`，被 `INTERACTION_PROVENANCE_UNAVAILABLE`（`interaction-provenance.ts:106`）拦下——呈现点是工具自动生成的，之后没有真实用户消息可绑定。防御方向正确，但技能没有教模型"归属问题必须等用户真答"，白烧一轮；
- **用户自然语言"确认"不被识别**：`matchNaturalDecision` 的 `confirmationTerms`（"确认""同意"…）只匹配 `id === "confirm" || "accept"` 的选项（`decision-language.ts:88-92`）；而 workspace-ownership 的选项 id 是 `adopt`/`exclude`（`ownership-workflow.ts:52-59`）。用户打"确认"直接 `DECISION_REPLY_NOT_RECOGNIZED`，必须精确复述完整标签"纳入当前任务"。单一待决问题上下文里，"确认"本该唯一指向确认，此处过度严格；
- **失败后事件消费状态让下一轮更难绑定**："The earlier '确认' was consumed by the failed attempt, so there's no fresh message to bind"——上一轮尝试消耗事件状态后，下一轮模型再想绑定新消息更困难，形成"再答一次"的负向循环。

### 优化原因

- 归属交互是**低频但必须发生**的用户接触点，3 轮往返的成本在"开始新任务"这个高频入口被放大；
- 匹配与绑定是纯机制问题，与第 1/2 条的"该不该问"正交：即使保留归属交互，也不该让用户答三次；
- 失败路径的状态越滚越乱（事件消费、revision 前移）说明交互重试缺少"回到干净起点"的语义。

### 涉及的阶段与时机

- **回答匹配**（`matchNaturalDecision`，`decision-language.ts`）：确认短语的作用域；
- **回答绑定**（`resolvePromptEvent` / `resolveInteractionPromptEvent`，`interaction-provenance.ts`）：失败后的消费状态与重试锚点；
- **技能层**（task/grillme SKILL）：模型不得自答待决问题，必须等用户真实回复。

### 优化方向

1. **确认短语放宽**：单一待决问题上下文下，无 `confirm`/`accept` 选项的交互若存在唯一可确认选项（如只有一个非排除选项），允许 `confirmationTerms` 命中该选项；或为 workspace-ownership 的 `adopt` 补充 `include` 别名与确认短语映射；
2. **失败即重锚**：`resolvePromptEvent` 失败时显式重置交互的呈现锚点（重新 `presentedRevision`/`presentedAt`），使下一轮用户消息可绑定，而不是继承上轮已消费的状态；
3. **技能强制**：待决问题只能由用户真实回复解析，模型不得用转述自答；失败时只呈现一次问题并等待新用户消息。

## 4. 启动失败场景的状态可见性差：模型反复 doctor / 重建

### 现状问题

同一个真实会话中，归属问题连续失败后，模型输出：**"The feature seems gone now. Let me re-check with doctor" → "No active feature now — the earlier one is gone. I'll create a fresh intake"**。模型分不清 feature 到底建没建、是否 active，只能靠 doctor 和重建探测状态，把一次普通启动拖成多次往返。

完整会话进一步补充两条证据：

- **用户拒绝回答后 feature 消失**：第一次 `/dev-flow:task` 时存在旧 active feature `qimen-sse-dead-removal`，模型呈现范围问题后**用户拒绝回答（declined）**；用户重跑 `/dev-flow:task` 时该 feature 已消失（"The feature seems gone" / "the earlier one is gone"）。需要明确：拒绝回答是模型主动 abandon 还是系统行为，以及该路径是否有清晰的状态说明；
- **旧 active feature 的 pending decision 与新指令冲突**：第一次运行里旧 feature 的待决问题登记的是旧范围（"只处理候选 1"），而用户新指令是"全部解决一下"。模型试图"修正旧决定"又因绑定失败卡住——正确的路径应是走 task-switch（`startFeature` 的 `TASK_SWITCH_REQUIRED`，`state-store.ts:903`）处理旧任务，而不是去改旧决定，但模型无从判断。

### 优化原因

- "刚创建 / 刚失败"场景下状态投影不清晰：`dev_flow_status` / inspect 没有给出"feature 已创建但 intake 未完成 / 有 pending 交互"这类可判定的中间态；
- 模型为自证状态反复调 doctor 与重建，既浪费轮次又可能误删/覆盖已有 feature；
- 状态可见性修复是纯投影改进，不改任何流程语义。

### 涉及的阶段与时机

- **启动后状态查询**（`dev_flow_status` / `dev_flow_inspect` 的返回）：明确呈现"已创建未分类 / pending 交互 / active"；
- **doctor 输出**：作为状态判定的权威入口，应能直接回答"当前是否有 feature、处于哪个阶段、卡在哪个交互"。

### 优化方向

- 状态投影增加中间态标记：intake 已创建但分类未锁定时明确提示"等待分类 / 等待解决待决交互"；
- `dev_flow_doctor` 输出增加一行"当前 active feature + 当前待决交互 + 建议下一步"，让模型无需重建即可继续；
- 失败重试路径（第 3 条）修复后，模型不再需要靠"重建 feature"来摆脱坏状态。

## 5. 同一批准被确认多次：路线 ×2 + 决定登记 ratify

### 现状问题

完整真实会话中，用户对同一逻辑批准被要求确认 2-3 次：

- **路线确认两次**：分类预览阶段，模型向用户完整呈现路线并要求确认（"请确认是否接受此路线，回复 确认路线 即可"），用户回"确认路线"；随后模型调用 `dev_flow_lock_classification`，Core 在 `routeConfirmationRequired` 时**创建正式 route-confirmation 交互并直接返回、锁定并不完成**（`route-workflow.ts:104-127`），必须再要一条新的用户消息确认"确认这条路线"。预览确认没有绑定任何正式交互，锁定后必须重答；
- **决定登记强制追认**：`recordDecision` **无条件**创建 decision-ratification 交互（`decision-workflow.ts:42-55`，ADR-0008）要求"确认登记 / 不要登记"。用户已在指令里明确同意 scope（"全部解决一下"），登记时还要再确认一次。

结果：用户依次输入"确认路线"→"确认登记"→（还需）"确认这条路线"，同一批逻辑批准被反复确认。模型甚至自己指出"the user already approved this route verbally"却无法把该确认绑定到正式 gate。

### 优化原因

- 确认是最高摩擦的用户接触点，同一批准重复确认把摩擦放大成"确认疲劳"；
- 预览确认与正式 gate 不互通：预览呈现的路线与 lock 后 gate 的路线是同一事实，却要求两次表态；
- ADR-0008 追认的本意是"较早聊天的决定需简短追认"；当决定直接引用当前/最近指令时，追认成为纯冗余。

### 涉及的阶段与时机

- **分类预览**（模型呈现的路线确认文本）：不应向用户讨确认；
- **锁定**（`lockClassification` 的 route-confirmation gate，`route-workflow.ts:104`）：唯一应承担路线确认的正式 gate；
- **决定登记**（`recordDecision` 的 decision-ratification，`decision-workflow.ts:42`）：追认的适用边界。

### 优化方向

1. **预览不要求确认**：classify 预览是给模型的分类依据，路线确认只应由 lock 后正式 gate 承担一次；task/classify 技能明确"预览不向用户讨确认"；
2. **或共享确认**：lock 检测到预览已获确认时，把该确认的呈现事件绑定为正式 gate 的确认（共享 `presentationEventId` / 已消费事件），不二次呈现；
3. **决定追认收窄**：`recordDecision` 的结论直接引用当前/最近用户消息时，用该事件作为 ratify 依据（复用第 3 条的绑定机制），仅对"较早对话中的决定"保留强制追认。

## 6. 事实登记与路线锁定往返低效：并行冲突 + ledger ID 反馈不清

### 现状问题

完整真实会话中，边界审计取证与锁定走了多轮失败往返：

- **并发注册必冲突**：模型并发调用 `dev_flow_record_repository_fact` 8 次 → 每次 mutate 都推进 revision，乐观 CAS 使并发调用相互冲突（`STATE_REVISION_CONFLICT`，`repository-facts.ts:149`）→ 只能改串行，8+ 次往返；
- **ledger ID 反馈不清**：`registerRepositoryFact` 返回 `FeatureState`，**不突出返回 recordId（FACT-xxx）**（`repository-facts.ts:147`）；recordId 是确定性哈希，但模型拿不到 → 只能用语义 ref（"web-in-process"）填 classificationBasis；
- **锁定要求账本真实 ID**：`lockClassification` 校验 classificationBasis 与 audit 的所有 ref 都必须是账本真实 ID（FACT/DEC-xxx，`route-workflow.ts:59-68`），语义 ref 直接 `BOUNDARY_AUDIT_UNRESOLVED`；
- 模型被迫：注册事实 → 查状态拿 ID → 重新 lock → 失败 → 再注册 → 再 lock；甚至 sed 读插件源码找 ref 合同（会话中 `sed -n '20,60p' .../route-workflow.ts`）。

### 优化原因

- 无批量入口 + 乐观 CAS = 并发冲突被工具设计放大；事实登记本应是"一次取证批量登记"；
- ledger ID 反馈不清迫使模型"猜 ID"，与"不猜、机器权威"的哲学相悖；
- ref 合同（必须是账本 ID）与模型可获取的信息（只有状态投影，ID 不突出）不对齐，把实现细节泄漏给模型翻源码。

### 涉及的阶段与时机

- **事实登记**（`dev_flow_record_repository_fact` 的调用与返回面）；
- **锁定**（`lockClassification` → `assertBoundaryAuditComplete`，`route-workflow.ts:59`）；
- **M/L 级边界审计取证阶段**（fact/decision 批量登记）。

### 优化方向

1. **批量登记入口**：新增一次调用注册 N 条事实的工具，内部串行 mutate；或让登记幂等——同 recordId 已存在则返回现有、不推进 revision，消除并发冲突；
2. **返回面突出 recordId**：响应直接列出本次登记/已存在的 recordId 清单，供模型直接引用；
3. **锁定失败即给修法**：`BOUNDARY_AUDIT_UNRESOLVED` 时把"未解析的 ref 清单 + 已登记 ID 清单"一起返回，替代让模型翻源码推断合同。

## 7. grillme 拼写误报：自定义 skill 名未入词典 + 与 grill-me 命名混用

### 现状问题

IDE 对 `grillme` 报 `Unknown word (cSpell)`。表面是拼写检查误报，核查后发现两层实义：

- **词典缺失**：`grillme` 是自定义 skill 名（`plugins/dev-flow/skills/grillme/SKILL.md`），仓库没有 `.cspell.json` / `cspell.json`，无法把该标识符加入词典，IDE 持续报错；
- **命名不一致**：代码库里并存两个不同技能——`grillme`（dev-flow 自带的 A/B/C 决策澄清，slash `/dev-flow:grillme`）与 `grill-me`（marketplace 技能，`.claude/skills/grill-me/`，来源 mattpocock，通用"连续盘问"）。`CLAUDE.md:185` 把两者混为一谈："边界不清必须 `grillme`…先调用 `/grill-me` 提问"——语义上把两个入口当成一个，模型/用户无法确定该调哪个。另 `README.md:152`、`docs/ai-coding-frameworks-compare.md` 等处两词混用。

### 优化原因

- 词典缺词本身很小，但暴露了"自定义标识符无词典管理"的惯例缺口：`grillme`、`dev-flow`、`boundaryAudit` 等大量自定义词都可能被 IDE 误报；
- `CLAUDE.md` 是给模型的行为约束，两个不同技能名在同一约束里混用会让模型调错入口（把 dev-flow 的决策澄清当成通用盘问，或反之），影响行为正确性而非仅是观感。

### 涉及的阶段与时机

- **文档与词典配置层**：仓库级 cspell 配置、`CLAUDE.md` / `README.md` 中两个技能的引用。

### 优化方向

1. **cspell 词典收录自定义标识符**：新增仓库级 `.cspell.json`，将 `grillme`、`dev-flow`、`boundaryAudit` 等惯用词加入 `words`，消除 IDE 误报；
2. **统一两个技能的引用**：区分语义——dev-flow 边界澄清用 `grillme`（或 `/dev-flow:grillme`），通用盘问用 `/grill-me`；修正 `CLAUDE.md:185` 等处的混用表述，避免模型把两个入口当成一个。
