### 1. 完成交互落账收拢：剩余 5 个交互 kind 接入 answer 的 kind 表

**涉及文件**
- `plugins/dev-flow/src/core/interaction-answer.ts:75-84`（kindResolvers 只接 8/13 kind）、`:119`（`DECISION_KIND_UNSUPPORTED`）
- `plugins/dev-flow/src/core/user-interactions.ts:12`（13 个 InteractionKind）、`:363`（resolveResponseForAnswer）
- `plugins/dev-flow/src/core/rollback.ts:555-734`、`acceptance.ts:155-206`、`quality-exceptions.ts:99/123`、`review-jobs.ts:1394/1422/1442`、`ownership-workflow.ts:167`（resolveTaskSwitchAnswer，**全仓零调用方，死代码**）
- `plugins/dev-flow/src/mcp/server.ts:1197-1357`（4~5 份 present→elicit→resolve→envelope 编排副本）、`:1206-1209`（caller 侧手工重推 pending 交互）

**问题**：交互落账存在两套并行合同。ADR-0019 的 `answer({ credential })` 只接 8/13 个 kind（decision-ratification、decision-revision、plan-revision、side-effect-rerun、grill、approval、workspace-ownership、route-confirmation），其余 5 个（risk-acceptance、rollback-confirmation、quality-exception、task-switch、acceptance-confirmation）走 9 个导出的 `resolveX{Answer,Elicitation}` 函数——其中 8 个带 `interactionId`（task-switch 的 resolver 参数形状不同），与 ADR-0019「caller 不传交互编号」的方向相违。`dev_flow_answer` 文本路径对这 5 个 kind 抛 `DECISION_KIND_UNSUPPORTED`，现役测试已锁定该失败关闭行为（生产功能缺口）；task-switch 更极端：`startFeature`（state-store.ts:909-919）会创建 task-switch 交互，但它既不在 kind 表里，专用 resolver 又是死代码，state-store.ts:933-934 的恢复文案自己承认"当前版本暂不支持通过统一回答入口处理"。语义解析入口与错误码存在分叉（两条路径交错使用 `matchDecisionReply` 与 `resolveTextInteraction`/`resolveResponseForAnswer`，不是整齐的 legacy/answer 二分）。

**方案**：把 5 个 kind 的领域落账写成 `AnswerKindResolver` 加进 interaction-answer.ts 的内部 kind 表（kind 特有证明——回撤的 later-turn/时间戳证明、验收的 dispositionHash 时效——收进各自 resolver 体内，不得弱化），删掉 9 个导出 legacy 函数与 server.ts 的对应编排块。删除前先迁移 server 和现役测试；文本与 elicitation 都经同一领域 apply；失败必须保持 revision、事件消费和 interaction 状态不变。

**deletion test**：真删除。`answer` 已通用实现「定位 → 证明 → 语义解析 → 一笔 mutatePrepared 落账」，删的是平行实现与编排副本，复杂度不散落。user-interactions 的 `resolveNative/resolveTextInteraction` 随之可私有化（interface 从 15 个导出缩到 ~8）。

**收益**
- 生产缺口闭合：5 个 kind 不再 UNSUPPORTED
- locality：组合问题收口 answer
- interface 收缩：15 导出 → ~8
- 语义解析单点，错误码不再分叉
- 测试只打 answer 的账本结果，删 5 组 legacy resolve 单测

**ADR**：无冲突——这正是 ADR-0019「下一刀验收或回撤加行，不改 answer」、ADR-0023「风险接受仍走交互（ADR-0019 下一刀）」、ADR-0024「回撤确认交互归 ADR-0019 下一刀」明示的方向。约束照旧：kind 表留在 implementation 内，不公开 inspect/prove/preview/replay；presentX 函数保留（present 文案不在此 module）。

**测试面**：全部交互测试统一到 `answer` 的账本结果（"凭证进、账本出"、失败 revision 不变）；kind 特有证明用例经 answer 触发。

### 2. 收拢 MCP「呈现门禁 → 征询 → 落账」管道

**涉及文件**
- `plugins/dev-flow/src/mcp/server.ts:1047-1374`（10 个带 elicitation 的管道 case；该区间共约 35 个 case）、`:724-773`（envelope helpers）
- `plugins/dev-flow/src/core/interaction-answer.ts:51`（`AnswerResult.pending` 已给出，调用点却重算）

**问题**：同一条 6 步管道（core present → attention 通知 → `connection.elicit` → 无选择时返回 pending envelope → 落账 → `interactionEnvelope` 包装）手抄 **10 份**：10 处 `connection.elicit`、11 处 attention 通知调用（其中 1 处是 workflow-finalized 通知，不属于交互征询管道）、21 处 `interactionEnvelope` 调用（字面 22 含定义）、7 处 `answer({`、4 处 `resolve*Elicitation` 调用（另 4 处为 import）。每份的细微差异正是 bug 藏身处：
- `dev_flow_present_approval` 同一个 handler 两种返回形状：pending 分支把整个 `presentation` 当 state（:1288），成功分支传 `state.state`（:1293-1298），靠 `compactMutationResult` 的 `isFeatureState` 猜测链（:561-579）兜底——目前能被 formatter 归一，属脆弱设计而非已证实的功能 bug；

**方案**：一个参数化管道函数（注入 present/resolve 两个回调与附加字段），10 个 case 各缩成 5 行。

**deletion test**：集中。pending 语义、envelope 形状、optionLabel 映射只有一份；变体差异（附加字段）以参数存在，不散落。

**收益**

- envelope 形状单点（21 处调用 → 1）
- locality：elicit 的 undefined / 超时 / decline 三分支集中

- `compactMutationResult` 的猜测链随之简化为纯 formatter

**ADR**：无冲突。守住边界：管道只收编排，**不得把 4 个 core `resolve*Elicitation` 并入 answer**（那才是越界，ADR-0019）。候选 1 落地后管道只剩一种落账形状，收益最大。

### 3. 把 dispatch 从 stdin 脚本解放为可导入深模块

**涉及文件**
- `plugins/dev-flow/src/mcp/server.ts:1006-1462`（dispatch + dispatchRequest + stdin 循环）、`:64`（模块级 `const root = process.cwd()`）、`:1450`（模块级 stdin `for await`）

### 4. 收拢「当前步骤」归约：一条走到哪一步的真理

**涉及文件**
- `plugins/dev-flow/src/core/step-order.ts:22-27`（`currentOpenStep`，走 orderedSteps，10+ 个门禁调用方的权威）
- `plugins/dev-flow/src/policy/stages.ts:17-25`（`effectiveStage`，走 `Object.keys` 插入序，服务 status-projection.ts:82、inspection.ts:48、execution-brief.ts:36 三个投影）
- `plugins/dev-flow/src/core/status.ts:149-158,185-186`（`buildProgress` 第三次走 + 从 action.kind/step 字符串反解码调度结论）
- `plugins/dev-flow/src/core/next.ts:76-81`（`deriveRouteAction` 第四次走）
- `plugins/dev-flow/src/core/route-workflow.ts:443-446`（`applyRouteTransition` 只保留已满足步骤前缀）

**问题**：「当前进行到哪一步」有四个 implementation。这不只是重复——重分类只保留 satisfied 前缀时，`effectiveStage` 的 `keys.find(status !== "satisfied")` 返回 undefined、回落成 `keys[0]`（新路线第一个**已满足**的步骤）。交叉核实已构造最小反例：`{ steps: { requirements_alignment: satisfied }, currentStage: planning }` 的实际输出为 `effectiveStage = requirements_alignment`、`currentOpenStep = planning`、`currentStage = planning`——CompactStatus 显示"需求确认"而调度器实际在 planning，两个 status 投影对同一状态给出不同答案。这是**已证实的一致性缺陷**，不只是代码重复。ADR-0021 说"readStatusView 只消费 nextAction，不另算一遍"——`buildProgress` 的重走和反解码正是没做完的那半刀。

**方案**：一个纯函数 route position 归约（输入 state 与定义，输出当前步骤/序号/剩余），调度、门禁、投影三方共用一个 implementation，投影只做翻译。先加「重分类后只有 satisfied 前缀」回归测试；compact status、stage capabilities、inspection、execution brief 与 scheduler 消费同一归约结果。

**deletion test**：删掉 `effectiveStage`/`buildProgress` 两处私有实现，调用方全部变 consumer，无新 interface 膨胀——集中，不是搬家。

**收益**
- 已证实的投影分叉消失
- locality：步骤语义单点
- 投影测试退化为翻译测，不再各自模拟步骤序列
- 归约函数一处单测覆盖「重分类后只剩 satisfied 前缀」用例

**ADR**：无冲突——恰是 ADR-0021 的既定方向（欠账）。实施优先级提升为紧随候选 1 的独立修复项。

**测试面**：装配器独立夹具测；一条「同一计划经三个入口诊断全等」回归，把注释不变量变成断言。

### 8. begin 就绪可问化：消除 writeGate 的「试 begin → 重载 → 重判」

**涉及文件**

**问题**：ADR-0022 让门禁「必要时自己 begin」，但 begin 的前置（host 健康、归属完备、trace 时效、工件时效、review 就绪、依赖 checkpointed……）全部藏在 mutate 闭包里，门禁无法预知成败，只能：尝试 begin → 若 revision 变了就整体重载 → 对每个路径重跑 implementationUnitWriteBlock → 失败时压成字符串诊断。「下一个可 begin 单元」的搜索重复在 `ensureActiveImplementationUnit`（:104-109）与 `next.ts` 的 `unitLifecycleAction`；begin 本身只校验调用方指定的 unitId 及其依赖（初版报告误写为 ensureActive 与 begin 各写一遍，已修正）。这正是 ADR-0023 刚为 review 解决过的同一种摩擦（抛错再翻译 → status 查询），单元域还没跟上。测试佐证：v2-implementation-units.test.mjs 只敢测纯判断（手捏残缺 state 字面量），begin 的重逻辑只能全夹具端到端打。

**deletion test**：**有条件集中**——只有查询与 apply 共享同一派生函数、且在锁内复查（避免 TOCTOU）时复杂度才真集中；另写一份前置镜像就是搬家（且两份必漂移）。这是本候选的关键设计约束。

**ADR**：与 ADR-0022 兼容（writeGate 仍是唯一写门禁、仍自己 begin）。借鉴 ADR-0023 形状时守其「不公开 deficit 集合」精神——就绪查询返回 status/原因码即可。
