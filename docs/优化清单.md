## 1. 对 grill 推荐做对抗性检查

### 现状问题

grill 决策的 A/B/C 选项与唯一推荐理由全部由模型生成，机制对 framing 质量没有校验：

- 若模型对问题本身理解偏差，三个选项可能都在错误框架内，用户被迫在错误框架里选择；
- `other` 是唯一的被动出口，无法强制"选项质量可被挑战"；
- 用户在默认效应 / 权威偏误下大概率直接接受推荐——模型推荐错方向时，机制放大而非纠正错误；
- 与 evidence 校验同类的问题：boundaryAudit 的 evidenceRef 只做形式校验（非空字符串即通过），不校验"处置充分性"，"扫描得对不对"仍由模型自证。

### 优化原因

决策质量 = 提问方 framing 质量 + 用户选择质量。当前机制只保障了后者（交互契约克制、每次一问、A/B/C 展示统一），前者完全依赖模型诚实度与能力。这是 agent 治理系统无法根除的弱点，但机制可以增加结构性约束，让错误更容易在决策时点被发现，而不是在实现阶段爆发（此时成本放大数倍）。

### 涉及的阶段与时机

- **锁定分类前**：boundaryAudit 处置必须由用户选择的边界项时（`dev_flow_request_grill_decision` 发起处）；
- **需求登记阶段**（`requirements_alignment`）：登记 `需求文档.md` 时的现场取舍；
- 以及后续任何走统一 grill 通道的阶段（planning 拆 RU、implementation 发现 scope 界定不清等）——建议作为 grill 通道的统一行为，而非按阶段分别实现。

### 优化方向

- 模型给出推荐前，先陈述"不选推荐选项的最强理由"（反向论证），该理由随 A/B/C 一并展示给用户；
- 对选项做结构校验：选项必须互斥、组合应覆盖主要可能分支、推荐理由必须可被合理反驳（即存在可辩护的替代选择）；
- 将选项 framing 质量纳入审计记录（作为 audit 项），供事后复盘与 plan-review 角色引用。

## 2. 显式的决策修订流程

### 现状问题

已落账的 grill / record_decision 决策缺乏显式撤销或修订路径：

- 5.0 合同对"决策后修正"只表述为"修正事实后重新分类"，没有定义已落账决策如何显式作废；
- 现场取舍只能重走 grill（`request_grill_decision` → `dev_flow_answer`），但"重走 grill 选另一个选项"与"修订一条旧决策"在语义上不同：前者是新决策，后者是对旧决策的否定；
- `dev_flow_record_decision` 一次性写入 evidence 与 conclusion，同样没有 supersede 语义；
- 若用户在实现阶段发现此前选错（例如 scope 界定），只能隐式覆盖——审计链上留下两条并存结论，需要人工辨别哪条当前有效，且无法自动推导哪些下游证据因此失效。

### 优化原因

决策修订是真实发生的场景（需求理解随实现推进而加深），当前机制把"改主意"变成了审计链上的模糊地带。显式修订流程的价值：

- 审计完整性：决策变更本身可追溯（谁在何时以何理由覆盖了哪条决策）；
- 失效传播可推导：修订一条决策后，可精确判定哪些下游证据（freshness、approval、checkpoint）因语义 basis 变化而失效，而不是全量 stale；
- 与"实现开始后控制只能增加"的单调性约束兼容：修订决策是事实修正，不削弱控制，属于允许的变更方向。

### 涉及的阶段与时机

- **锁定分类前**：修订影响 scope / 拓扑 / 风险事实 → 重算分类，重新呈现 route-confirmation；
- **需求登记阶段**（`requirements_alignment`）：修订需求文档 → 重新登记 → 重新向用户确认；
- **实现阶段**（`implementation` 及之后）：发现决策错误时修订 → 精确失效受影响证据，回退到最早受影响阶段重做（复用 5.0 的 freshness 语义 basis 机制）。

### 优化方向

- 为决策记录增加 `superseded` 状态与修订链（记录修订原因、来源事件、替代决策引用）；
- 修订入口建议复用统一决策通道（新增受限交互或显式修订请求），禁止隐式覆盖；
- 修订时按决策的语义 basis 精确失效下游证据，避免全量重跑；
- 保持 5.0 红线：修订不得改写原始决策记录（追加 supersede 标记而非原地修改），不得削弱已派生控制。

## 3. 已评审否决的候选改进（存档）

### 决策批量合并（否决）

曾提议将互不耦合的决策合并为一轮多问以降低打断次数。否决理由：

- grill 过滤器按"影响度"（是否改变范围/验收/拓扑/风险/不可逆取舍）而非"可知性"筛选，对需求成熟的工程师用户实际触发轮数很低；
- 轮数高的场景恰是需求真正模糊或 M/L 共享契约类任务，此时逐轮互斥确认的认知质量优于批量多选；
- 批量合并不省思考成本，只省确认成本，且引入"一次面对多个决策"的负担，得不偿失。

结论：保持"每次只问一个互斥决策"，不为此改动机制。若未来使用场景扩展（非工程师用户、系统级重构任务）导致打断次数成为瓶颈，可再评估，但需附带单轮上限与耦合度校验。

## 4. planning 全覆盖校验与 TDD 豁免的裂缝

### 现状问题

两条规则在 Core 层与技能层各自成立，但接缝处没有衔接：

- **Core 层**（`plugins/dev-flow/src/core/traceability.ts`，complete 模式）：`every acceptance criterion requires a test`——每个 AC 必须有 TEST 节点 `verifies` 它，否则 `TRACE_SLICE_INCOMPLETE`，实施计划无法登记；
- **技能层**（plan / implement SKILL.md）：含行为变更的 TASK 声明 TDD 或**明确无法 TDD 的理由**（文档、类型导出、机械重构等），即"有些任务合法地没有测试"。

问题：Core 的完整图校验不认识"豁免"概念。"无法 TDD" 在计划里是 TASK 的自由文本理由，Trace 图校验只认 TEST 节点是否存在。两个判断系统（行为性判断在技能层、覆盖性判断在 Core 层）没有共享结构化字段。无行为变更的 AC 面前只有两条路：编一个形式 TEST，或登记失败反复往返。

### 真实开发中的后果

- **覆盖假象（coverage theater），最有害**：形式 TEST 节点（"验证方法：运行 typecheck""目视检查"）让 Trace 图显示 100% AC 有测试覆盖；requirements-coverage 审查、finalize 报告、用户信任全部收到"全绿"信号，而这个信号可由一行自由文本廉价伪造。机制本意是防止遗漏，结果反而掩盖遗漏——"保证 > 实际"是治理系统中最危险的一类问题。
- **纯文档/配置/依赖任务被逼出假测试**：升级依赖、改配置、更新文档类 AC 没有行为测试，模型必须编造 TEST 锚点且无真实测试文件对应；实现阶段"测试先行"退化为"锚点先行"，TDD 红-绿流程被污染。
- **多 AC 一测试场景节点膨胀**：一个真实行为测试通常覆盖 3–5 个 AC，校验却要求每个 AC 各有 TEST 节点，模型写多个内容重复的锚点指向同一测试；Trace 图节点虚增，审查与 finalize 报告失真。
- **审查噪声**：requirements-coverage 角色被迫人工甄别真测试/形式测试，roleBasisHash 中没有该维度，甄别结论也无法结构化落账。
- **深层观察：TEST 节点是声明不是证据**：真正驱动执行的是 verification commands（`provides` 声明 + RU forward_verification），TEST 节点不参与命令选择、不参与 checkpoint 校验，存在的唯一理由是满足完整性校验——完备性被建模成"节点存在性"而非"证据存在性"。

### 涉及的阶段与时机

- **planning 登记**（`recordArtifactWithTrace` → `assertTraceabilityComplete`）：豁免通道必须在此刻生效，否则登记仍失败；
- **plan_review**：requirements-coverage 角色把豁免合理性作为显式 finding 项核验；
- **implementation**：豁免 AC 的 TASK 按计划声明直接实现，不强制测试先行；
- **finalize**：报告行为覆盖与显式豁免的分项计数，消除覆盖假象。

### 优化方向

核心修法：**把"每个 AC 必须有 TEST"改为"每个 AC 必须有验证处置（TEST 或显式豁免）"，豁免与技能层的 TDD 声明共用同一结构化字段。**

1. TASK 节点新增结构化字段（如 `verification: behavioral | non-behavioral`），与 plan 技能的 TDD 声明合并为单一来源；`non-behavioral` 必须附非空理由并引用具体证据（文档路径/配置项/依赖版本），空理由登记拒绝。
2. 校验放宽为：每个 AC 至少满足一条——被 TEST 节点 verifies，或**其覆盖的全部 TASK 都声明 non-behavioral**。完备性不降（每个 AC 仍有处置），编造压力消失（无行为 AC 有合法通道）。
3. 豁免合理性交给审查而非模型自证：requirements-coverage 角色将豁免是否成立作为显式 finding，不成立则 blocking，用户可风险接受或驳回——判断权从模型自证转移到"独立审查 + 用户拍板"，与系统其余部分的信任模型一致。
4. Trace 图暴露豁免状态：summary 增加豁免计数，finalize 报告"X 个 AC 行为测试覆盖、Y 个 AC 显式豁免"，审查视图按状态着色。
5. 根治方向（更远）：让验证覆盖挂在证据上而非声明上——TEST 节点或 RU forward_verification 命令声明 `covers: [AC-xxx]` 映射，校验"每个 AC 被至少一条可执行验证覆盖或被豁免"。代价是命令级覆盖映射的声明负担，但形式测试将没有存在空间。

### 新方案引入的代价

- 模型新增判断负担：判定 AC 是否有行为变更；该判断本身可能出错（误判 non-behavioral），由审查角色兜底拦截；
- 审查职责前移：requirements-coverage 的 finding 范围扩大（从"覆盖缺失"到"覆盖缺失 + 豁免不当"），审查角色 basis 需要纳入豁免维度；
- 结构化字段使计划语法更严格，模板与技能说明需同步更新。

### 待决策项

- 豁免粒度取 TASK 级还是 AC 级（TASK 级与 TDD 声明对齐但多对多映射复杂；AC 级直接但引入第二套声明）；
- 是否将 `verification` 字段与 TDD 执行顺序声明合并为同一字段（避免两套"行为性"判断并存）。

## 5. planning 缺少 dry-run 校验入口

### 现状问题

计划登记（`recordArtifactWithTrace`）是唯一校验时机，且 `validateTraceGraph` 为 throw-on-first（遇第一个错误即抛）。校验链很长（锚点解析 → delta 白名单 → 任务图双向一致 → AC→TEST 全覆盖 → 命令引用 → fileScope 安全），复杂计划（多 TASK、多 RU、多 TEST）首次登记通过率低。失败 → 修改 → 重新登记是往返式：修完一个错再撞上下一个（级联往返）；错误 details/recoveryHint 是给模型看的，用户只能听模型转述，可见性差；`writeTraceSnapshot` 在校验失败路径会留下孤儿快照文件（状态不提交，但文件残留）。

### 优化原因

- 消灭级联往返：一次返回全部错误清单，模型一次修完；
- 把"还没准备好"（正常预检）与"登记失败"（异常）从语义上分开；
- 预检通过后再提交审查，避免"审查了一个根本登记不了的版本"；
- 缓解探索性调整的摩擦：改计划 → dry-run → 再改，比改计划 → 登记失败 → 再改便宜。

### 涉及的阶段与时机

- **planning 阶段**（`dev_flow_record_artifact` 之前）：模型编辑 `实施计划.md` 后、登记前的预检入口；审查提交前也可用它确认计划可登记。

### 优化方向

- 新增只读校验工具（如 `dev_flow_validate_plan`），复用现有纯函数校验（`validatePlanTaskGraph`、`validateTraceDelta`、`validateTraceGraph`、`assertArtifactDeltaContract`、`assertTraceabilityComplete`）串成全量校验；
- **聚合全部错误**而非 throw-on-first，每条带定位（锚点 ID/字段）与修复建议；
- **零副作用**：不写快照、不改状态、不推进 revision，失败不产生孤儿文件；
- 实现成本低：校验函数已全部是纯函数，仅需串接与聚合。

## 6. 执行图静态 DAG：独立 RU 并行与修订通道降价

### 现状问题

- 执行图是静态 DAG（RU 的 `depends_on` 为静态完成依赖，校验强制无环），且 begin 强制**单 active unit**（`IMPLEMENTATION_UNIT_ALREADY_ACTIVE`）；
- 计划的刚性 vs 实现的探索性：实现中发现计划缺陷时，必须 abandon 当前单元 → 改计划 → 重登记 → 重新 begin，全量仪式化；
- 依赖粒度是 RU 级：B 只等 A 的一个文件就绪，却要等 A 全部 checkpointed；无依赖关系的 RU 被迫串行排队；
- 循环依赖（真实模块互调常态）被强制线性化为"A → B → A'"，"A' 是 A 的补丁"的语义关系丢失；
- "B 失败 → 回滚 B → 重做 A 的部分 → 再重做 B"的恢复序列没有表达。

### 优化原因（与价值排序）

- 修订通道太贵是探索性冲突的主因，不是图表达力不足——**修通道比修图便宜**；
- 独立 RU 并行直接改善 M 级多组件任务的节奏；
- 静态 DAG 本体是正确的默认：计划的确定性（机器可校验、可审查、可回滚）是整套信任模型的基础，引入条件边/动态图会让模型的自主决策空间变大，校验、审查、finalize 证据链全部需要重新设计——**"更复杂的图"是自毁，不做**。

### 涉及的阶段与时机

- **planning**：图结构本身不变；并行与修订语义在登记校验中体现（依赖检查、失效传播）；
- **implementation**：begin/checkpoint 的单元生命周期（并行激活、局部修订的单元保留）；
- **plan_review**：修订后按语义 diff 只重审受影响角色（已有机制延伸）。

### 优化方向

1. **独立 RU 并行**：放宽单 active unit 约束——允许无依赖关系的 RU 并行激活（begin 只检查依赖链是否 checkpointed，不再检查"是否已有 active"）；checkpoint 按依赖顺序落账，rollback 按依赖逆序。
2. **修订通道降价（最高优先）**：允许 checkpointed 单元的**局部修订**——计划重登记时，只失效语义 diff 影响的下游单元，已 checkpointed 且不受影响的单元保留（与 5.0 review 角色级复用的同一逻辑延伸到实现单元级）；放弃"计划变更 → 全量重来"的现状。
3. **L 级可选 `recovery_sequence`（暂缓）**：为协调回滚场景显式声明"失败 → 回滚 → 重做依赖单元的部分 → 重做本单元"的恢复序列；仅增加 L 级计划语言复杂度，M 级不受影响。

### 优先级结论

| 项目 | 成本 | 收益 | 建议 |
| --- | --- | --- | --- |
| dry-run 校验工具（第 5 条） | 低 | 中（消灭级联往返） | 做 |
| 独立 RU 并行 | 中 | 中高（M 级多组件节奏） | 值得做 |
| 修订通道降价（局部修订） | 中 | 高（探索性冲突主解） | 最值得做 |
| L 级 recovery_sequence | 高 | 低（罕见场景） | 暂缓 |
| 图模型升级（条件/动态） | 极高 | 负（确定性受损） | 不做 |

## 7. plan_review：attestation 信任边界

### 现状问题

Assurance 阶梯（`assuranceForReviewBatch`，`plugins/dev-flow/src/policy/review.ts`）中，`multi-agent-attested` 档只校验 attestation 的**形状**（host/agentId/issuedAt/raw 非空），不校验真伪：`attested` 只过滤 `submission?.attestation` 存在，`agentIds.size >= 2 && rawHashes.size >= 2` 即达成。`defaultReviewIdentityVerifier` 永不返回 trusted 只影响最高档（multi-agent-verified），`normalizeHostAttestation` 也只验形状。若宿主 hook 不强制注入 attestation，模型理论上可以自造两份 agentId/raw 不同的 attestation，把 assurance 抬到 multi-agent-attested。

当前缓解：Review 2a 阶段 `assuranceForReview2a` 恒返回 multi-perspective、`evidenceSourcesForReviewBatch` 诚实列出证据来源。但档位本身依赖宿主调用方可信，属于"形状校验被当成真实性校验"的信任虚高方向。

### 优化原因

- assurance 是审查结论可信度的对外承诺，档位可被伪造会破坏用户对审查结果的信任模型；
- 与决策（grill/record_decision）的 provenance 设计不一致：决策绑定可信宿主事件，attestation 却没有同等的来源绑定；
- 这是系统里少见的"错误方向"问题（信任虚高），成本可持续性角度无法接受。

### 涉及的阶段与时机

- **plan_review 提交**（`submitReviewJob` 的 hostAttestation 入参）：attestation 的来源注入点；
- **assurance 计算**（`assuranceForReviewBatch` 的 multi-agent-attested 档）：档位判定处。

### 设计方向

1. **attestation 与决策一样绑定可信宿主事件**：attestation 必须引用 feature 启动后、当前宿主产生的可信事件（与 `record_decision` 的 provenance 同一机制），无事件引用的 attestation 不得计入 multi-agent-attested 档；
2. 或**2a 阶段强制不看 attestation**：`assuranceForReviewBatch` 在 2a 下忽略 attestation 证据，档位只从 role-jobs 与 server-sampling 计算，attestation 仅作诊断展示；
3. 保留 `ReviewIdentityVerifier` 扩展点，未来可信宿主接入时由 verifier 提供真实性判定，`multi-agent-verified` 档才启用。

## 8. plan_review：未知 diff 全量重审缺少诊断

### 现状问题

`createReviewBatch`（`plugins/dev-flow/src/core/review-jobs.ts`）中，未知 diff 的判定为：basisHash 变化但所有角色 roleBasisHash 均命中复用 → 保守全量重审。这是正确的 fail-safe 方向，但**触发原因被吞掉**——未知 diff 的本质是"basis 中某字段变化但不落入任何角色切片"，可能是 roleBasisHash 切片覆盖缺口（该失效的角色未失效），当前实现不输出任何诊断，维护者无法发现切片缺口，只能等某次漏审暴露。

### 优化原因

- 全量重审本身正确，真正需要修的是"为什么触发"的可见性；
- 角色切片覆盖缺口是静默积累的维护风险：切片越改越多，某次字段新增后忘记落入某角色切片，未知 diff 频率会悄悄上升（成本）或某角色失效被吞（风险）；
- 低成本纯增量改进，不改变任何审查行为。

### 涉及的阶段与时机

- **plan_review 批次创建**（`createReviewBatch` 的 unknownDiff 分支）：触发点处输出诊断。

### 设计方向

- 批次创建事件中记录：basis 变化的字段清单、未落入任何角色切片的具体字段（如 scopeManifest、governedRootsFingerprint、workflowCapabilities 等变化）、触发的全量重审原因；
- 诊断输出到 mutation event（与 artifactChanged/traceChanged 同级），供 inspect 与审计查看；
- 不改变 unknownDiff 的判定与重审行为，仅增加可见性。

## 9. code_review：审查发现记账与审查视角完整性

### 现状问题

code_review 阶段只有**浅记账**：`record_step code_review` 校验的 evidence 仅为 `reviewType: "code"`、风险时 `reviewDepth: "full"` 与 `risk-review` check（`plugins/dev-flow/src/policy/evidence.ts`）——只核对"审过了 + 深度正确 + 检查覆盖声明"，审查发现本身不结构化入账。`review-jobs.ts` 中无任何 code_review 引用：review ledger / batch / job / finding / risk-acceptance 全部服务于 plan_review。

对比借鉴源 `.claude/skills/code-review/SKILL.md`（双轴 Standards/Spec 并行子代理、固定 Fowler smell baseline、Spec 轴逐条核对需求忠实度），dev-flow 在"范围控制"（Core 派生文件 + Git 基线）和"深度分级"（none/focused/independent/full）上更严格，但缺少三样东西：审查发现记账、实现层需求忠实度检查（scope creep 无归属）、固定审查基线。

### 真实开发中的后果

- **blocking 修复无法核验**："先修 blocking 再复审"是纯技能指令，Core 无法验证"真的修了"——除非人工对比复审前后的交付 diff；
- **scope creep 无归属**：plan_review 的 requirements-coverage 只审计划层，实现层"加了需求没要的东西 / 漏实现需求"没有明确审查轴——agent 实现的真实高频问题漏检；
- **审查一致性依赖模型状态**：无固定基线时，"审得多深"由模型当天状态决定，跨批次不可比。

### 涉及的阶段与时机

- **code_review 阶段**（`record_step code_review` 的证据提交处）：记账扩展与核验；
- **full 深度执行**（技能层）：双轴与基线写入审查清单。

### 设计方向

1. **blocking 修复的轻量记账（最值得补）**：blocking finding 列表 + 修复引用（指向修复后的文件），`record_step code_review` 时核对"声明的 blocking 均有修复证据"；不需要 plan_review 的重型 ledger，一行结构化证据即可。
2. **full 深度明确双轴**：现有 full 清单（调用影响、失败路径、安全、数据/金额/不可逆、测试充分性）是"实现质量轴"；补充"Spec 轴"——逐 AC 核对实现是否忠实、有无超范围改动，两轴分离报告不合并（沿用 .claude 版"不合并防一轴掩盖另一轴"的原则）。成本最低（技能文本），收益直接。
3. **引入固定审查基线**：将 12 项 Fowler smell 作为 Standards 基线的可选项写入技能（仓库规范优先、smell 是判断不是硬性违规），审查一致性不再依赖模型状态。
4. **independent 执行形态明确化**：定义"与实现分离"的形态——实现完成后独立审查、可用子代理但遵守 assurance 原则（同一模型多次输出不算多代理，与 plan_review 一致）。
5. **测试充分性审查与 verification 关联（小）**：审查 evidence 可引用其检查的 TEST 锚点 ID，与 verification 阶段的命令覆盖形成闭环。

### 不借鉴项

- **自动 commit**：.claude 版"审查完 commit"与 dev-flow 的人工 Git 闸门冲突，保持不自动提交；
- **双轴合并**：引入双轴后仍应分离报告，不合并不排序。

## 10. verification：手动验收信任缺口与修复路径完整性

### 现状问题

- **browser / code-path-audit 手动验收无可信事件绑定**（`plugins/dev-flow/src/core/verification.ts`）：`assertOptionalManualAcceptance` 只对 `user-signoff` 强制解析可信宿主事件 + 防重放；`browser` 与 `code-path-audit` 模式只要 source + scenarios 非空即通过——模型可编造验收证据，无需任何用户事件。与 user-signoff、approval、decision 的信任模型（全部绑定可信事件）不一致。
- **verification 修复绕过 code_review**：验证失败 → repair loop → 模型改代码 → 重跑验证 → finalize。该修改不使 `steps.code_review` 失效（无机制重新打开），也不重新 checkpoint——M 级独立代码审查从未看过这些修复。5.0 只覆盖"code_review 阶段修复自动入交付"，未覆盖"verification 阶段修复需重审"。
- **命令超时/缓冲硬编码且与失败不可区分**：`runVerificationCommand` 硬编码 120 秒超时、1MB maxBuffer；超时被归一为 exitCode 1，模型无法区分"测试失败"与"超时被杀"，可能修不存在的 bug 或进 repair loop 撞墙。

### 优化原因

- 前两项属错误方向（验收证据可编造、审查缺口），是"形状校验被当成真实性校验"模式在 verification 域的实例；
- 第三项是真实可用性问题：长集成/全量测试超过 2 分钟即被杀。

### 涉及的阶段与时机

- **verification 执行**（`runVerificationCommand` / `assertOptionalManualAcceptance`）：信任绑定与超时配置；
- **verification 失败修复**（repair loop 入口）：修复路径的阶段归属；
- **finalize 收口**：code_review 证据有效性核验。

### 设计方向

1. **browser / code-path-audit 绑定可信事件**：与 user-signoff 同一机制——必须引用宿主可信事件（或明确标注"未经用户事件验证"降级证据标记），禁止无事件编造验收；
2. **验证阶段修复触发 code_review 失效**：验证失败且涉及 governed 文件修改时，撤销 code_review 证据或要求回到 implementation 流程（重新 begin 单元、重新审查），与"code_review 修复自动入交付"对称；
3. **per-command 超时/缓冲配置**：project schema 支持命令级 timeout/maxBuffer，超时错误带明确标记（退出原因），不再归一为普通失败。

## 11. finalize：quality exception 时效性绑定

### 现状问题

`quality-exceptions.ts` 接受风险时记录 `fingerprint: state.workspace.lastWorkspaceFingerprint`，但 resolve 与 finalize（`hasCurrentQualityException`）**不校验当前工作区指纹是否仍等于该值**——用户接受风险后 governed 文件变化，exception 仍为 current，finalize 继续放行。对比 plan_review 的 risk-acceptance（严格绑定 batch + basisHash + findingSetHash，任何漂移即失效），此处是弱绑定，属于"证据时效未绑定"的错误方向。

### 优化原因

- 质量例外是完整性阻塞的受控绕过，其有效性应绑定接受时的证据状态；
- 接受后文件变化 = 例外针对的状态已不存在，继续放行会让"接受风险"演变为"永久豁免"。

### 涉及的阶段与时机

- **quality exception 呈现与解析**（`presentQualityException` / `resolveQualityExceptionResponse`）：记录指纹的校验点；
- **finalize 义务核验**（`hasCurrentQualityException` 调用处）：有效性复查。

### 设计方向

- finalize 时校验 exception.fingerprint 与当前工作区指纹一致，不一致则标记 stale 并重新呈现质量例外（接受或修复二选一）；
- 与 plan_review risk-acceptance 的绑定强度对齐：同依据、同指纹才有效，任何漂移即失效。

## 12. 启动与分类域：record_decision 语义匹配弱绑定

### 现状问题

`recordDecision`（`plugins/dev-flow/src/core/state-store.ts`）调用 `resolvePromptEvent` 时传入 `presentedAt=new Date(0)`、`presentedRevision=-1`——`isAfterPresentation` 因此对**所有历史事件都成立**，匹配条件只剩：同宿主 + 未被消费 + 事件文本与 conclusion 匹配。后果：**用户对另一个问题说过的同文本内容，可能被记录为当前问题的决策证据**。机制只保证"这句话确实存在且来自当前宿主"，不保证"这句话是针对这个问题的"。

这是有意的设计放宽（历史结论无法满足严格呈现匹配，`record_decision` 用于"用户之前已口头决定"的场景），但与 grill（严格呈现绑定）形成两条信任档位：grill 先呈现问题再绑定回答（可靠），record_decision 回溯匹配任意历史事件（语义关联依赖模型调用时的判断）。属于"形状校验被当成真实性校验"模式的温和实例——事件真实存在，但语义错配无法机制化拦截。

### 优化原因

- 决策是后续 boundaryAudit、planning、approval 的事实来源，语义错配会沿证据链向下传播；
- 当前审计只能看到"匹配了某事件"，无法从决策记录本身判断匹配上下文是否相关；
- 成本可控，不改变 grill 路径的严格性。

### 涉及的阶段与时机

- **intake 与分类域**（`dev_flow_record_decision` 调用处）：匹配加固与审计上下文记录；
- **技能层**（grillme 的 record_decision 说明）：conclusion 必须引用用户原话。

### 设计方向

1. **匹配上下文入账**：决策记录携带匹配到的 eventId、事件文本与时间，审计可直接核对语义相关性；
2. **question 参与匹配约束**：conclusion 匹配的事件前后上下文与 question 相关才通过，无关则要求走 grill 重新确认；
3. **技能层强制**：conclusion 必须引用用户原话、禁止模型改写，降低"结论与事件同文本但语义不同"的概率。

## 13. 启动与分类域：route-confirmation basisHash 未纳入项目配置

### 现状问题

`lockClassification` / `reclassifyFeature` 的 route-confirmation `basisHash = hash(facts + orderedRoute + controls)`（`state-store.ts`），**不含 project config sha256**。确认与落账之间若 `update_project` 改变验证命令配置，确认不会失效（`ROUTE_CONFIRMATION_STALE` 不会触发）。

### 优化原因

- 配置变化会改变后续 verification 的可执行性，属于"确认依据"的一部分；
- 现有缓解：`update_project` 返回受影响证据并使引用命令变化的 Trace/RU stale——有兜底，但路线确认这一层没有绑定；
- 成本一行，收益是确认与落账间的配置漂移也被拦截。

### 涉及的阶段与时机

- **route-confirmation 呈现与确认**（`lockClassification` / `reclassifyFeature` / `confirmRouteClassification` / `resolveRouteClassificationElicitation`）：basisHash 计算处。

### 设计方向

- basisHash 纳入 `projectConfigSha256`（与 approvalBasis、review basis 的既有做法对齐）；
- 确认时重算发现配置漂移 → 与 `ROUTE_CONFIRMATION_STALE` 同一路径处理。

## 14. 状态与交互域：inspect 与 assertReviewComplete 的 blocking 计算路径不一致

### 现状问题

`inspection.ts` 的 review 主题只用 `unresolvedBlockingFindings({ findingEvents })` 计算未解决 blocker——这是 v3 findingEvents 路径；而 `assertReviewComplete`（`plugins/dev-flow/src/core/review-jobs.ts`）在 findingEvents 为空时走 **jobs + dispositions 路径**计算 blocker。旧格式批次（无 findingEvents）时，inspect 可能显示 0 blocking，而 `record_step` 实际会拒绝——**显示与执行的判定依据不一致**，模型可能依据 inspect 结果误判审查已通过。

### 优化原因

- 状态投影是模型与用户判断流程状态的依据，与执行层判定不一致会造成误导与往返；
- 两条路径（findingEvents 与 jobs+dispositions）已并存于代码库，统一计算入口是纯一致性修复，不改变任何审查行为。

### 涉及的阶段与时机

- **状态与交互域**（`dev_flow_inspect` 的 review 主题）：blocking 计算处；
- **plan_review 推进**（`assertReviewComplete`）：与 inspect 共用同一计算函数。

### 设计方向

- 抽取统一的 `currentUnresolvedBlocking` 计算：同时覆盖 findingEvents 路径与 jobs+dispositions 路径，inspect 与 assertReviewComplete 共用；
- 或 inspect 同时报告两条路径的结果（findingEvents 计数 + jobs/dispositions 计数），明确标注各自依据。

## 15. 对账域：finalize 不报告 excluded 路径的内容变化

### 现状问题

用户对未归属路径选择 `exclude`（排除并先处理）后，该路径的后续内容变化在工作区对账与交付快照中被静默忽略——`createDeliverySnapshot` 只列 feature-owned 文件，`DELIVERY_FILE_UNREGISTERED` 不拦 excluded 路径，finalize 也不报告"excluded 但内容仍变化"的路径。用户明确排除后若忘了处理，最终交付不含该路径（正确），但流程不提供任何可见性提示。

### 优化原因

- 设计意图正确（用户明确排除即不算交付），但透明性缺失：排除时的承诺是"先处理"，finalize 是最后一次检查点，应提示排除路径仍有未处理变更；
- 低成本纯展示改进，不改变交付语义与归属决策。

### 涉及的阶段与时机

- **finalize 交付快照生成**（`createDeliverySnapshot`，`delivery-snapshot.ts`）：报告处。

### 设计方向

- finalize 报告（交付快照文档或响应摘要）增加一行：excluded 且内容仍有变化的路径清单；
- 仅提示不改语义：不阻塞 finalize，不重新打开归属决策。

## 16. 宿主 hook 层：授权记忆无时效

### 现状问题

`host-authorization.ts` 的授权记忆（`host-authorization-granted` 记录）在 feature 生命周期内**永久有效**：用户确认过一次的破坏性命令（task-reusable 类：`rm -rf`、`git reset --hard`、`git clean -f`、`git checkout --`、`git rebase` 等，仓库内且同命令指纹），同一 feature 后续执行**自动 allow，不再询问**。跨长时间会话（同一天早晚、跨天），用户"早上确认过"的预期可能已变化，但危险命令仍被自动放行。

### 优化原因

- 同命令同指纹（用户确实确认过这条命令）所以不是信任漏洞，但**放行的"时间边界"缺失**——授权应反映"用户当前时点的意愿"，而非 feature 生命周期内的一次性承诺；
- 破坏性命令是 task-reusable 类，正是"用户确认过就想省事"与"时间久了想再确认"之间最敏感的一类；
- 低成本改动：granted 记录携带时间，允许判定加时间窗口。

### 涉及的阶段与时机

- **PermissionRequest 授权判定**（`evaluatePermissionRequest` 的 granted 匹配处）：时效校验点；
- **PostToolUse 授权记忆**（`recordPermissionPostToolUse`）：granted 记录的时间戳。

### 设计方向

- granted 记录加时间窗口（如 60 分钟）：窗口内同 feature + 同风险类 + 同命令指纹自动 allow，超窗回到宿主原生确认；
- 或按轮次/会话失效（turn-boundary 事件重置授权），更适合"会话级"预期；
- always-confirm 类（外部发布）不受影响——本来每次都问；
- 权衡：确认过的命令在窗口后会再次询问（可接受的打扰），换取危险命令放行的时间边界。

## 17. 审查"角色/轴级"重跑未实现（比 spec 保守）

### 现状问题

spec（§187）要求"计划或代码变化只让相关审查角色或轴重新执行"，当前实现是**整步骤重开**：

- 代码变化后（issue 21 失效传播），`code_review` 双轴整体重做——质量轴与需求忠实度轴没有各自的内容指纹，无法判断哪个轴受变化影响；
- 计划变化后（issue 17 计划修订），plan review 批次整体作废重建，没有按角色（如 security/architecture 角色）定位受影响者；
- 无法定位差异时的完整重审兜底已实现（`unknownDiffInfo`），但"可定位时只重跑受影响轴/角色"的精确失效未落地。

### 优化原因

- 与"局部变化只重做受影响工作"的核心原则存在差距：小修复会触发整份双轴重审，成本随代码量放大；
- 双轴 evidence 已有结构（`axes.quality/fidelity`），补轴级指纹（记录各轴审查时的快照或文件集合）即可支持轴级失效判定；
- 安全方向正确（重做多于必需），所以属于效率与体验优化，不阻塞正确性。

### 涉及的阶段与时机

- **code_review 记录**（`recordStep` 双轴 evidence）：为每个轴补充内容指纹；
- **失效传播**（`change-invalidation.ts`）：变化文件命中某轴审查依据时只重开该轴；
- **计划修订**（`applyPlanRevision` / review 批次重建）：按角色命中的文件/任务范围决定重建范围。

### 设计方向

- 轴级指纹：双轴 evidence 增加 `axes.quality.fingerprint` / `axes.fidelity.fingerprint`（逐文件快照引用），失效传播按文件归属轴；
- 角色级重跑：plan review 批次记录每个 job 的审查切片（文件/任务范围），变化只使命中切片的 job 失效（stale），未命中 job 复用（类似 issue 16 的 `unknownDiffInfo` 反向）；
- 无法定位时维持现有完整重审兜底。
